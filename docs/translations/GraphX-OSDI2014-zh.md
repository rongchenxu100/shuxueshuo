## 摘要

为了追求图处理性能，系统领域在很大程度上放弃了通用分布式数据流框架，转而采用专用图处理系统。这些系统提供量身定制的编程抽象，并加速迭代式图算法的执行。本文主张，专用图处理系统的许多优势都可以在现代通用分布式数据流系统中重新获得。

我们提出 GraphX：一个构建在广泛使用的分布式数据流系统 Apache Spark 之上的嵌入式图处理框架。GraphX 提供一种熟悉、可组合的图抽象，足以表达现有图 API，同时只需少数基本数据流算子（如连接、映射和分组）即可实现。为了达到专用图系统的性能水平，GraphX 将图特有的优化重新表述为分布式连接优化和物化视图维护。借助分布式数据流框架的进展，GraphX 还为图处理带来了低成本容错。

我们使用真实工作负载评估 GraphX。结果表明，与基础数据流框架相比，GraphX 可获得一个数量级的性能提升；它既能达到专用图处理系统的性能，又支持范围更广的计算。

**图 1　GraphX 是位于通用 Spark 数据流框架之上的一个薄层（括号内为代码行数）。** GraphX 约 2,500 行，Spark 约 30,000 行；GAS Pregel API 约 34 行，PageRank、连通分量、K-core、三角形计数、LDA 与 SVD++ 等算法通常只需数十至数百行。

## 1　引言

图数据的规模与重要性不断增长，推动了 Pregel [22]、PowerGraph [13] 及许多其他专用图处理系统 [7, 9, 37] 的发展。这些系统公开专门化抽象，并以图特有的优化作为支撑，因此能够自然地表达并高效执行 PageRank [30]、社区发现 [18] 等迭代式图算法，处理包含数十亿顶点和边的图。其结果是，图处理系统的性能通常比 Hadoop MapReduce 一类通用分布式数据流框架高出若干数量级 [13, 20]。

然而，受限的专门化也有代价。图通常只是更大分析流程的一部分，而整个流程往往还要结合非结构化数据和表格数据。因此，分析流水线（例如图 11）不得不组合多个系统，增加复杂性，并导致不必要的数据移动与重复。为了性能，图处理系统还经常放弃常规容错，转而采用快照恢复。最后，作为专用系统，图处理框架通常也享受不到分布式数据流框架所拥有的广泛生态支持。

相比之下，通用分布式数据流框架（如 MapReduce [10]、Spark [39] 和 Dryad [15]）提供丰富的数据流算子，如映射、归约、分组和连接；它们适于分析非结构化与表格数据，并已得到广泛采用。但是，直接用数据流算子实现迭代式图算法颇具挑战，常常需要多个复杂连接阶段。此外，分布式数据流框架中的通用连接与聚合策略没有利用迭代式图算法的常见模式与结构，因而错失了重要的优化机会。

从历史上看，图处理系统与分布式数据流框架分别演化，原因有若干。第一，早期分布式数据流框架（如 MapReduce）强调单阶段计算和磁盘处理，这限制了它们对迭代式图算法的适用性；后者会反复、随机地访问图的不同子集。第二，早期数据流框架不允许细粒度控制数据划分，妨碍了图划分技术的应用。但新的内存型分布式数据流框架（如 Spark 和 Naiad）允许控制数据划分和内存表示，已经缓解其中一些限制。

鉴于这些进展，我们认为存在这样一个机会：把图处理系统与数据流系统两方面的进展统一起来，让单一系统覆盖完整分析流水线。本文探讨如何在通用分布式数据流系统之上设计图处理系统。我们的论点是：只要识别图计算中的基本数据流模式，并把图处理系统中的优化重新表述为数据流优化，就能在通用分布式数据流框架中重新获得专用图处理系统的优势。

为支持这一论点，我们提出 GraphX——嵌入 Spark [39] 分布式数据流系统的高效图处理框架。GraphX 提供熟悉且富有表达力的图 API（第 3 节）。我们使用 GraphX API 实现了流行 Pregel 抽象的一种变体以及一系列常见图操作。不同于既有图处理系统，GraphX API 允许把图与非结构化及表格数据组合起来；同一份物理数据既可以被视为图，也可以被视为集合，无须移动或复制数据。例如，用 GraphX 可以轻松地把社交图与用户评论连接起来，应用图算法，再把结果以集合或图的形式交给其他过程（如可视化或汇总）。因此，用户可以采用最适合当前任务的计算模式——图或集合——而无须牺牲性能或灵活性。

我们把 GraphX 构建成 Spark 之上的一个库（图 1）：将图编码为集合，再用标准数据流算子表达 GraphX API。GraphX 不需要修改 Spark。这揭示了一种把图计算嵌入分布式数据流框架的通用方法，也把图计算提炼为一种特定的“连接—映射—分组”数据流模式。将图计算归约为这一模式之后，我们便能确定系统优化的关键路径。然而，朴素地把图编码成集合，并用通用数据流算子执行迭代式图计算，仍可能十分缓慢、低效。

为了达到专用图处理系统的性能，GraphX 在图的集合编码方式以及常用数据流算子的执行方式上引入了一系列优化（第 4 节）。系统采用灵活的顶点切分来把图编码成水平划分的集合，从而达到分布式图划分的先进水平。GraphX 把图处理系统中的优化改写成连接优化（如 CSR 索引、连接消除和连接位置指定）以及物化视图维护（如顶点镜像和增量更新），再将其应用于 Spark 数据流算子。借助逻辑划分和血缘关系，GraphX 实现了低成本容错。最后，利用不可变性，GraphX 能够在图视图、集合视图和多轮迭代之间复用索引，从而降低内存开销并改善性能。

我们在真实图上评估 GraphX，并将它同两类实现比较：直接使用 Spark 数据流算子实现的图算法，以及使用专用图处理系统的实现。实验表明，GraphX 在保留通用数据流框架优势的同时，可以达到专用图处理系统的性能。

本文的主要贡献如下：

1. 提出统一的图与集合 API。该 API 足以表达现有图抽象，并支持范围宽得多的计算。
2. 将采用顶点切分的图嵌入水平划分的集合，并用少量通用数据流算子实现 GraphX API。
3. 提出分布式连接与物化视图优化，使通用分布式数据流框架能够以专用图系统的性能执行图计算。
4. 在真实大规模图上开展评估，用常见基准算法将 GraphX 与广泛使用的图处理系统进行比较。

## 2　背景

本节回顾图处理系统与分布式数据流框架的设计权衡和局限。从高层看，图处理系统以顶点及其邻域为计算粒度，并利用图预先定义的稀疏依赖结构。相较之下，通用分布式数据流框架把计算定义为数据流算子，其粒度或者是单个数据项（如过滤、映射），或者是整个集合（如非广播连接一类需要混洗的操作）。

### 2.1　属性图数据模型

图处理系统使用属性图 [33] 表示图结构数据，即为每个顶点和每条边关联用户定义的属性。属性既可包括元数据（如用户资料和时间戳），也可包括程序状态（如顶点的 PageRank 或推断出的亲和度）。由社会网络、Web 图等自然现象生成的属性图，往往具有高度偏斜的幂律度分布，而且边数通常比顶点数高出若干数量级 [18]。

数据流系统中的算子（如连接）可以跨越多个集合；与之不同，图处理系统中的操作（如顶点程序）通常只针对一张具有预先声明稀疏结构的属性图来定义。这种受限的关注范围虽然有利于多种优化（第 2.3 节），却也使跨多张图和子图的分析任务更难表达。

### 2.2　图并行抽象

从 PageRank 到潜在因子分析，许多算法都会根据相邻顶点和边的属性，迭代地变换顶点属性。这种反复执行局部变换的共同模式构成了图并行抽象的基础。在图并行抽象 [13] 中，每个顶点都并发实例化一个用户定义的顶点程序，并通过消息（如 Pregel [22]）或共享状态（如 PowerGraph [13]）同相邻顶点程序交互。每个顶点程序都能读取和修改本顶点的属性；在某些系统 [13, 20] 中还可访问相邻顶点属性。当所有顶点程序都投票停止时，整个程序终止。

作为具体示例，代码清单 1 用 Pregel 顶点程序表达 PageRank。顶点 \(v\) 的程序首先对消息求和，这些消息编码了相邻顶点加权后的 PageRank；然后用所得总和更新 PageRank，并把新值按链接数加权后广播给邻居。最后，顶点程序判断自己是否已经局部收敛，并投票停止。

```scala
def PageRank(v: Id, msgs: List[Double]) {
  // 计算消息总和
  var msgSum = 0
  for (m <- msgs) { msgSum += m }
  // 更新 PageRank
  PR(v) = 0.15 + 0.85 * msgSum
  // 广播包含新 PR 的消息
  for (j <- OutNbrs(v)) {
    msg = PR(v) / NumLinks(v)
    send_msg(to = j, msg)
  }
  // 检查终止条件
  if (converged(PR(v))) voteToHalt(v)
}
```

**代码清单 1　Pregel 中的 PageRank。** 计算入站消息之和，更新顶点的 PageRank，把新加权值发送给相邻顶点；如果 PageRank 未发生变化，顶点程序便投票停止。

不同系统中顶点程序的并发程度不同。多数系统 [7, 13, 22, 34] 采用批量同步执行模型：所有顶点程序在一系列超步中并发运行。有些系统 [13, 20, 37] 也支持异步执行模型，在资源可用时运行顶点程序，以缓解拖尾任务的影响。不过，异步编程模型带来的收益往往会被额外复杂性抵消。因此，本文关注批量同步模型，并依靠流水线与推测执行等系统级技术处理拖尾任务。

图并行抽象很适合遵循静态邻域结构的迭代式图算法（如 PageRank），却不适合表达互不相连顶点之间的交互，也不适合表达改变图结构的计算。例如，从原始文本或非结构化数据构图、图粗化以及跨多张图的分析，都很难在以顶点为中心的编程模型中表达。

### 2.3　图系统优化

图并行抽象施加的限制与图的稀疏结构共同促成了多项重要的系统优化。

**GAS 分解。** Gonzalez 等人 [13] 观察到，多数顶点程序同相邻顶点交互时，先以广义的交换结合求和来收集消息，再在一个天然并行的循环中广播新消息。他们提出 GAS 分解，把顶点程序拆分为三个数据并行阶段：收集（Gather）、应用（Apply）与分发（Scatter）。代码清单 2 将 PageRank 顶点程序拆成了这三个阶段。

```scala
def Gather(a: Double, b: Double) = a + b

def Apply(v, msgSum) {
  PR(v) = 0.15 + 0.85 * msgSum
  if (converged(PR(v))) voteToHalt(v)
}

def Scatter(v, j) = PR(v) / NumLinks(v)
```

**代码清单 2　采用 GAS 的 PageRank。** 收集阶段合并入站消息；应用阶段使用最终消息总和更新顶点属性；分发阶段定义每条边上的消息计算。

GAS 分解导出了一种拉取式消息计算模型：系统向顶点程序询问相邻顶点间消息的值，而不是由用户直接从顶点程序发送消息。因此，GAS 分解支持顶点切分、改善负载均衡、支持串行边迭代 [34]，并减少数据移动。不过，它也禁止不相邻顶点之间直接通信，因而不利于表达更一般的通信模式。

**图划分。** 图处理系统使用多种图划分算法 [16]，以减少通信并均衡计算。Gonzalez 等人 [13] 证明，顶点切分 [12] 对许多大型自然图效果良好。顶点切分把边均匀分配给机器，同时尽量减少每个顶点被切分的次数。

**镜像顶点。** 高度数顶点往往在同一台远程机器上有多个邻居。与其通过网络发送多条通常完全相同的消息，图处理系统 [13, 20, 24, 32] 会采用镜像技术：只向镜像发送一条消息，再由镜像转发给所有邻居。图处理系统利用静态图结构复用镜像数据结构。

**活跃顶点。** 随着图算法推进，图中不同顶点程序以不同速度收敛，使工作集（活跃顶点程序的集合）快速缩小。近期系统 [11, 13, 20, 22] 会追踪活跃顶点，消除针对已收敛顶点的数据移动和无用计算。此外，这些系统通常维护紧凑、高效的数据结构（如压缩稀疏行 CSR），从而以常数时间访问活跃顶点相邻的本地边。

### 2.4　分布式数据流框架

本文用“分布式数据流框架”指 MapReduce 及其推广形式一类的集群计算框架。尽管各框架细节不同，它们通常具有以下性质：

1. 数据模型由带类型的集合组成，即把表推广到非结构化数据。
2. 粗粒度的数据并行编程模型由确定性算子构成，这些算子负责变换集合，如映射、分组和连接。
3. 调度器把每个作业拆成任务的有向无环图（DAG），每个任务处理一个水平数据分区。
4. 运行时能够容忍拖尾任务和部分集群故障，而不必重启整个作业。

MapReduce 编程模型只提供两个数据流算子：map 和 reduce（亦即 group-by），每个作业的任务 DAG 至多包含两层。DryadLINQ [15]、Pig [29] 和 Spark 等较新的框架则提供 fold、join 等更多算子，并可执行具有多层依赖关系的任务。

分布式数据流框架已广泛用于 ETL、SQL 查询处理和迭代式机器学习等多种数据处理任务，并已证明能够扩展到数千节点和 PB 级数据。本文聚焦于 GraphX 所构建在其上的 Apache Spark。Spark 的若干特性对 GraphX 尤具吸引力：

1. Spark 的存储抽象“弹性分布式数据集”（RDD）允许应用把数据留在内存中，这对迭代式图算法至关重要。
2. RDD 允许用户定义数据划分；执行引擎可利用划分信息对 RDD 进行协同划分与协同调度，避免数据移动。这是编码分区图的基础。
3. Spark 记录构建 RDD 所用操作的血缘关系，发生故障时可自动重建丢失的分区。即使应用长时间运行，血缘图也相对较小，因此这种方法与检查点不同，运行时开销可以忽略，可始终开启而无须担心性能。Spark 还支持可选的分布式内存复制，以减少故障后的重新计算。
4. Spark 提供易于扩展的 Scala 高级 API，便于为集合和图创建连贯统一的 API。

我们相信，GraphX 的许多思想也可以应用到其他现代数据流系统。第 6 节将讨论 GraphLINQ 的初步工作——它是 Naiad 中的图处理框架。

## 3　GraphX 编程抽象

下面从通用数据流框架的角度重新审视图计算。我们把属性图数据模型重新表述成集合，把图并行抽象重新表述成特定的数据流算子模式。这个过程揭示了图并行计算的基本结构，也确定了高效执行图算法所需的关键算子。

### 3.1　将属性图表示为集合

第 2.1 节所述属性图在逻辑上可以表示为一对顶点属性集合与边属性集合。顶点集合包含以顶点标识符为唯一键的顶点属性。GraphX 的顶点标识符是 64 位整数，可以来自外部（如用户 ID），也可以通过对顶点属性（如网页 URL）应用哈希函数得到。边集合包含以源、目标顶点标识符为键的边属性。

把属性图归约为一对集合之后，图就能在分布式数据流框架中同其他集合组合起来。添加顶点属性等操作可以自然地表达为与顶点属性集合的连接。分析图计算结果（最终顶点和边属性）以及比较多张图上的属性，也简化为分析和连接相应集合。这些任务在广义图分析中都十分常见，却得不到图并行抽象的良好支持。

还可以组合不同的顶点与边属性集合来构造新的属性图。例如，可以构造逻辑上不同、顶点属性彼此独立的图——一张存储 PageRank，另一张存储连通分量成员关系——同时共享同一个边集合。这看似只是一项小成果，但专用图处理系统中顶点与边的紧密集成，往往连这种基本复用也会妨碍。此外，共享顶点或边集合的图还可共享图专用索引，降低存储开销并提高性能。

### 3.2　将图计算表示为数据流操作

把属性图规范化为一对顶点与边属性集合，使我们能够把图嵌入分布式数据流框架。本节说明如何组合数据流算子来表达图计算。

第 2.2 节介绍的图并行计算，需要计算每个顶点邻域的聚合属性，例如按边权加权后对相邻顶点的 PageRank 求和。在分布式数据流框架中，这一计算可以表达成若干连接与分组阶段，并在其间插入映射操作。在连接阶段，顶点属性与边属性连接，形成“三元组视图”[^1]：每条边及其对应源、目标顶点属性的组合。

```sql
CREATE VIEW triplets AS
SELECT s.Id, d.Id, s.P, e.P, d.P
FROM edges AS e
JOIN vertices AS s JOIN vertices AS d
ON e.srcId = s.Id AND e.dstId = d.Id
```

**代码清单 3　用 SQL 构造三元组。** 列 `P` 表示顶点和边属性集合中的属性。

三元组视图可以由代码清单 3 的 SQL 最清楚地说明：它是以源、目标顶点 ID 为键的三路连接。在分组阶段，三元组按源顶点或目标顶点分组，以构造每个顶点的邻域并计算聚合。例如，计算顶点 PageRank 可执行：

```sql
SELECT t.dstId, 0.15 + 0.85 * sum(t.srcP * t.eP)
FROM triplets AS t
GROUP BY t.dstId
```

迭代执行上述查询以更新顶点属性，直到属性收敛，即可算出每个顶点的 PageRank。

这两个阶段涵盖了第 2.3 节的 GAS 分解。分组阶段收集发往同一顶点的消息；中间的映射操作应用消息总和以更新顶点属性；连接阶段则把新的顶点属性分发给所有相邻顶点。

同样地，可以迭代组合连接、分组和数据并行映射阶段，实现 Pregel 抽象的 GAS 分解。每轮迭代首先执行连接，把活跃顶点与其出边绑定；然后利用三元组视图，在映射阶段沿每个三元组计算消息，再在分组阶段按目标顶点聚合；最后，在顶点集合上的映射阶段，由顶点程序接收消息。

Pregel 抽象的数据流嵌入表明，图并行计算可以表示为简单的连接与分组算子序列。同时，它也凸显了两个需要高效处理的问题：在连接阶段维护三元组视图，以及在分组阶段计算邻域聚合。因此，图处理系统的性能优化主要集中于这两个阶段。第 4 节将介绍其高效实现。

[^1]: “三元组”一词源自经典的资源描述框架（RDF），见第 6 节。

### 3.3　GraphX 算子

GraphX 编程抽象通过引入少量专用图算子，扩展了 Spark 数据流算子。代码清单 4 汇总了这些算子。

```scala
class Graph[V, E] {
  // 构造器
  def Graph(v: Collection[(Id, V)],
            e: Collection[(Id, Id, E)])

  // 集合视图
  def vertices: Collection[(Id, V)]
  def edges: Collection[(Id, Id, E)]
  def triplets: Collection[Triplet]

  // 图并行计算
  def mrTriplets(
    f: (Triplet) => M,
    sum: (M, M) => M): Collection[(Id, M)]

  // 便捷函数
  def mapV(f: (Id, V) => V): Graph[V, E]
  def mapE(f: (Id, Id, E) => E): Graph[V, E]
  def leftJoinV(v: Collection[(Id, V)],
                f: (Id, V, V) => V): Graph[V, E]
  def leftJoinE(e: Collection[(Id, Id, E)],
                f: (Id, Id, E, E) => E): Graph[V, E]
  def subgraph(vPred: (Id, V) => Boolean,
               ePred: (Triplet) => Boolean): Graph[V, E]
  def reverse: Graph[V, E]
}
```

**代码清单 4　图算子。** 这些算子用于变换顶点与边集合。

`Graph` 构造器在逻辑上把一对顶点和边属性集合绑定成属性图，同时验证完整性约束：每个顶点只出现一次，边不会连接到不存在的顶点。反过来，`vertices` 和 `edges` 算子公开图的顶点与边属性集合。

`triplets` 算子返回第 3.2 节（代码清单 3）所述三元组视图。如果三元组视图已经存在，就增量维护原视图，避免完整连接（见第 4.2 节）。

`mrTriplets`（Map Reduce Triplets，映射—归约三元组）算子编码了第 3.2 节所定义的图并行计算核心两阶段过程。在逻辑上，它是在三元组视图上组合映射与分组数据流算子。用户定义的映射函数作用于每个三元组，产生一个值（即类型为 `M` 的消息），再用用户定义的二元聚合函数在目标顶点聚合：

```sql
SELECT t.dstId, reduceF(mapF(t)) AS msgSum
FROM triplets AS t
GROUP BY t.dstId
```

`mrTriplets` 产生一个集合，其中包含以目标顶点 ID 为键的入站消息总和。例如，图 2 使用该算子计算社交网络中每位用户年龄比自己大的关注者人数。因为结果集合只包含图中一部分顶点，所以可复用原顶点集合的索引。

**图 2　`mrTriplets` 使用示例。** 对每条边，映射函数在源用户年龄大于目标用户时返回 1，否则返回 0；按目标顶点归约后，得到每个顶点的年长关注者数量。

代码清单 4 还包含若干简化顶点或边集合数据流操作的函数。它们仅为调用者便利而定义，并非抽象的必要组成部分，也很容易用标准数据流算子实现。例如：

```scala
g.mapV(f) ≡ Graph(g.vertices.map(f), g.edges)
```

代码清单 5 使用 GraphX API 实现了 Pregel 抽象的 GAS 分解。首先给顶点属性增加一个字段，用于追踪尚未投票停止的活跃顶点。只要仍有活跃顶点，就用 `mrTriplets` 计算消息，并把顶点程序作用于消息总和。

```scala
def Pregel(
    g: Graph[V, E],
    vprog: (Id, V, M) => V,
    sendMsg: (Triplet) => M,
    gather: (M, M) => M): Collection[V] = {
  // 将所有顶点设为活跃
  g = g.mapV((id, v) => (v, halt = false))
  // 迭代直至收敛
  while (g.vertices.exists(v => !v.halt)) {
    val msgs: Collection[(Id, M)] =
      g.subgraph(ePred = (s,d,sP,eP,dP) => !sP.halt)
       .mrTriplets(sendMsg, gather)
    // 接收消息并运行顶点程序
    g = g.leftJoinV(msgs).mapV(vprog)
  }
  return g.vertices
}
```

**代码清单 5　增强版 Pregel。** 使用 GraphX API 实现 Pregel 抽象。

把消息计算表达为边并行映射后接交换结合聚合，可以借助 GAS 分解降低高度数顶点的成本。让消息计算看到完整三元组，也能简化连通分量等算法。对于不需要完整三元组的情形——例如 PageRank 只需源属性——系统依靠用户定义函数（UDF）的字节码分析自动删除连接中未使用的字段（见第 4.3.2 节）。

代码清单 6 用 GraphX 版 Pregel 实现连通分量算法，为每个顶点计算可达顶点中的最小 ID。首先用 `mapV` 把每个顶点属性初始化为自身 ID，然后定义 GraphX Pregel API 所需的三个函数。`sendMsg` 借助边的三元组视图，只在相邻顶点的分量 ID 应改变时发送消息；`gatherMsg` 计算入站消息值的最小值；顶点程序 `vProg` 则确定新的分量 ID。

```scala
def ConnectedComp(g: Graph[V, E]) = {
  g = g.mapV(v => v.id)

  def vProg(v: Id, m: Id): Id = {
    if (v == m) voteToHalt(v)
    return min(v, m)
  }

  def sendMsg(t: Triplet): Id =
    if (t.src.cc < t.dst.cc) t.src.cc
    else None

  def gatherMsg(a: Id, b: Id): Id = min(a, b)

  return Pregel(g, vProg, sendMsg, gatherMsg)
}
```

**代码清单 6　连通分量。** 使用 Pregel 为每个顶点计算可达的最小顶点 ID。

**组合图算子与集合算子。** 一组相互连通的顶点有时更适合建模为单个顶点。此时可以把具有共同特征（如同属一个 Web 域）的相连顶点聚合起来，对图进行粗化，从而得到一张新图（如域级图）。代码清单 7 使用 GraphX 抽象实现图粗化。

粗化操作接收边谓词和顶点聚合函数，折叠所有满足谓词的边，并合并相应顶点。首先用边谓词构造待折叠边的子图，即修改图结构；然后在该子图上运行图并行连通分量算法。每个连通分量对应粗化图中的一个超顶点，分量 ID 是该分量内最小的顶点 ID。使用数据并行聚合算子，把拥有相同分量 ID 的所有顶点聚合起来，构造超顶点。最后更新边，使其连接超顶点，并生成可供后续图并行计算的新图。

```scala
def coarsen(
    g: Graph[V, E],
    pred: (Id, Id, V, E, V) => Boolean,
    reduce: (V, V) => V) = {
  // 将图限制为可收缩的边
  val subG = g.subgraph(v => true, pred)
  // 计算所有顶点的连通分量 ID
  val cc: Collection[(Id, ccId)] =
    ConnectedComp(subG).vertices
  // 合并同一分量中的顶点
  val superV: Collection[(ccId, V)] =
    g.vertices.leftJoin(cc).groupBy(CC_ID, reduce)
  // 连接各分量之间剩余的边
  val invG = g.subgraph(ePred = t => !pred(t))
  val remainingE: Collection[(ccId, ccId, E)] =
    invG.leftJoin(cc).triplets.map {
      e => (e.src.cc, e.dst.cc, e.attr)
    }
  Graph(superV, remainingE)
}
```

**代码清单 7　图粗化。** 合并由满足边谓词的边连接起来的顶点。

`coarsen` 算子在一个图分析任务中同时组合数据并行与图并行算子，展示了统一抽象的力量。

## 4　GraphX 系统

GraphX 把第 2.3 节的图专用优化重新表述为 Spark 中少量标准数据流算子的优化，由此达到专用图处理系统的性能。本节在传统数据库系统经典技术——索引、增量视图维护和连接优化——的语境下介绍这些优化，并沿途量化其效果；数据集和实验设置详见第 5 节。

### 4.1　分布式图表示

GraphX 在内部把图表示成一对构建在 Spark RDD 抽象之上的顶点集合与边集合。这些集合在 RDD 之上增加了索引和图专用划分层。图 3 展示了水平划分的顶点、边集合及其索引的物理表示。

顶点集合按顶点 ID 进行哈希划分。为了支持顶点集合间频繁连接，每个分区中的顶点都存储在本地哈希索引中（第 4.2 节）。系统还使用一个位掩码记录各顶点的可见性，从而以软删除方式促进索引复用（第 4.3.1 节）。

边集合由用户定义的划分函数进行水平划分。GraphX 支持顶点切分，这能减少社会网络和 Web 图等自然图中的通信 [13]。默认情况下，边按输入集合的划分（如其在 HDFS 上的原始位置）分配给各分区。GraphX 也内置了多种划分函数，包括对 `mrTriplets` 等算子的通信复杂度具有严格上界 [8] 的二维哈希划分器。第 4.2 节所述路由表带来了这种边放置灵活性。

为了按源、目标顶点高效查找边，每个分区内部都使用压缩稀疏行（CSR）表示 [35] 按源顶点 ID 对边聚簇，并按目标 ID 建立哈希索引。第 4.3.1 节将说明这些索引如何加速迭代计算。

**索引复用。** GraphX 继承了 Spark 的不可变性，所以所有图算子在逻辑上都会创建新集合，而非破坏性地修改原集合。因此，派生的顶点和边集合通常能够共享索引，既减少内存开销，又加速本地图操作。例如，顶点哈希索引支持快速聚合，聚合结果还能与原顶点共享索引。

共享索引也能加速连接。具有相同索引的顶点集合（如顶点集合，以及来自 `mrTriplets` 的消息集合）可以通过协调扫描完成连接，类似归并连接，而无须执行任何索引查找。在基准测试中，索引复用使 Twitter 图上 PageRank 的单轮运行时间降低 59%。

GraphX 算子会尽可能复用索引。不修改图结构的算子（如 `mapV`）自动保留索引。对于限制图结构的操作（如 `subgraph`），GraphX 依靠位掩码构建受限视图。若索引复用可能降低效率（如图被高度过滤），可使用 `reindex` 算子建立新索引。

**图 3　分布式图表示。** 左侧图在右侧表示为顶点集合与边集合。边由划分函数（如二维划分）分到三个边分区；顶点按 ID 划分。GraphX 维护一张与顶点协同划分的路由表，记录每个顶点对应哪些边分区。若顶点 6 及其相邻边被 `subgraph` 等操作排除，系统只需更新位掩码，将它们从相应集合视图中移除，从而继续复用索引。

### 4.2　三元组视图的实现

第 3.2 节指出，图计算的关键阶段之一是构造和维护三元组视图。该视图是源顶点属性、目标顶点属性和边属性之间的三路连接。

**顶点镜像。** 顶点与边属性集合各自独立划分，因此连接需要移动数据。GraphX 把顶点属性通过网络发送到边所在位置，以边分区作为连接位置 [21]，由此完成三路连接。这样做能显著减少通信，原因有二：第一，真实图的边数通常比顶点数高出若干数量级；第二，同一顶点可能在同一分区中拥有许多边，因而顶点属性可以大量复用。

**多播连接。** 把所有顶点发送到每个边分区的广播连接虽然也能保证连接发生在边分区，却可能十分低效，因为大多数分区只需要顶点的一小部分。GraphX 因此引入多播连接：每个顶点属性只发送到包含其相邻边的边分区。GraphX 为每个顶点维护具有相邻边的边分区集合。这些连接位置信息存储在路由表中；路由表与顶点集合协同划分（图 3），关联于边集合，并在首次实例化三元组视图时延迟构建。

多播连接策略提供的划分灵活性，使复杂的应用专用图划分技术成为可能。例如，Ugander 等人 [38] 对 Facebook 社交网络采用按城市划分，使查询时间降低 50.5%。第 5.1 节利用样本数据集的优化划分，与二维哈希划分相比，最多将运行时间降低 56%、通信量降低 5.8 倍。

**部分物化。** 顶点属性变化时立即复制顶点，但边分区上的本地连接不进行物化，以避免数据重复。镜像顶点属性存储在各边分区的哈希映射中，构造三元组时再引用。

**增量视图维护。** 迭代式图算法每轮通常只修改部分顶点属性。因此，GraphX 对三元组视图应用增量视图维护，以避免移动未变化的数据。每个图操作之后，系统追踪自上次构造三元组视图以来哪些顶点属性发生了变化。下次访问三元组视图时，只有已变化顶点会被重新路由到其边分区连接位置；未变化顶点继续复用本地镜像值。图算子会自动管理这一机制。

**图 4　增量维护三元组视图的效果。** 对 PageRank 和连通分量而言，随着顶点收敛，增量视图维护会降低通信量。最初通信量上升是因为消息压缩（第 4.4 节）：许多 PageRank 初值相同。

在收敛阈值设为 0 的 PageRank 中，活跃顶点数量下降缓慢，所以收益较温和。相反，在连通分量算法中，大多数顶点彼此距离很短，很快收敛，因此增量维护显著减少通信。若没有增量维护，每轮都必须从头重建三元组视图，通信量会在整个计算过程中一直保持峰值。

### 4.3　`mrTriplets` 优化

GraphX 为 `mrTriplets` 加入两项查询优化：过滤式索引扫描与自动连接消除。

#### 4.3.1　过滤式索引扫描

`mrTriplets` 的第一阶段在逻辑上需要扫描三元组视图，把用户定义的映射函数作用于每个三元组。但迭代式图算法逐渐收敛时，工作集通常会缩小，映射函数会跳过绝大多数三元组。具体而言，它只需处理包含活跃集合中顶点的三元组，而活跃集合由应用专用谓词定义。随着活跃集合缩小，直接扫描全部三元组会越来越浪费。

例如，在 Twitter 图的连通分量算法最后一轮中，只有少数顶点仍然活跃；但执行 `mrTriplets` 时，若无优化，仍须顺序扫描 15 亿条边并检查其顶点是否属于活跃集合。

为解决这个问题，GraphX 给三元组视图引入索引扫描。应用使用 `subgraph` 限制图，以表达当前活跃集合。顶点谓词被下推到边分区，在那里利用源顶点 ID 上的 CSR 索引（第 4.1 节）过滤三元组。系统测量顶点谓词的选择率；选择率低于 0.8 时，从顺序扫描切换为聚簇索引扫描。

**图 5　顺序扫描与索引扫描。** Twitter 图上的连通分量算法在第 4 轮之后切换为索引扫描，收益显著；PageRank 到第 15 轮时活跃顶点集合仍很大，因此收益较小。

与增量视图维护一样，索引扫描对 PageRank 运行时间的改善较小，对连通分量则改善显著。有趣的是，在连通分量最初几轮中，大部分顶点都处于活跃状态，顺序扫描略快，因为它不需要额外的索引查找。因此，GraphX 根据活跃顶点比例在全量扫描和索引扫描之间动态切换。

#### 4.3.2　自动连接消除

某些三元组视图操作只访问一个顶点属性，甚至完全不访问顶点属性。例如，用 `mrTriplets` 统计各顶点的度时，映射 UDF 不访问任何顶点属性；计算 PageRank 消息时则只使用源顶点属性。

GraphX 使用 JVM 字节码分析器在运行时检查用户定义函数，判断是否引用源或目标顶点属性。如果只引用其中一个属性，且三元组视图尚未物化，GraphX 会自动重写三元组视图的查询计划，把三路连接改为两路连接。如果两个顶点属性都未引用，则完全消除连接。

这一改写之所以可行，是因为三元组视图遵循 Spark RDD 的惰性语义：用户不访问它，它就不会物化。因此，调用 `mrTriplets` 时仍可重写生成三元组视图相关部分所需的连接。

**图 6　自动连接消除对通信量与运行时间的影响。** 在 Twitter 关注关系图上分别启用和禁用连接消除，运行 20 轮 PageRank。连接消除使传输数据量几乎减半，并显著缩短总执行时间。

第一轮通信量并未减少，这是因为压缩算法利用了所有消息初值完全相同这一事实。不过，压缩与解压本身仍消耗 CPU 时间，所以总运行时间仍接近减半。

### 4.4　其他优化

实现 GraphX 时，我们发现多项底层工程细节会显著影响性能，下面简要介绍其中几项。

**基于内存的混洗。** Spark 的默认混洗实现把临时数据物化到磁盘。我们修改了混洗阶段，使映射输出物化到内存，并在超时后删除临时数据。

**批处理与列式结构。** 在连接代码路径中，系统不逐个混洗顶点，而是把路由到同一目标连接位置的一批顶点打包，并将数据块从行式格式转换为列式格式，然后用 LZF 算法压缩后发送。批处理对 CPU 时间影响很小，却在基准测试中把 LZF 压缩率提高了 10%—40%。

**可变长整数编码。** GraphX 使用 64 位顶点 ID，但多数 ID 远小于 \(2^{64}\)。在混洗时，系统采用可变长编码：每个字节只用低 7 位编码数值，最高位表示是否还需要下一个字节。较小整数因此只需较少字节；最坏情况下，大于 \(2^{56}\) 的整数需要 9 个字节。这项技术使 PageRank 的通信量降低 20%。

## 5　系统评估

本节说明：对于迭代式图算法，GraphX 比直接使用第 3.2 节通用数据流算子的实现快一个数量级以上，并且能够达到或超过专用图处理系统的性能。

我们在若干图分析任务上评估 GraphX，并与以下系统比较：

1. **Apache Spark 0.9.1：** GraphX 的基础分布式数据流系统。与 Spark 比较，旨在说明 GraphX 相对基础数据流框架的性能收益。
2. **Apache Giraph 1.1：** 基于 Pregel 抽象的开源图计算系统。
3. **GraphLab 2.2（PowerGraph）：** 基于顶点程序 GAS 分解的开源图计算系统。GraphLab 用 C++ 实现，其他系统均运行在 JVM 上；在优化相同的条件下，预期 GraphLab 会有轻微性能优势。

我们还比较了禁用共享内存并行的 GraphLab，记作 **GraphLab NoSHM**。GraphLab 的同机工作进程通过共享数据结构通信；Giraph、Spark 和 GraphX 则采用无共享工作进程模型，同机工作进程之间也会产生额外序列化开销。为隔离这一开销，我们强制 GraphLab 工作进程在不同进程中运行，从而禁用共享内存。

值得注意的是，GraphLab 的共享数据结构增加了系统复杂性。我们曾在其中一个共享数据结构里发现并修复严重缺陷。补丁增加了一把锁，导致少量线程竞争。因此在某些情形（如图 7c）中，禁用共享内存反而略微改善性能。

所有实验均在 Amazon EC2 上使用 16 个 `m2.4xlarge` 工作节点进行。每个节点具有 8 个虚拟核心、68 GB 内存和两块硬盘，集群运行 64 位 Linux 3.2.28。图中给出每项实验多次试验的均值与标准差。

### 5.1　系统比较

跨系统基准测试往往不公平，因为很难以同等程度调优各系统。我们尽力减小这一影响，同各系统专家密切合作，以获得最优配置。需要强调的是，我们并不声称 GraphX 从根本上快于 GraphLab 或 Giraph；理论上，这些系统也可实现 GraphX 的相同优化。我们的目标是证明：在获得容错等通用数据流功能的同时，通用数据流引擎也可以达到专用图处理系统的性能。

尽管我们在 GraphX 上实现了大量图算法，性能评估仅选用 PageRank 和连通分量。这两种代表性算法已由多数图处理系统实现，行为易于理解，也足够简单，能够有效衡量系统性能。

为保证公平，PageRank 实现基于代码清单 1，不利用增量消息，因此从索引扫描和增量视图维护中受益较少。连通分量实现则只在顶点必须改变分量成员关系时发送消息，因此可从增量视图维护中获益。

### 5.2　GraphX 性能

**扩展性。** 图 8 评估 GraphX 在 Twitter 关注关系图上运行 PageRank 时的强扩展性能。从 8 台增至 32 台机器（4 倍），速度提高 3 倍；增至 64 台（8 倍）时，速度只提高 3.5 倍。

## 6　相关工作

第 2 节介绍了许多早期图处理系统共有的一般特征，但其中也存在值得注意的例外。

尽管大规模分布式图处理的大多数研究都聚焦静态图，仍有一些系统关注不同形式的流处理。较早的例子之一是 Kineograph [9]，它构造图的增量快照，供离线静态图分析。在多核环境中，GraphChi [17] 以及后来的 X-Stream [34] 支持在现有顶点之间、计算阶段之间添加边。

从概念上说，GraphX 可以支持增量加入边，甚至加入顶点，但现有数据结构还需进一步优化。GraphX 当前主要支持高效删除边与顶点，这是离线子图分析的基本功能。

早期图处理系统的多数优化与编程模型都面向单图场景。虽然其中一些系统 [19, 13, 34] 能独立处理多张图，却没有公开跨图（或跨表）操作的 API，也没有为此提供优化。一个值得注意的例外是 CombBLAS [7]：它把图乃至更一般的数据视为矩阵，并支持广义二元代数算子。GraphX 则保留图和表的原生语义，并提供简单 API 来组合不同表示中的数据。

GraphX 的三元组视图与经典的资源描述框架 [23]（RDF）数据模型有关，后者把图结构数据编码为“主语—谓语—宾语”三元组，例如“纽约市—属于—城市”。已有大量系统 [1, 6, 28] 用于存储 RDF 三元组，并在其上执行 SPARQL [31] 子图查询。与 GraphX 一样，这些系统也高度依赖索引与聚簇来获得性能；不同之处是，它们要么不是分布式系统，要么不处理迭代式图算法。尽管如此，我们相信 GraphX 的优化技术也可能有益于分布式图查询处理的设计。

近期已有若干工作探索在数据流系统中执行图算法。Najork 等人 [27] 比较了在 DryadLINQ [15] 和 SQL Server 数据流系统上实现的一系列图算法。然而，这些实现相当复杂且高度专用，对图专用优化讨论不多。

Ewen 等人 [11] 与 Murray 等人 [26] 都提出了面向增量迭代计算的数据流系统，并展示了图算法专用实现的性能收益。这些工作凸显了增量更新对图计算的重要性，却没有提出表达图算法的通用方法，也未提供增量数据流以外的图专用优化。我们相信 GraphX 可以移植到这些数据流框架之上，并可能从及时数据流 [26] 等进展中受益。

本文发表时，Microsoft Naiad 团队已经公布 GraphLINQ [25] 的初步工作。这是 Naiad 之上的图处理框架，与 GraphX 有许多相似之处。和 GraphX 一样，GraphLINQ 旨在通用数据流框架中提供丰富的图功能。它特别提供了 `GraphReduce` 算子，语义上类似 GraphX 的 `mrTriplets`，但操作的是顶点流与边流。对流处理的强调，为流处理文献中的经典优化以及 Naiad 及时数据流 [26] 等新进展创造了机会。这进一步支持了把图处理嵌入更通用数据处理系统的优势。

其他研究还探索了分布式数据流框架中的连接优化。Blanas 等人 [3] 表明，在将大表（如边）与小表（如顶点）连接时，广播连接与半连接优于标准 MapReduce 式混洗连接。Afrati 等人 [2] 的工作与本文密切相关，它研究 MapReduce 框架中的多路连接优化：连接一个大关系和多个较小关系，并给出类似经典二维划分 [8] 的划分与复制策略。

但与本文工作不同，他们没有构造路由表，而是迫使系统把较小关系（如顶点）广播到较大关系（如边）的所有可能包含匹配元组的分区。此外，他们还对较大关系强制采用特定哈希划分，排除了使用用户定义图划分算法 [16, 38, 36] 的可能性。

## 7　讨论

GraphX 的工作触及数据管理系统与系统设计中的若干核心主题。

**物理数据独立性。** GraphX 允许同一份物理数据在不移动、不复制的情况下，同时被视为集合或图，因此用户可针对眼前任务自由选择最佳视图。我们证明，集合与图上的操作可以用同一物理表示和底层算子高效实现。实验结果表明，这一共同基底可以达到专用图系统的性能。

**将图计算表示为连接与分组。** GraphX 的设计揭示了分布式图计算与分布式连接优化之间的紧密联系。从数据流算子的视角看，图计算可以归约为连接与分组算子；它们分别对应 GAS 抽象中的分发与收集阶段。同样，图处理系统中的优化也可归约为索引、分布式连接位置选择、多播连接、部分物化和增量视图维护。

**窄腰。** 设计 GraphX 抽象时，我们希望在数据流算子之上构建一个薄扩展，以识别支持图计算所需的基本数据模型与核心操作。目标是形成可移植的框架，能够嵌入多种数据流系统。我们相信，包括大规模并行处理（MPP）数据库在内的其他数据流系统也可采用 GraphX 设计，高效支持广泛的图计算。

**分析流水线。** GraphX 使整个分析过程能够留在一个框架内，不再需要学习和维护多个系统（如图 11），也不必编写系统间交换数据的格式和管道。因此，在大型图上反复切片、变换和计算，以及在流水线不同阶段共享数据结构，都变得容易得多。图计算在性能与扩展性上的收益缩短了分析反馈环路，也令工作流程更加高效。

**图 11　图分析流水线。** 传统流水线常用不同系统完成 ETL、切片、计算和分析，需要同一数据的多个集合视图与图视图。

**采用情况。** GraphX 随 Apache Spark 开源项目 0.9.0 版公开发布。[^2] 此后，它在社区中引发了广泛兴趣，并已在多个场所投入生产。[^3] 尽管仍处早期阶段，GraphX 已获得大量开源贡献，贡献者提供了若干核心图功能。我们认为，这源于 GraphX 的广泛适用性，以及它建立在流行数据流框架之上的简单抽象。

[^2]: https://spark.apache.org
[^3]: 一个大规模商业应用案例见文献 [14]。

## 8　结论与未来工作

本文提出 GraphX：一种高效图处理系统，使 Spark 等分布式数据流框架可以自然地表达并高效执行迭代式图算法。我们识别出一种简单的“连接—映射—分组”数据流算子模式，它构成图并行计算的基础。受此观察启发，我们提出 GraphX 抽象：把图表示成水平划分的集合，把图计算表示成这些集合上的数据流算子。

GraphX 不仅支持现有图并行抽象与广泛的迭代式图算法，还允许组合图和集合，使用户可以采用最自然的视图，而无须担心数据移动或复制。

在图计算与数据流算子之间联系的指引下，我们把图处理系统的近期进展重新表述为一系列经典数据库优化：把顶点切分式图划分表述成水平划分的顶点与边集合，把活跃顶点追踪表述成增量视图维护，把顶点镜像表述成使用路由表的多播连接。

结果表明，对于图算法，GraphX 比基础数据流系统快一个数量级以上，并且能够达到或超过专用图处理系统的性能。此外，GraphX 还受益于现代数据流系统提供的低成本容错和透明恢复等功能。

我们认为，GraphX 的工作指向一项更广阔的研究议程：统一专用数据处理系统。主题建模、图处理、流处理与深度学习等专用系统的近期进展，揭示了许多新的系统优化和设计权衡。然而，只有将这些系统集成起来，才能充分发挥它们的潜力，例如把深度学习应用于社交网络中的文本与图像。

若能把这些系统纳入共同范式（如数据流算子），就可能揭示共同模式，并开启新的分析能力。
