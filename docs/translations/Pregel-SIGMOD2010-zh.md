# Pregel：大规模图处理系统

**Grzegorz Malewicz、Matthew H. Austern、Aart J. C. Bik、James C. Dehnert、Ilan Horn、Naty Leiser、Grzegorz Czajkowski**

Google, Inc.  
{malewicz,austern,ajcbik,dehnert,ilan,naty,gczaj}@google.com

## 摘要

许多实际计算问题都涉及大规模图，典型例子包括 Web 图和各类社交网络。这些图的规模——有时达到数十亿个顶点、数万亿条边——给高效处理带来了挑战。本文提出一种适合此类任务的计算模型。程序被表述为一系列迭代：在每次迭代中，顶点可以接收上一轮迭代发送的消息、向其他顶点发送消息、修改自身状态及其出边状态，或者改变图的拓扑结构。这种以顶点为中心（vertex-centric）的方法足够灵活，可以表达广泛的算法。

该模型旨在集群上实现高效、可扩展且具容错能力的计算；集群可由数千台商用计算机组成。模型内含的同步性使程序推理更加容易，而与分布式执行有关的细节则被隐藏在抽象 API 之后。由此得到的是一个既富有表达力又易于编程的大规模图处理框架。

## 1. 引言

互联网使 Web 图成为广受关注的分析与研究对象，Web 2.0 又进一步激发了人们对社交网络的兴趣。其他大型图——例如由交通路线、报纸文章相似性、疾病传播路径或已发表科研成果之间的引用关系所形成的图——也已经被研究和处理了数十年。常用算法包括最短路径计算、各种聚类算法，以及 PageRank 主题的多种变体。还有许多具有实际价值的图计算问题，例如最小割和连通分量。

高效处理大型图极具挑战性。图算法往往表现出较差的内存访问局部性、每个顶点上的工作量很小，并且执行过程中的并行度不断变化 [31, 39]。将计算分布到多台机器上会进一步加剧局部性问题，同时也提高计算期间机器发生故障的概率。尽管大型图无处不在且具有重要的商业价值，但据我们所知，此前还没有一种可扩展的通用系统，能够在大规模分布式环境中，针对任意图表示实现任意图算法。

实现一个处理大型图的算法，通常意味着在以下方案中作出选择：

1. 定制分布式基础设施。这通常需要投入大量实现工作，而且每遇到一种新算法或新的图表示，往往都必须重复这些工作。

2. 借助现有分布式计算平台，而这些平台通常并不适合图处理。例如，MapReduce [14] 非常适合多种大规模计算问题，也有时被用于大型图挖掘 [11, 30]，但这可能导致性能欠佳和易用性问题。基本数据处理模型已经得到扩展，以支持聚合 [41] 和类 SQL 查询 [40, 47]，然而图算法往往更适合消息传递模型，因此这些扩展通常并不理想。

3. 使用单机图算法库，例如 BGL [43]、LEDA [35]、NetworkX [25]、JDSL [20]、Stanford GraphBase [29] 或 FGL [16]，但这会限制可处理问题的规模。

4. 使用现有并行图系统。Parallel BGL [22] 和 CGMgraph [8] 程序库面向并行图算法，但未处理容错等对超大规模分布式系统至关重要的问题。

这些备选方案都无法满足我们的需求。为了解决大型图的分布式处理问题，我们构建了一个可扩展且具容错能力的平台，其 API 足够灵活，能够表达任意图算法。本文介绍由此产生的 Pregel 系统，并报告我们的使用经验。[^pregel-name]

Pregel 程序的高层组织方式受到 Valiant 的整体同步并行（Bulk Synchronous Parallel，BSP）模型 [45] 启发。Pregel 计算由一系列称为“超步”（superstep）的迭代组成。在一个超步中，框架从概念上并行地为每个顶点调用一个用户定义函数。该函数描述单个顶点 \(V\) 在单个超步 \(S\) 中的行为：它可以读取超步 \(S-1\) 中发送给 \(V\) 的消息，发送将在超步 \(S+1\) 被接收的消息，并修改 \(V\) 及其出边的状态。消息通常沿出边发送，但也可以发往任何标识符已知的顶点。

以顶点为中心的方法与 MapReduce 有相似之处：用户专注于局部操作，独立处理每个数据项，系统再组合这些操作，使计算能够作用于大型数据集。该模型在设计上适合分布式实现：它不提供任何机制来探知一个超步内部的执行顺序，而且所有通信都从超步 \(S\) 指向超步 \(S+1\)。这种同步性使实现算法时更容易推理程序语义，并保证 Pregel 程序从根本上避免异步系统中常见的死锁和数据竞争。

原则上，只要拥有足够的并行余量，Pregel 程序的性能就应当能够与异步系统竞争 [28, 34]。典型图计算中的顶点数远多于机器数，因此应当可以均衡机器负载，使超步之间的同步不会引入过多延迟。

本文其余部分的组织如下：第 2 节介绍计算模型；第 3 节介绍该模型在 C++ API 中的表达；第 4 节讨论实现问题，包括性能和容错；第 5 节给出该模型在若干图算法问题上的应用；第 6 节展示性能结果；最后讨论相关工作与未来方向。

## 2. 计算模型

Pregel 计算的输入是一个有向图，其中每个顶点都由字符串形式的顶点标识符唯一标识。每个顶点关联一个可修改的、由用户定义的值。有向边归属于其源顶点，每条边由一个可修改的用户定义值和一个目标顶点标识符构成。

典型的 Pregel 计算首先进行输入并初始化图，随后执行一系列由全局同步点分隔的超步，直至算法终止，最后产生输出。在每个超步中，各顶点并行计算，并执行同一个用于表达特定算法逻辑的用户定义函数。顶点可以修改自身状态或出边状态，接收上一超步发给它的消息，发送将在下一超步被其他顶点接收的消息，甚至改变图的拓扑结构。在该模型中，边不是一等公民（first-class citizen），没有与之关联的独立计算。

算法通过所有顶点投票停机而终止。在超步 0 中，每个顶点都处于活跃状态；在任一给定超步中，所有活跃顶点都参与计算。顶点通过投票停机来停用自身，这表示除非受到外部触发，否则该顶点已无更多工作要做；后续超步中，Pregel 框架不会再执行该顶点，除非它收到消息。顶点因消息而重新激活后，仍须再次明确停用自身。当所有顶点同时处于非活跃状态，且没有正在传输的消息时，整个算法终止。

**图 1：顶点状态机**

```text
活跃 ──投票停机──> 非活跃
活跃 <──收到消息── 非活跃
```

Pregel 程序的输出是由顶点明确输出的一组值。输出通常是与输入同构的有向图，但这不是系统的必要性质，因为计算过程中可以添加或删除顶点与边。例如，聚类算法可以从大型图中选出一小组彼此不连接的顶点；图挖掘算法也可以只输出从图中挖掘出的聚合统计量。

图 2 用一个简单示例说明这些概念：给定一个每个顶点都含有数值的强连通图，将最大值传播至每个顶点。在每个超步中，只要一个顶点从消息中获知了更大的值，它就将这个值发送给所有邻居。当某个超步中不再有任何顶点发生变化时，算法终止。

**图 2：最大值示例。虚线表示消息，阴影顶点表示已经投票停机。**

```text
超步 0：3  6  2  1
超步 1：6  6  2  6
超步 2：6  6  6  6
超步 3：6  6  6  6
```

我们选择了纯消息传递模型，省略远程读取和其他模拟共享内存的方式，原因有二。第一，消息传递具有足够的表达能力，不需要远程读取；我们尚未发现任何消息传递无法胜任的图算法。第二，这一选择更有利于性能。在集群环境中，从远程机器读取一个值会产生难以隐藏的高延迟。消息传递模型允许我们以异步批量投递消息的方式摊销延迟。

图算法也可以写成一系列串联的 MapReduce 调用 [11, 30]。我们出于易用性和性能考虑选择了不同的模型。Pregel 将顶点和边保留在执行计算的机器上，仅利用网络传输消息；而 MapReduce 本质上是函数式的，因此用串联的 MapReduce 表达图算法时，必须将图的完整状态从一个阶段传递到下一个阶段，通常会产生多得多的通信量以及相应的序列化开销。此外，串联 MapReduce 各步骤之间的协调也会增加编程复杂度，而 Pregel 对超步的迭代避免了这一问题。

## 3. C++ API

本节介绍 Pregel C++ API 中最重要的方面，省略较为机械化的细节。

编写 Pregel 程序需要继承预定义的 `Vertex` 类（见图 3）。其模板参数定义三种值类型，分别与顶点、边和消息关联。每个顶点都有一个指定类型的关联值。这种一致性看似限制较强，但用户可以借助协议缓冲区（Protocol Buffers）[42] 等灵活类型来应对；边和消息类型亦然。

用户需要重写虚方法 `Compute()`，框架会在每个超步中对每个活跃顶点执行该方法。`Vertex` 的预定义方法允许 `Compute()` 查询当前顶点及其边的信息，并向其他顶点发送消息。`Compute()` 可以通过 `GetValue()` 检查顶点关联值，也可以通过 `MutableValue()` 修改它；还可以利用出边迭代器提供的方法检查和修改出边的值。这些状态更新立即可见。由于其可见范围仅限于被修改的顶点，并发访问不同顶点的值时不会发生数据竞争。

与顶点及其边关联的值，是跨超步持续存在的唯一逐顶点状态。将框架管理的图状态限制为每个顶点或每条边一个值，可以简化主计算循环、图的分布以及故障恢复。

```cpp
template <class VertexValue, class EdgeValue, class MessageValue>
class Vertex {
 public:
  virtual void Compute(MessageIterator* msgs) = 0;

  const string& vertex_id() const;
  int64 superstep() const;
  const VertexValue& GetValue();
  VertexValue* MutableValue();
  OutEdgeIterator GetOutEdgeIterator();

  void SendMessageTo(const string& dest_vertex,
                     const MessageValue& message);
  void VoteToHalt();
};
```

**图 3：`Vertex` API 的基础。**

### 3.1 消息传递

顶点通过发送消息直接通信，每条消息由消息值和目标顶点名称组成。消息值类型由用户作为 `Vertex` 类的模板参数指定。一个顶点可以在一个超步内发送任意数量的消息。超步 \(S\) 中发给顶点 \(V\) 的所有消息，在超步 \(S+1\) 调用 \(V\) 的 `Compute()` 方法时均可通过迭代器访问。迭代器中的消息顺序没有保证，但系统保证消息一定会送达且不会重复。

一种常见用法是顶点 \(V\) 遍历其出边，并向每条边的目标顶点发送消息，如图 4 的 PageRank 算法所示。然而，`dest_vertex` 不必是 \(V\) 的邻居。顶点可以从先前收到的消息中获知非邻居的标识符，也可以隐式地知道顶点标识符。例如，图可能是一个团，其顶点标识符 \(V_1\) 至 \(V_n\) 为众所周知的名称；在这种情况下，图中甚至可能无需显式保存边。

若消息的目标顶点不存在，系统会执行用户定义的处理器。例如，处理器可以创建缺失的顶点，或从源顶点删除悬空边。

### 3.2 组合器

发送消息会产生一定开销，尤其是在目标顶点位于另一台机器上时。在某些情况下，借助用户提供的信息可以降低这一开销。假设 `Compute()` 接收整数消息，并且只有总和有意义，单个值并不重要，那么系统就可以将发往顶点 \(V\) 的多条消息合并为一条包含其总和的消息，从而减少需要传输和缓冲的消息数量。

系统默认不启用组合器（combiner），因为不存在一种机械方法，能够找到既有用又与用户 `Compute()` 方法语义一致的组合函数。要启用这一优化，用户需要继承 `Combiner` 类并重写虚方法 `Combine()`。系统不保证哪些消息会被组合、是否会进行组合、消息如何分组或以何种顺序组合，因此组合器只应当用于满足交换律和结合律的运算。对于单源最短路径（第 5.2 节）等算法，我们观察到组合器能够将消息流量降低到原来的四分之一以下。

### 3.3 聚合器

Pregel 聚合器（aggregator）是一种用于全局通信、监控和数据处理的机制。每个顶点都可以在超步 \(S\) 向聚合器提供一个值，系统使用归约算子组合这些值，并在超步 \(S+1\) 将所得结果提供给所有顶点。Pregel 预定义了多种聚合器，例如针对不同整数或字符串类型的最小值、最大值和求和运算。

聚合器可以用于统计。例如，对每个顶点的出度应用求和聚合器，即可得到图中的边总数；更复杂的归约算子则可以生成某项统计量的直方图。

聚合器也可用于全局协调。例如，在若干超步中执行 `Compute()` 的一个分支，直至逻辑与聚合器判定所有顶点均满足某项条件，此后再执行另一个分支直至终止。对顶点 ID 应用最小值或最大值聚合器，可以选出一个在算法中承担特殊角色的顶点。

要定义新的聚合器，用户需要继承预定义的 `Aggregator` 类，指定如何从第一个输入值初始化聚合值，以及如何将多个部分聚合值归约为一个值。聚合运算应当满足交换律和结合律。默认情况下，聚合器只归约单个超步中的输入值，但也可以定义一种“粘性”聚合器（sticky aggregator），使其使用所有超步中的输入值。例如，这可用于维护全局边数，并且仅在添加或删除边时调整计数。

聚合器还支持更高级的用法。例如，可以用聚合器为 \(\Delta\)-stepping 最短路径算法 [37] 实现分布式优先队列。每个顶点依据其暂定距离被分配到一个优先级桶中。在一个超步中，各顶点将自己的桶索引提交给最小值聚合器；最小值在下一超步广播给所有工作进程，随后最低索引桶中的顶点执行边松弛。

### 3.4 拓扑变更

有些图算法需要改变图的拓扑结构。例如，聚类算法可能以单个顶点替换每个簇，最小生成树算法可能删除除树边以外的所有边。用户的 `Compute()` 函数不仅可以发送消息，也可以发出添加或删除顶点、边的请求。

多个顶点可能在同一超步中发出相互冲突的请求，例如以不同初始值两次请求添加顶点 \(V\)。我们采用偏序和处理器两种机制来保证确定性。

与消息一样，拓扑变更在请求发出后的下一超步生效。在该超步中，系统先执行删除操作：先删除边，再删除顶点，因为删除顶点会隐式删除其所有出边。添加操作在删除操作之后执行：先添加顶点，再添加边；所有变更都先于 `Compute()` 调用。这一偏序可以使多数冲突得到确定性结果。

其余冲突由用户定义的处理器解决。如果同一超步内有多个请求创建同一个顶点，系统默认任意选择其中一个；有特殊需求的用户则可以在 `Vertex` 子类中定义适当的处理器方法，指定更好的冲突解决策略。相同的处理器机制也用于解决多个顶点删除请求，以及多个边添加或删除请求造成的冲突。

我们将冲突解决委托给处理器，以保持 `Compute()` 代码简单。这样做限制了处理器与 `Compute()` 之间的交互，但在实践中并未造成问题。

我们的协调机制是惰性的：全局变更在真正应用时才需要协调。这一设计选择有利于流式处理，其直觉是，涉及修改顶点 \(V\) 的冲突由 \(V\) 自身处理。

Pregel 还支持纯局部变更，即顶点添加或删除自身的出边，或者删除自身。局部变更不会引入冲突，使其立即生效可以采用更易理解的顺序程序语义，从而简化分布式编程。

### 3.5 输入与输出

图可以采用多种文件格式，例如文本文件、关系数据库中的一组顶点，或 Bigtable [9] 中的若干行。为了避免强制使用特定文件格式，Pregel 将“把输入文件解释为图”的任务与图计算任务解耦。同样，系统可以用任意格式生成输出，并采用最适合特定应用的形式存储。Pregel 程序库为多种常见文件格式提供读取器和写入器；有特殊需求的用户也可以继承抽象基类 `Reader` 和 `Writer`，编写自己的实现。

## 4. 实现

Pregel 面向 Google 集群架构设计，该架构详见文献 [3]。每个集群由数千台商用 PC 组成，并按机架组织，机架内部具有较高带宽。各集群彼此互联，但在地理位置上分散。

我们的应用通常运行在集群管理系统上。该系统通过调度作业来优化资源分配，有时会终止实例或将实例迁移到其他机器。系统包含名称服务，因此可以使用逻辑名称引用实例，而不依赖其当前绑定的物理机器。持久数据以文件形式存储在分布式存储系统 GFS [19] 或 Bigtable [9] 中，缓冲消息等临时数据则存储在本地磁盘上。

### 4.1 基本架构

Pregel 程序库将图划分为若干分区，每个分区包含一组顶点及这些顶点的全部出边。顶点被分配到哪个分区仅取决于其顶点 ID。这意味着，即使一个顶点由另一台机器负责，甚至该顶点尚不存在，也可以判断它属于哪个分区。

默认分区函数为 \(\operatorname{hash}(ID) \bmod N\)，其中 \(N\) 为分区数；用户也可以替换该函数。将顶点分配给工作机器，是 Pregel 中分布细节并非完全透明的主要环节。有些应用使用默认分配方式即可获得良好效果，另一些应用则适合定义自定义分配函数，以便更好地利用图中固有的局部性。例如，Web 图通常采用的一种启发式方法，是将表示同一站点页面的顶点放置在一起。

在没有故障的情况下，Pregel 程序按以下阶段执行：

1. 用户程序的许多副本开始在集群机器上运行，其中一个副本担任主进程（master）。主进程不负责图的任何部分，而是协调工作进程（worker）的活动。工作进程通过集群管理系统的名称服务发现主进程的位置，并向主进程发送注册消息。

2. 主进程确定图的分区数，并为每台工作机器分配一个或多个分区。分区数可以由用户控制。每个工作进程拥有多个分区，可以在分区之间实现并行和更好的负载均衡，通常能够改善性能。每个工作进程负责维护其所辖图区域的状态、在其中的顶点上执行用户的 `Compute()` 方法，并管理与其他工作进程之间的消息。每个工作进程都会获得所有工作进程的完整分配信息。

3. 主进程将用户输入的一部分分配给每个工作进程。输入被视为一组记录，每条记录可以包含任意数量的顶点和边。输入的划分与图本身的分区相互独立，通常依据文件边界进行。如果工作进程加载的顶点属于其负责的图区域，它会立即更新相应的数据结构（第 4.3 节）；否则，它会将消息加入发往负责该顶点的远程对等工作进程的队列。输入加载完成后，所有顶点均被标记为活跃。

4. 主进程指示每个工作进程执行一个超步。工作进程遍历其活跃顶点，每个分区使用一个线程；它为每个活跃顶点调用 `Compute()`，并向其交付上一超步发送的消息。消息以异步方式发送，以便重叠计算与通信并进行批处理，但都会在该超步结束前送达。工作进程完成后向主进程作出响应，告知主进程下一超步中将有多少个活跃顶点。只要仍有顶点活跃或仍有消息在传输，就会重复这一步骤。

5. 计算停止后，主进程可以指示每个工作进程保存其负责的图区域。

### 4.2 容错

Pregel 通过检查点（checkpointing）实现容错。在一个超步开始时，主进程指示工作进程将其分区状态保存到持久存储中，包括顶点值、边值和传入消息；主进程则单独保存聚合器的值。

工作进程故障通过主进程定期发送的“ping”消息检测。如果工作进程在指定时间间隔后仍未收到 ping 消息，该工作进程就会终止。若主进程没有收到某个工作进程的响应，则将该工作进程标记为发生故障。

一个或多个工作进程发生故障时，分配给它们的分区当前状态会丢失。主进程将图分区重新分配给当前可用的工作进程，随后所有工作进程从最近可用的检查点重新加载其分区状态。该检查点位于某个超步 \(S\) 的开头，而 \(S\) 可能比故障前任何分区已完成的最新超步 \(S'\) 早若干步，因此恢复过程需要重新执行缺失的超步。我们依据平均故障间隔时间模型 [13] 选择检查点频率，在检查点成本与预期恢复成本之间取得平衡。

我们正在开发局限恢复（confined recovery），以降低恢复成本和延迟。除了基本检查点之外，工作进程在图加载和各超步期间，还会记录其所辖分区发出的消息。这样，恢复就被限制在丢失的分区内：这些分区从检查点恢复，系统利用健康分区记录的消息，以及正在恢复的分区重新计算所得的消息，重新执行缺失的超步直至 \(S'\)。

这种方法只重新计算丢失的分区，因而节省恢复期间的计算资源；由于每个工作进程可能只需恢复较少分区，也能改善恢复延迟。保存发出消息会增加开销，但典型机器拥有足够的磁盘带宽，可以保证 I/O 不会成为瓶颈。

局限恢复要求用户算法具有确定性，以免将原执行保存的消息与恢复过程新产生的消息混用时造成不一致。随机算法可以根据超步和分区，以确定性方式设定伪随机数生成器的种子，从而转化为确定性算法。非确定性算法则可以禁用局限恢复，退回基本恢复机制。

### 4.3 工作进程实现

一台工作机器在内存中维护其负责的图状态。从概念上说，这可以看作从顶点 ID 到各顶点状态的映射。每个顶点的状态包括当前值、出边列表（每条边的目标顶点 ID 与当前边值）、传入消息队列，以及表示该顶点是否活跃的标志。

工作进程执行一个超步时，会遍历所有顶点并调用 `Compute()`，传入当前值、传入消息迭代器和出边迭代器。系统不提供对入边的访问，因为每条入边都属于其源顶点所拥有的列表，而该源顶点通常位于另一台机器上。

出于性能考虑，活跃顶点标志与传入消息队列分开存储。此外，顶点值与边值都只保存一个副本，而活跃顶点标志和传入消息队列各保存两个副本：一个用于当前超步，另一个用于下一超步。

工作进程在超步 \(S\) 处理顶点的同时，会由另一个线程接收来自同样正在执行该超步的其他工作进程的消息。由于顶点接收的是上一超步发送的消息（见第 2 节），用于超步 \(S\) 与 \(S+1\) 的消息必须分开保存。同理，某条发给顶点 \(V\) 的消息到达，意味着 \(V\) 在下一超步中会处于活跃状态，而不一定在当前超步中活跃。

当 `Compute()` 请求向另一个顶点发送消息时，工作进程首先判断目标顶点是由远程工作机器负责，还是与发送者归属同一工作进程。若目标在远程，则将消息缓冲起来，等待投递给目标工作进程。当缓冲区大小达到阈值时，系统会异步刷新其中最大的缓冲区，将每个缓冲区作为单个网络消息投递给目标工作进程。若目标在本地，则可以进行优化：直接将消息放入目标顶点的传入消息队列。

如果用户提供了组合器（第 3.2 节），那么在消息被加入传出消息队列以及被传入消息队列接收时，都会应用该组合器。后一次组合不会减少网络用量，但可以减少存储消息所需的空间。

### 4.4 主进程实现

主进程主要负责协调各工作进程的活动。每个工作进程注册时都会获分配一个唯一标识符。主进程维护所有当前已知仍存活的工作进程列表，其中包括工作进程的唯一标识符、寻址信息，以及分配给它的图区域。

主进程数据结构的大小与分区数成正比，而不是与顶点数或边数成正比，因此即使面对非常大的图，单个主进程也能够协调计算。

主进程的大多数操作——包括输入、输出、计算，以及保存检查点和从检查点恢复——都在屏障（barrier）处结束：主进程向操作开始时已知存活的每个工作进程发送同一请求，并等待每个工作进程响应。如果有任何工作进程发生故障，主进程就会进入第 4.2 节所述的恢复模式。如果屏障同步成功，主进程便进入下一阶段。例如，在计算屏障处，主进程会递增全局超步索引，然后进入下一超步。

主进程还维护关于计算进度和图状态的统计信息，例如图的总大小、出度分布直方图、活跃顶点数、近期超步的耗时与消息流量，以及所有用户定义聚合器的值。为了便于用户监控，主进程运行一个 HTTP 服务器来展示这些信息。

### 4.5 聚合器

聚合器（第 3.3 节）通过对用户提供的一组值应用聚合函数，计算出单个全局值。每个工作进程维护一组聚合器实例，以类型名称和实例名称标识。

当工作进程为图的任一分区执行一个超步时，它会将提交给某个聚合器实例的所有值组合为一个局部值，即在该分区内所有工作进程顶点上经过部分归约的聚合器值。超步结束时，各工作进程组成一棵树，将部分归约的聚合器继续归约为全局值，并交付给主进程。

我们采用树形归约，而不是通过工作进程链进行流水线式处理，以便在归约期间并行利用 CPU。主进程在下一超步开始时将全局值发送给所有工作进程。

## 5. 应用

本节介绍四个示例，它们是 Pregel 用户为解决实际问题而开发的算法的简化版本：PageRank、最短路径、二分图匹配和半聚类算法。

### 5.1 PageRank

图 4 给出了 PageRank 算法 [7] 的 Pregel 实现。`PageRankVertex` 类继承自 `Vertex`。其顶点值类型为 `double`，用于保存暂定 PageRank；消息类型也为 `double`，用于传递 PageRank 份额；边值类型为 `void`，因为边不保存信息。

我们假设图已经初始化，使超步 0 中每个顶点的值均为 `1 / NumVertices()`。在前 30 个超步中，每个顶点沿每条出边发送其暂定 PageRank 除以出边数所得的值。从超步 1 开始，每个顶点将消息携带的值累加到 `sum` 中，并将自身暂定 PageRank 设置为 `0.15 / NumVertices() + 0.85 × sum`。到达超步 30 后，不再发送消息，每个顶点都投票停机。在实践中，PageRank 算法通常会运行至收敛，并可使用聚合器检测收敛条件。

```cpp
class PageRankVertex : public Vertex<double, void, double> {
 public:
  virtual void Compute(MessageIterator* msgs) {
    if (superstep() >= 1) {
      double sum = 0;
      for (; !msgs->Done(); msgs->Next())
        sum += msgs->Value();
      *MutableValue() =
          0.15 / NumVertices() + 0.85 * sum;
    }
    if (superstep() < 30) {
      const int64 n = GetOutEdgeIterator().size();
      SendMessageToAllNeighbors(GetValue() / n);
    } else {
      VoteToHalt();
    }
  }
};
```

**图 4：在 Pregel 中实现的 PageRank。**

### 5.2 最短路径

最短路径是图论中最著名的问题之一，广泛见于多种应用 [10, 24]，并有若干重要变体。单源最短路径（single-source shortest paths，SSSP）问题要求找出单个源顶点到图中每个其他顶点的最短路径。\(s\)-\(t\) 最短路径问题要求找出给定顶点 \(s\) 与 \(t\) 之间的一条最短路径，它在驾车路线规划等领域具有显而易见的实际应用，也得到了广泛研究。

\(s\)-\(t\) 最短路径相对容易：在道路网等典型图中，求解过程只会访问很少一部分顶点。Lumsdaine 等人 [31] 的一个示例在 3,200 万个顶点中只访问了 8 万个。第三种变体是全点对最短路径，但其存储需求为 \(O(|V|^2)\)，对大型图并不实用。

为简洁起见，这里只讨论单源变体。它非常符合 Pregel 处理大型图的目标，同时能比 \(s\)-\(t\) 最短路径问题提供更有意义的扩展性数据。其实现见图 5。

在该算法中，我们假设每个顶点的关联值均被初始化为 `INF`，该常量大于图中从源顶点出发的任何可行距离。在每个超步中，每个顶点首先接收邻居以消息形式发送的、从源顶点出发的候选最短距离更新。若这些更新中的最小值小于顶点当前关联值，该顶点便更新自身的值，并向邻居发出候选更新：将每条出边的权重加到新发现的最短距离上。

在第一个超步中，只有源顶点会将其值从 `INF` 更新为 0，并向直接邻居发送更新。随后，这些邻居又更新自身的值并发送消息，于是更新波前会在图中传播。当不再有更新发生时，算法终止；此后，每个顶点的关联值表示从源顶点到该顶点的最短距离，`INF` 则表示该顶点完全不可达。如果所有边的权重均非负，算法一定会终止。

```cpp
class ShortestPathVertex : public Vertex<int, int, int> {
  void Compute(MessageIterator* msgs) {
    int mindist = IsSource(vertex_id()) ? 0 : INF;
    for (; !msgs->Done(); msgs->Next())
      mindist = min(mindist, msgs->Value());
    if (mindist < GetValue()) {
      *MutableValue() = mindist;
      OutEdgeIterator iter = GetOutEdgeIterator();
      for (; !iter.Done(); iter.Next())
        SendMessageTo(iter.Target(),
                      mindist + iter.GetValue());
    }
    VoteToHalt();
  }
};
```

**图 5：单源最短路径。**

该算法中的消息由候选的更短距离组成。由于接收顶点最终只关心最小值，因此适合利用组合器（第 3.2 节）进行优化。图 6 所示的组合器可大幅减少工作进程之间传输的数据量，也能减少执行下一超步之前需要缓冲的数据量。

```cpp
class MinIntCombiner : public Combiner {
  virtual void Combine(MessageIterator* msgs) {
    int mindist = INF;
    for (; !msgs->Done(); msgs->Next())
      mindist = min(mindist, msgs->Value());
    Output("combined_source", mindist);
  }
};
```

**图 6：取消息值最小值的组合器。**

图 5 的代码只计算距离，但将其修改为同时计算最短路径树也十分直接。该算法执行的比较次数可能远多于 Dijkstra 或 Bellman–Ford [5, 15, 17, 24] 等顺序算法，但它能够以任何单机实现都不可行的规模求解最短路径问题。

也存在更高级的并行算法，例如 Thorup 算法 [44] 或 \(\Delta\)-stepping 方法 [37]，它们已经被用作专用并行最短路径实现的基础 [12, 32]。这些高级算法同样可以在 Pregel 框架中表达。不过，图 5 的实现非常简单，而且已经能够取得可接受的性能（见第 6 节），这对无法投入大量精力进行调优或定制的用户可能颇具吸引力。

### 5.3 二分图匹配

二分图匹配算法的输入由两个互不相交的顶点集组成，边只存在于两个集合之间；输出是一个边子集，其中任何两条边都不共享端点。极大匹配（maximal matching）是指无法在不共享端点的前提下再添加任何边的匹配。

我们实现了一个随机化极大匹配算法 [1] 和一个最大权二分图匹配算法 [4]，这里介绍前者。

在该算法的 Pregel 实现中，顶点值是由两个值组成的元组：一个标志指明顶点位于哪个集合（\(L\) 或 \(R\)），另一个值是在匹配确定后记录其匹配顶点的名称。边值类型为 `void`，因为边不携带信息；消息类型为布尔值。

算法以四个阶段为一个周期运行，阶段索引就是超步索引模 4，并采用三次握手：

- 在一个周期的阶段 0 中，每个尚未匹配的左侧顶点向所有邻居发送匹配请求，随后无条件投票停机。如果它没有发送消息（因为已经匹配或没有出边），或者消息的所有接收者都已经匹配，那么它将永远不会再被激活；否则，它会在两个超步之后收到响应并重新激活。

- 在阶段 1 中，每个尚未匹配的右侧顶点从收到的消息中随机选择一个，向其发送批准请求的消息，并向其他请求者发送拒绝消息，随后无条件投票停机。

- 在阶段 2 中，每个尚未匹配的左侧顶点从收到的批准中选择一个，并发送接受消息。已经匹配的左侧顶点不会执行这一阶段，因为它们不会在阶段 0 发送消息。

- 最后，在阶段 3 中，一个尚未匹配的右侧顶点至多收到一条接受消息。它记录匹配节点并无条件投票停机，因为此后已无更多工作。

### 5.4 半聚类

Pregel 已被用于多种聚类算法。其中一种称为半聚类（semi-clustering），源于社交图。社交图中的顶点通常表示人，边则表示人与人之间的联系。边可能来自显式操作，例如在社交网站中添加好友；也可能从人的行为中推断出来，例如电子邮件往来或共同发表论文。边还可以具有权重，以表示互动的频率或强度。

社交图中的半簇（semi-cluster）是一组彼此频繁互动、而与外部互动较少的人。半聚类与普通聚类的区别在于，一个顶点可以属于多个半簇。

本节介绍一种并行贪心半聚类算法。其输入是一个带权无向图——在 Pregel 中，每条边以两个方向各构造一次来表示无向边；输出至多包含 \(C_{\max}\) 个半簇，每个半簇至多包含 \(V_{\max}\) 个顶点，其中 \(C_{\max}\) 和 \(V_{\max}\) 是用户指定的参数。

半簇 \(c\) 的分数定义为：

\[
S_c =
\frac{I_c - f_B B_c}
     {V_c(V_c-1)/2},
\tag{1}
\]

其中，\(I_c\) 是所有内部边的权重之和，\(B_c\) 是所有边界边的权重之和，即连接半簇内顶点与簇外顶点的边；\(V_c\) 是半簇中的顶点数；\(f_B\) 是用户指定的边界边评分因子，通常介于 0 与 1 之间。该分数以大小为 \(V_c\) 的团的边数进行归一化，从而避免大型簇获得人为偏高的分数。

每个顶点 \(V\) 维护一个至多包含 \(C_{\max}\) 个半簇的列表，并按分数排序。在超步 0 中，\(V\) 将自身作为一个大小为 1、分数为 1 的半簇加入该列表，并将其发布给所有邻居。在后续超步中：

- 顶点 \(V\) 遍历上一超步发送给它的半簇 \(c_1,\ldots,c_k\)。如果半簇 \(c\) 尚未包含 \(V\)，且 \(V_c < V_{\max}\)，则将 \(V\) 加入 \(c\)，形成 \(c'\)。

- 将 \(c_1,\ldots,c_k,c'_1,\ldots,c'_k\) 按分数排序，并将其中最优者发送给 \(V\) 的邻居。

- 顶点 \(V\) 使用 \(c_1,\ldots,c_k,c'_1,\ldots,c'_k\) 中包含 \(V\) 的半簇更新自身的半簇列表。

当半簇不再变化时，算法终止；为了改善性能，也可以在超步数达到用户指定的上限时终止。此时，可以将每个顶点的最优半簇候选列表聚合成全局最优半簇列表。

## 6. 实验

我们在一个由 300 台多核商用 PC 组成的集群上，对第 5.2 节的单源最短路径（SSSP）实现进行了多项实验。我们报告两类图上的运行时间：一类是二叉树，用于研究扩展性质；另一类是对数正态随机图，用于研究更贴近现实场景的性能。实验使用多种图规模，并将所有边的权重隐式设为 1。

测量结果不包括初始化集群、在内存中生成测试图及验证结果的时间。由于所有实验都能在相对较短的时间内完成，发生故障的概率较低，因此禁用了检查点。

为了说明 Pregel 如何随工作任务数量扩展，图 7 展示了包含 10 亿个顶点、因而包含 10 亿减 1 条边的二叉树上的最短路径运行时间，其中 Pregel 工作进程数从 50 增加到 800。工作进程数增加 16 倍后，运行时间从 174 秒降至 17.3 秒，约获得 10 倍加速。

**图 7：SSSP——含 10 亿个顶点的二叉树；改变调度到 300 台多核机器上的工作任务数。**

为了说明 Pregel 如何随图规模扩展，图 8 展示了从 10 亿到 500 亿个顶点的不同规模二叉树上的最短路径运行时间。这里固定使用 800 个工作任务，并调度到 300 台多核机器上。运行时间从 17.3 秒增加到 702 秒，这表明，对于平均出度较低的图，运行时间随图规模线性增长。

**图 8：SSSP——二叉树；在 300 台多核机器上调度 800 个工作任务，并改变图规模。**

前述实验能够说明 Pregel 随工作进程数和图规模的扩展情况，但二叉树显然不能代表实践中遇到的图。因此，我们还对出度服从对数正态分布的随机图进行了实验：

\[
p(d) =
\frac{1}{\sqrt{2\pi}\sigma d}
e^{-(\ln d-\mu)^2/(2\sigma^2)},
\tag{2}
\]

其中 \(\mu=4\)、\(\sigma=1.3\)，平均出度为 127.1。这种分布类似许多现实世界的大型图，例如 Web 图或社交网络：大多数顶点的度相对较小，但也有一些异常值大得多，可达到 10 万甚至更高。

图 9 展示了此类图上的最短路径运行时间。图规模从 1,000 万个顶点变化到 10 亿个顶点，因而最大图包含超过 1,271 亿条边；同样使用调度到 300 台多核机器上的 800 个工作任务。对最大图运行最短路径算法只花费了略多于 10 分钟。

**图 9：SSSP——平均出度为 127.1 的对数正态随机图（因此最大图包含超过 1,271 亿条边）；在 300 台多核机器上调度 800 个工作任务，并改变图规模。**

在所有实验中，图都使用基于随机哈希的默认分区函数划分给各工作进程；如果使用能够感知拓扑的分区函数，性能会更好。此外，实验采用的是朴素并行最短路径算法；使用更高级的算法同样能够取得更好的性能。

因此，本节实验结果不应被理解为 Pregel 求解最短路径问题所能达到的最佳运行时间。相反，这些结果旨在说明，只需投入相对较少的编码工作，就能够获得令人满意的性能。

事实上，我们在含 10 亿个顶点和 10 亿条边的图上所得结果，与下一节提及的 Parallel BGL \(\Delta\)-stepping 结果 [31] 相当；后者在由 112 个处理器组成的集群上处理一个含 2.56 亿个顶点和 10 亿条边的图。而当规模超过这一水平时，Pregel 的扩展性更好。

## 7. 相关工作

Pregel 是一个分布式编程框架，重点在于为图算法编程提供自然的 API，同时对用户透明地管理分布式执行细节，包括消息传递和容错。其概念与 MapReduce [14] 相似，但提供自然的图 API，并对图上的迭代计算给予高效得多的支持。

以图为中心也使 Pregel 区别于其他隐藏分布细节的框架，例如 Sawzall [41]、Pig Latin [40] 和 Dryad [27, 47]。Pregel 的另一项差异在于，它实现了有状态模型：长生命周期的进程持续计算、通信并修改局部状态；而在数据流模型中，每个进程只依据输入数据计算，再产生供其他进程输入的输出数据。

Pregel 受到整体同步并行模型 [45] 启发，从中采用了以同步超步组织计算和通信的模型。BSP 有多种通用程序库实现，例如 Oxford BSP Library [38]、Green BSP Library [21]、BSPlib [26] 和 Paderborn University BSP Library [6]。这些实现所提供的通信原语各不相同，对可靠性（机器故障）、负载均衡和同步等分布式问题的处理方式也不同。

据我们所知，此前尚未在数十台以上的机器上评估 BSP 实现的可扩展性和容错能力，而且这些实现都不提供图专用 API。

与 Pregel 最接近的是 Parallel Boost Graph Library 和 CGMgraph。Parallel BGL [22, 23] 定义了若干用于描述分布式图的关键泛型概念，提供基于 MPI [18] 的实现，并基于这些概念实现多种算法。它力求与顺序版 BGL [43] 保持兼容，以方便移植算法。

Parallel BGL 使用属性映射保存图中与顶点和边关联的信息，并使用幽灵单元（ghost cell）保存与远程组件关联的值。当算法需要引用大量远程组件时，这种做法可能导致扩展性问题。Pregel 使用显式消息来获取远程信息，不会在本地复制远程值。

最关键的区别在于，Pregel 提供容错能力，可以应对计算期间发生的故障，从而能够在故障常见的超大型集群环境中运行；故障可能来自硬件失效，也可能来自作业被更高优先级任务抢占。

CGMgraph [8] 在概念上也相似，它使用基于 MPI 的粗粒度多计算机（Coarse Grained Multicomputer，CGM）模型，提供多种并行图算法。其底层分布机制对用户暴露得更多，而且重点是提供算法实现，而不是提供可供用户实现算法的基础设施。CGMgraph 使用面向对象的编程风格，这与 Parallel BGL 和 Pregel 的泛型编程风格不同，并会付出一定性能代价。

除 Pregel 和 Parallel BGL 外，鲜有系统报告十亿级顶点图上的实验结果。规模最大的既有报告来自 \(s\)-\(t\) 最短路径的定制实现，而非通用框架。

Yoo 等人 [46] 报告了 BlueGene/L 上的广度优先搜索（即 \(s\)-\(t\) 最短路径）实现。该系统使用 32,768 个 PowerPC 处理器和高性能环面网络，在含 32 亿个顶点、320 亿条边且服从泊松分布的随机图上取得了 1.5 秒的运行时间。

Bader 和 Madduri [2] 报告了 Cray MTA-2 上类似问题的实现。在一个由 10 个节点组成的高度多线程系统上，对含 1.34 亿个顶点和 8.05 亿条边的无标度 R-MAT 随机图，运行时间为 0.43 秒。

Lumsdaine 等人 [31] 将由 200 个 x86-64 Opteron 处理器组成的集群上的 Parallel BGL 结果与 BlueGene/L 实现进行了比较。在含 40 亿个顶点和 200 亿条边的 Erdős–Rényi 随机图上，他们取得了 0.43 秒的运行时间。他们将较好性能归因于幽灵单元，同时观察到处理器数超过 32 后，其实现性能开始下降。

对于含 2.56 亿个顶点、统一出度为 4 的 Erdős–Rényi 随机图，采用 \(\Delta\)-stepping 算法的单源最短路径结果分别见于 Cray MTA-2（40 个处理器，2.37 秒，[32]）和 Opteron 上的 Parallel BGL（112 个处理器，35 秒，[31]）。后一个时间与我们的二叉树实验相近：使用 400 个工作进程处理含 10 亿个节点和边的图。

据我们所知，尚无其他工作报告过与我们的对数正态图同等规模——10 亿个顶点、1,271 亿条边——的 SSSP 结果。

另一条研究路线是使用外部磁盘存储器，在单机上处理超大规模问题，例如文献 [33, 36]。但是，对含 10 亿个顶点的图，这些实现需要运行数小时。

## 8. 结论与未来工作

本文的贡献在于提出了一种适用于大规模图计算的模型，并介绍了其达到生产质量、可扩展且具容错能力的实现。根据用户反馈，我们认为已经成功地使该模型兼具实用性和易用性。已有数十个 Pregel 应用完成部署，还有更多应用正在设计、实现和调优。

用户报告称，一旦转向“像顶点一样思考”（think like a vertex）的编程方式，Pregel API 就显得直观、灵活且易于使用。这并不令人意外，因为我们从一开始就与早期使用者合作，由他们参与影响 API 的设计。例如，聚合器正是为消除用户在早期 Pregel 模型中发现的限制而加入的。

Pregel 中其他由用户经验推动的易用性功能包括：一组详细展示 Pregel 程序进度的状态页面、一个单元测试框架，以及有助于快速原型开发和调试的单机模式。

对于含数十亿个顶点的图，Pregel 的性能、可扩展性和容错能力已经令人满意。我们正在研究扩展到更大图的技术，例如放宽模型的同步性，以免较快的工作进程频繁在超步间屏障处等待。

目前，完整计算状态驻留在 RAM 中。我们已经会将部分数据溢写到本地磁盘，未来还将继续沿这一方向发展，使系统在无法获得数 TB 主存时也能够处理大型图。

如何将顶点分配给机器以尽量减少机器间通信，是一项挑战。如果输入图的拓扑与消息流量相符，依据拓扑进行图分区可能已经足够，但二者也可能不一致。我们希望设计动态重新分区机制。

Pregel 面向稀疏图设计，其中的通信主要沿边发生；我们预计这一重点不会改变。尽管系统已经谨慎地支持高扇出和高扇入流量，但如果大多数顶点持续向大多数其他顶点发送消息，性能仍会下降。不过，现实中的稠密图十分少见，在稀疏图上产生稠密通信的算法也同样少见。

其中一些算法可以转化为对 Pregel 更友好的变体，例如利用组合器、聚合器或拓扑变更。当然，这类计算对任何高度分布式的系统而言都很困难。

一个实际问题是，Pregel 正逐渐成为用户群体的生产基础设施。我们已不能再不考虑兼容性就随意修改 API。不过，我们相信，所设计的编程接口足够抽象和灵活，能够适应底层系统的进一步演进。
