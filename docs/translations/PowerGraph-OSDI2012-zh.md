## 摘要

大规模图结构计算是从定向广告到自然语言处理等任务的核心，由此催生了 Pregel、GraphLab 等多种图并行抽象。然而，现实世界中常见的自然图具有高度偏斜的幂律度分布，这对上述抽象所依赖的假设构成挑战，并限制了其性能与可扩展性。本文首先结合现有图并行抽象，刻画自然图计算所面临的挑战；随后提出 PowerGraph 抽象，利用图程序的内部结构解决这些问题。借助 PowerGraph 抽象，我们进一步提出一种新的分布式图放置与表示方法，以充分利用幂律图的结构。本文通过细致分析和实验评估，将 PowerGraph 与两种流行的图并行系统进行比较。最后，我们介绍 PowerGraph 的三种不同实现策略，讨论各自的相对优势，并在大规模真实问题上开展实证评估，结果表明其性能可获得数量级提升。

## 1 引言

机器学习与数据挖掘（MLDM）对大规模图结构数据的推理需求不断增长，形成了一项关键挑战。随着数据集规模扩大，统计理论表明，我们应采用更丰富的模型来消除简单模型带来的非期望偏差，并从数据中提取更强的信号。与此同时，更丰富模型的计算与存储复杂度，加之数据集的迅速增长，已经突破单机计算的极限。

由此产生的需求推动了 Pregel [30]、GraphLab [29] 等新型图并行抽象的发展。它们把计算编码为并行运行的顶点程序，并使程序沿图中的边进行交互。图并行抽象依赖两个条件：每个顶点的邻域较小，以最大化并行度；划分足够有效，以最小化通信。然而，社交网络和 Web 等现实世界现象所形成的图通常具有幂律度分布，这意味着少数顶点会连接图中很大一部分内容。此外，幂律图难以划分 [1, 28]，也难以在分布式环境中表示。

为应对幂律图计算的挑战，我们提出 PowerGraph 抽象。它利用顶点程序的结构，显式地按边而非按顶点分解计算。因此，PowerGraph 能够暴露出显著更多的并行性，降低网络通信和存储成本，并为分布式图放置提供一种高效的新方法。本文描述 PowerGraph 分布式实现的设计，并使用真实应用在大规模 EC2 部署上加以评估。具体而言，本文的主要贡献如下：

1. 分析幂律图在分布式图计算中的挑战，以及现有图并行抽象的局限（第 2、3 节）。
2. 提出 PowerGraph 抽象（第 4 节），对单个顶点程序进行分解。
3. 提出增量缓存过程，使计算状态能够动态维护（第 4.2 节）。
4. 提出一种适用于分布式环境中幂律图的快速数据布局方法（第 5 节）。
5. 从理论上刻画网络与存储开销（定理 5.2、5.3）。
6. 给出 PowerGraph 抽象的高性能开源实现（第 7 节）。
7. 在大规模 EC2 部署上使用真实 MLDM 应用，对 PowerGraph 的三种实现进行全面评估（第 6、7 节）。

## 2 图并行抽象

图并行抽象由稀疏图 \(G=\{V,E\}\) 和顶点程序 \(Q\) 组成。程序在每个顶点 \(v\in V\) 上并行执行，并可与相邻实例 \(Q(u)\) 交互，其中 \((u,v)\in E\)；交互方式可以是 GraphLab 中的共享状态，也可以是 Pregel 中的消息。与更通用的消息传递模型不同，图并行抽象把顶点程序间的交互约束在图结构上，从而能够优化数据布局与通信。本文重点讨论 Pregel 和 GraphLab，因为它们足以代表现有图并行抽象。

### 2.1 Pregel

Pregel [30] 是一种批同步消息传递抽象，所有顶点程序在一系列超步（super-step）中同时运行。在一个超步内，每个程序实例 \(Q(v)\) 接收上一超步的全部消息，并向其邻居发送供下一超步使用的消息。超步之间设有屏障，以确保所有程序实例完成对上一超步消息的处理后，才进入下一超步。当不存在剩余消息，且所有程序都投票决定停止时，计算终止。

Pregel 引入了可交换、可结合的消息合并器，即由用户定义、用于合并发往同一顶点之消息的函数。下面给出 Pregel 中 PageRank 顶点程序的示例。合并后，顶点程序接收唯一一条输入消息，其中包含所有入邻居 PageRank 的总和；程序据此计算新的 PageRank，并将其发送给出邻居。

```text
Message combiner(Message m1, Message m2):
    return Message(m1.value() + m2.value())

void PregelPageRank(Message msg):
    float total = msg.value()
    vertex.val = 0.15 + 0.85 * total
    foreach (nbr in out_neighbors):
        SendMsg(nbr, vertex.val / num_out_nbrs)
```

### 2.2 GraphLab

GraphLab [29] 是一种异步分布式共享内存抽象。顶点程序共享访问一个分布式图，而每个顶点和每条边上均可存储数据。无论边的方向如何，每个顶点程序都可以直接访问当前顶点、相邻边及相邻顶点上的信息。顶点程序还可以调度邻居顶点程序在未来执行。GraphLab 通过禁止相邻程序实例同时运行来保证可串行化。

下面给出 GraphLab 中 PageRank 顶点程序的示例。GraphLab 顶点程序直接读取邻居顶点值并计算总和。

```text
void GraphLabPageRank(Scope scope):
    float accum = 0
    foreach (nbr in scope.in_nbrs):
        accum += nbr.val / nbr.nout_nbrs()
    vertex.val = 0.15 + 0.85 * accum
```

GraphLab 消除了显式消息，使用户定义的算法与数据移动相隔离，系统因而能够自行选择何时、以何种方式移动程序状态。GraphLab 允许顶点和边都关联可变数据，使算法设计者可以更准确地区分与所有邻居共享的数据（顶点数据）和只与特定邻居共享的数据（边数据）。

### 2.3 特征刻画

GraphLab 和 Pregel 中 MLDM 顶点程序在收集与传播信息的方式上虽有不同，却具有共同的总体结构。为刻画这种共同结构，并区分顶点特定计算与边特定计算，我们提出图计算的 GAS 模型。GAS 模型把顶点程序概念性地分为三个阶段：收集（Gather）、应用（Apply）和散发（Scatter）。

在收集阶段，通过对运行 \(Q(u)\) 的顶点 \(u\) 的邻域执行广义求和，收集相邻顶点与边的信息：

\[
\Sigma \leftarrow \bigoplus_{v\in \operatorname{Nbr}[u]}
g\!\left(D_u,D_{(u,v)},D_v\right). \tag{2.1}
\]

其中，\(D_u\)、\(D_v\) 和 \(D_{(u,v)}\) 分别是顶点 \(u\)、顶点 \(v\) 和边 \((u,v)\) 的值，包括程序状态与元数据。用户定义的求和运算 \(\oplus\) 必须满足交换律和结合律；它既可以是数值求和，也可以是所有相邻顶点及边上数据的并集。收集阶段得到的 \(\Sigma\) 在应用阶段用于更新中心顶点的值：

\[
D_u^{\mathrm{new}}\leftarrow a(D_u,\Sigma). \tag{2.2}
\]

最后，散发阶段使用中心顶点的新值更新相邻边上的数据：

\[
\forall v\in\operatorname{Nbr}[u]:
D_{(u,v)}\leftarrow s\!\left(D_u^{\mathrm{new}},D_{(u,v)},D_v\right). \tag{2.3}
\]

顶点程序的扇入和扇出分别由相应的收集阶段和散发阶段决定。例如，在 PageRank 中，收集阶段只处理入边，散发阶段只处理出边。然而，许多 MLDM 算法的图边表达的是表面上对称的关系，例如友谊关系，此时收集与散发阶段都要触及所有边，扇入与扇出因而相等。第 3 节将表明，图并行抽象能否同时支持高扇入和高扇出计算，是在自然图上实现高效计算的关键。

**图 1：** Twitter 关注者网络的入度分布与出度分布，采用双对数坐标绘制。

GraphLab 与 Pregel 以截然不同的方式表达 GAS 程序。在 Pregel 抽象中，收集阶段通过消息合并器实现，应用与散发阶段则在顶点程序中表达。相反，GraphLab 向顶点程序暴露整个邻域，允许用户在程序内部定义收集与应用阶段。GraphLab 通过保证对顶点或边数据所做的修改自动对相邻顶点可见，隐式定义了收集/散发阶段的通信方式。还应注意，GraphLab 不区分边的方向。

## 3 自然图的挑战

自然图的稀疏结构给高效的分布式图并行计算带来了独特挑战。自然图的标志性属性之一是偏斜的幂律度分布 [16]：大多数顶点只有较少邻居，少数顶点则拥有大量邻居，例如社交网络中的名人。在幂律度分布下，顶点度数为 \(d\) 的概率为

\[
P(d)\propto d^{-\alpha}, \tag{3.1}
\]

其中指数 \(\alpha\) 是控制度分布“偏斜程度”的正常数。较大的 \(\alpha\) 意味着图密度（边数与顶点数之比）较低，绝大多数顶点的度较小；随着 \(\alpha\) 减小，图密度与高度顶点数量都会增加。大多数自然图的幂律常数通常约为 \(\alpha\approx 2\)。例如，Faloutsos 等人 [16] 估计 Internet 域间图的幂律常数约为 \(\alpha\approx 2.2\)。

在双对数坐标中绘制各个度数对应的顶点数量，可以直观呈现偏斜的幂律度分布。图 1 展示 Twitter 关注者网络的入度和出度分布，呈现出典型的线性幂律形态。幂律度分布虽可由经验观测得到，却不能完整刻画自然图的属性。关于更复杂的自然图模型已有大量研究（见 [27]），但本文技术只关注度分布，不需要其他建模假设。

偏斜的度分布意味着，一小部分顶点与很大一部分边相邻。例如，Twitter Web 图中 1% 的顶点与近一半的边相邻。这种边的集中形成了类似星形的结构，对现有图并行抽象提出了以下挑战：

- **工作负载均衡：** 对称对待所有顶点的图并行抽象会因幂律度分布而产生显著的工作失衡。由于收集和散发阶段的存储、通信与计算复杂度均与度数线性相关，不同顶点程序的运行时间可能差异悬殊 [36]。
- **划分：** 自然图难以划分 [26, 28]。GraphLab 和 Pregel 都依赖图划分来减少通信并保证工作负载均衡；但面对自然图时，两者都不得不采用哈希（随机）划分，而这种方法的局部性极差（第 5 节）。
- **通信：** 自然图偏斜的度分布会造成通信不对称，进而形成瓶颈。此外，高度顶点会迫使 Pregel 等消息抽象生成并发送大量相同消息。
- **存储：** 图并行抽象必须在本地存储每个顶点的邻接信息，因此每个顶点所需内存与其度数线性相关；高度顶点可能超出单台机器的内存容量。
- **计算：** 虽然多个顶点程序可以并行执行，但现有图并行抽象不会并行化单个顶点程序内部的计算，因而限制了在高度顶点上的可扩展性。

## 4 PowerGraph 抽象

为解决幂律图上的计算问题，我们提出新的图并行抽象 PowerGraph。它直接利用 GAS 分解，按边分解顶点程序，从而消除顶点程序对度数的依赖。PowerGraph 把收集和散发阶段提升到抽象层，在保留自然的“像顶点一样思考”理念 [30] 的同时，可将单个顶点程序的计算分布到整个集群。

PowerGraph 结合了 Pregel 和 GraphLab 的优势。它从 GraphLab 借鉴数据图和共享内存式计算视图，使用户不必自行设计信息移动；从 Pregel 借鉴满足交换律与结合律的收集概念。PowerGraph 既支持 Pregel 高度并行的批同步计算模型，也支持 GraphLab 计算效率较高的异步模型。

与 GraphLab 一样，PowerGraph 程序的状态按数据图分解，包含用户定义的顶点数据 \(D_v\) 与边数据 \(D_{(u,v)}\)。数据图中的数据既包括元数据（如 URL 和边权重），也包括计算状态（如顶点的 PageRank）。第 5 节将介绍顶点切割，它使 PowerGraph 能够在分布式环境中高效表示和存储幂律图。

### 4.1 GAS 顶点程序

PowerGraph 中的计算被编码为无状态顶点程序。程序实现如下 `GASVertexProgram` 接口，显式分解为 `gather`、`sum`、`apply` 和 `scatter` 函数。PowerGraph 引擎按照算法 1 的语义，分阶段调用这些函数。由于顶点程序已经分解，执行引擎可将单个顶点程序分布到多台机器，并把计算移向数据。

```text
interface GASVertexProgram(u) {
    // 在 gather_nbrs(u) 上运行
    gather(Du, D(u,v), Dv) → Accum
    sum(Accum left, Accum right) → Accum
    apply(Du, Accum) → Du_new

    // 在 scatter_nbrs(u) 上运行
    scatter(Du_new, D(u,v), Dv) → (D(u,v)_new, Accum)
}
```

**图 2：** 所有 PowerGraph 程序都必须实现无状态的 `gather`、`sum`、`apply` 和 `scatter` 函数。

**算法 1　顶点程序执行语义**

```text
输入：中心顶点 u
if 缓存的累加器 au 为空 then
    foreach gather_nbrs(u) 中的邻居 v do
        au ← sum(au, gather(Du, D(u,v), Dv))
    end
end
Du ← apply(Du, au)
foreach scatter_nbrs(u) 中的邻居 v do
    (D(u,v), Δa) ← scatter(Du, D(u,v), Dv)
    if av 与 Δa 均非空 then
        av ← sum(av, Δa)
    else
        av ← 空
    end
end
```

在收集阶段，`gather` 和 `sum` 分别充当映射与归约操作，用于收集顶点邻域信息。`gather` 在与 \(u\) 相邻的各条边上并行调用；具体边集由 `gather_nbrs` 指定，可以是空集、入边、出边或所有边。`gather` 接收相邻顶点与边的数据，返回用户定义类型的临时累加器。各结果通过满足交换律和结合律的 `sum` 运算合并。收集阶段的最终结果 \(a_u\) 被传入应用阶段，并由 PowerGraph 缓存。

收集完成后，`apply` 接收最终累加器，计算新的顶点值 \(D_u\)，并将其原子写回图中。累加器 \(a_u\) 的大小与 `apply` 的复杂度对 PowerGraph 的网络和存储效率起决定作用；二者应当关于顶点度数呈次线性增长，理想情况下应为常数。

在散发阶段，`scatter` 在与 \(u\) 相邻的边上并行调用，产生并写回数据图的新边值 \(D_{(u,v)}\)。与收集阶段相同，`scatter_nbrs` 指定调用 `scatter` 的边集。`scatter` 还可以返回可选值 \(\Delta a\)，用于动态更新相邻顶点 \(v\) 的缓存累加器 \(a_v\)（见第 4.2 节）。

图 3 使用 PowerGraph 抽象实现了 PageRank、贪心图着色和单源最短路径（SSSP）。PageRank 的 `gather` 与 `sum` 收集相邻顶点值之和，`apply` 计算新的 PageRank，`scatter` 在必要时激活相邻顶点程序。图着色的 `gather` 与 `sum` 收集相邻顶点的颜色集合，`apply` 计算新颜色，`scatter` 激活违反着色约束的相邻顶点。SSSP 的 `gather` 与 `sum` 计算经过各邻居的最短路径，`apply` 返回新距离，`scatter` 激活受影响的邻居。

| 函数 | PageRank | 贪心图着色 | 单源最短路径（SSSP） |
|---|---|---|---|
| `gather_nbrs` | 入邻居 | 所有邻居 | 所有邻居 |
| `gather` | 返回 \(D_v.rank/\#outNbrs(v)\) | 返回集合 \(\{D_v\}\) | 返回 \(D_v+D_{(v,u)}\) |
| `sum` | \(a+b\) | \(a\cup b\) | \(\min(a,b)\) |
| `apply` | \(r_{new}=0.15+0.85\,acc\)，并记录增量 | 选择不在集合中的最小颜色 | 令 \(D_u\) 为新距离 |
| `scatter_nbrs` | 出邻居 | 所有邻居 | 所有邻居 |
| `scatter` | 增量超过 \(\varepsilon\) 时激活邻居并返回增量 | 相邻颜色相同时激活邻居；使缓存失效 | 距离改变时激活邻居；可返回新路径值 |

**图 3：** 在 PowerGraph 抽象中实现的 PageRank、图着色和单源最短路径算法。PageRank 与单源最短路径均支持在收集阶段使用增量缓存。

### 4.2 增量缓存

很多时候，只有少数邻居发生变化便会触发某个顶点程序。此时，收集操作仍会反复作用于全部邻居，其中许多并未变化，从而浪费计算周期。对许多算法 [2]，可以动态维护收集结果 \(a_u\)，并在后续迭代中跳过收集。

PowerGraph 引擎为每个顶点保留上一次收集阶段的累加器 \(a_u\)。`scatter` 可额外返回 \(\Delta a\)，由 `sum` 原子地加到邻居顶点 \(v\) 的缓存累加器 \(a_v\) 上。如果未返回 \(\Delta a\)，则清空邻居的缓存 \(a_v\)，迫使其下一次执行顶点程序时进行完整收集。如果缓存 \(a_v\) 可用，PowerGraph 执行顶点 \(v\) 的程序时直接使用该值，绕过收集阶段。

直观而言，\(\Delta a\) 是对该边先前收集结果的加性修正。更形式化地，若累加器类型构成阿贝尔群，即具有满足交换律和结合律的加法以及逆运算，则可定义（以 \(g\) 简写 `gather`）：

\[
\Delta a =
g\!\left(D_u,D_{(u,v)}^{\mathrm{new}},D_v^{\mathrm{new}}\right)
-g\!\left(D_u,D_{(u,v)},D_v\right). \tag{4.1}
\]

图 3 的 PageRank 示例利用了 PageRank 求和操作的阿贝尔性质；图着色中的集合并运算不构成阿贝尔群，因而只能使累加器失效。

### 4.3 发起后续计算

PowerGraph 引擎维护一个活动顶点集合，最终会在这些顶点上执行顶点程序。用户通过调用 `Activate(v)` 或 `Activate_all()` 发起计算。随后，引擎不断在活动顶点上执行程序，直至活动顶点集合为空。顶点程序完成散发阶段后变为非活动状态，直到再次被激活。

顶点可以激活自身与相邻顶点。顶点程序中的每个函数只能激活其参数中可见的顶点；例如，在边 \((u,v)\) 上调用的 `scatter` 只能激活 \(u\) 与 \(v\)。这一限制确保激活事件产生于能够高效处理它的机器上。

活动顶点的执行顺序由 PowerGraph 执行引擎决定；唯一保证是所有活动顶点最终都会得到执行。这种调度灵活性使 PowerGraph 程序既可同步执行，也可异步执行，从而在算法性能、系统性能与确定性之间形成不同权衡。

#### 4.3.1 批同步执行

同步运行时，PowerGraph 引擎按顺序执行收集、应用和散发阶段。每个阶段称为一个小步（minor-step），在所有活动顶点上同步运行，并在阶段末设置屏障。完整的一组 GAS 小步称为一个超步。对顶点数据和边数据的修改在各小步结束时提交，并在下一小步中可见；每个超步中激活的顶点在下一超步执行。

同步执行模型无论使用多少台机器都能保证确定性，且与 Pregel 十分相似。然而，频繁的屏障以及无法使用最新数据，可能造成低效的分布式执行和缓慢的算法收敛。为克服这些限制，PowerGraph 也支持异步执行。

#### 4.3.2 异步执行

异步运行时，只要处理器与网络资源可用，PowerGraph 引擎便执行活动顶点。`apply` 与 `scatter` 对顶点和边数据的修改会立即提交到图，并对相邻顶点上的后续计算可见。

异步执行能够即时利用可用的处理器与网络资源，并让数据图修改立即对后续计算可见，因此可更有效地利用资源，加快底层算法收敛。例如，图 3 中的贪心图着色算法同步执行时无法收敛，异步执行时却能迅速收敛。异步计算在数值算法领域的优势已有广泛研究 [4]；我们在 [18, 19, 29] 中证明，对一系列重要 MLDM 应用，异步计算能够在理论和实践上同时改善算法与系统性能。

不过，异步执行行为取决于机器数量与网络资源可用性，由此产生的非确定性会增加算法设计与调试难度。对统计模拟等算法，如果未谨慎控制，非确定性甚至可能导致不稳定或发散 [17]。

为解决这些问题，GraphLab 自动强制可串行化，即每次并行执行都对应一次顺序执行。文献 [29] 表明，可串行化足以支持广泛的 MLDM 算法。GraphLab 采用细粒度锁协议，禁止相邻顶点程序同时运行；该协议必须依次获取所有邻居顶点上的锁，而且对高度顶点并不公平。

PowerGraph 保留 GraphLab 的强可串行化保证，同时解决其局限。我们引入新的并行加锁协议（第 7.4 节），消除顺序加锁问题，并公平对待高度顶点。此外，PowerGraph 暴露出细得多的边级并行性，使整个集群都能参与单个顶点程序的执行。

### 4.4 与 GraphLab、Pregel 的比较

尽管 PowerGraph 抽象施加了很强的约束，它仍能模拟 GraphLab 与 Pregel 的顶点程序。要模拟 GraphLab 顶点程序，可通过 `gather` 与 `sum` 拼接所有相邻顶点和边上的数据，再在 `apply` 中运行 GraphLab 程序。

要表达 Pregel 顶点程序，可通过 `gather` 与 `sum` 合并输入消息（以边数据存储），并拼接计算输出消息所需的邻居列表。Pregel 顶点程序随后在 `apply` 中运行，生成消息集合，并把消息作为顶点数据传递给 `scatter`，由后者写回边。

为解决自然图问题，PowerGraph 要求累加器大小与 `apply` 复杂度关于度数呈次线性增长。然而，直接在 `apply` 中执行 GraphLab 或 Pregel 顶点程序，会使累加器大小与 `apply` 复杂度均与度数线性相关，从而丧失 PowerGraph 在自然图上的诸多优势。

## 5 分布式图放置

PowerGraph 抽象依赖分布式数据图来存储计算状态，并编码顶点程序之间的交互。数据图结构与数据的放置方式，对减少通信和保证工作负载均衡至关重要。

在由 \(p\) 台机器组成的集群上放置图，一种常见方法是构造均衡的 \(p\) 路边切割（图 4a）：将顶点均匀分配给各机器，并尽量减少跨机器的边。不幸的是，构造均衡边切割的工具 [23, 31] 在幂律图上的表现很差 [1, 26, 28]。图难以划分时，GraphLab 和 Pregel 都会采用哈希（随机）顶点放置。该方法快速且易于实现，却会切断绝大多数边。

**定理 5.1。** 若将顶点随机分配给 \(p\) 台机器，则被切边所占比例的期望为

\[
\mathbb{E}\!\left[\frac{|\text{Edges Cut}|}{|E|}\right]
=1-\frac{1}{p}. \tag{5.1}
\]

对于指数为 \(\alpha\) 的幂律图，每个顶点对应的期望被切边数为

\[
\mathbb{E}\!\left[\frac{|\text{Edges Cut}|}{|V|}\right]
=\left(1-\frac1p\right)\mathbb{E}[D[v]]
=\left(1-\frac1p\right)\frac{h_{|V|}(\alpha-1)}{h_{|V|}(\alpha)}, \tag{5.2}
\]

其中

\[
h_{|V|}(\alpha)=\sum_{d=1}^{|V|-1}d^{-\alpha}
\]

是幂律 Zipf 分布的归一化常数。

**证明。** 当一条边的两个端点被随机分配到不同机器时，该边被切断；这一事件的概率为 \(1-1/p\)。证毕。

每条被切边都会带来存储与网络开销，因为两台机器都要保存邻接信息的副本；在某些情形 [20] 中，还需保存顶点和边数据的幽灵副本（ghost）。例如，图 4a 将一个四顶点图切成三部分，产生五个幽灵顶点，而且所有边数据都被复制。与被切边相关联的顶点或边数据一旦变化，就必须通过网络同步。即使只有两台机器，随机切割也会切断约一半的边，需要约 \(|E|/2\) 的通信量。

**图 4：** 将一个图切成三部分的（a）边切割与（b）顶点切割。阴影顶点分别表示幽灵副本和镜像副本。

### 5.1 均衡的 \(p\) 路顶点切割

PowerGraph 沿图中的边分解顶点程序，允许单个顶点程序跨越多台机器。图 5 中，一个高度顶点程序被拆分到两台机器；`gather` 和 `scatter` 在两台机器上并行运行，累加器与顶点数据则通过网络交换。

正因为单个顶点程序可以跨越多台机器，我们可以把边均匀分配给机器，并允许顶点跨机器存在，从而改善工作负载均衡，降低通信和存储开销。每台机器只保存分配给它的边信息，使海量边数据得到均匀分布。由于每条边只存储一次，边数据变化无须通信。然而，顶点的变化必须复制到该顶点所跨越的所有机器，因此存储与网络开销取决于每个顶点跨越的机器数。

**图 5：** 采用顶点切割时 PowerGraph 抽象的通信模式。`gather` 在每台机器上本地运行，各镜像向主副本发送一个累加器；主副本执行 `apply`，再把更新后的顶点数据发送给所有镜像；最后，各镜像并行执行 `scatter`。

我们通过限制每个顶点跨越的机器数，最小化存储与网络开销。均衡的 \(p\) 路顶点切割把目标形式化为：将每条边 \(e\in E\) 分配给机器 \(A(e)\in\{1,\ldots,p\}\)。每个顶点由此跨越集合 \(A(v)\subseteq\{1,\ldots,p\}\)，其中各机器至少包含一条与 \(v\) 相邻的边。均衡顶点切割的目标为

\[
\min_A\ \frac1{|V|}\sum_{v\in V}|A(v)|, \tag{5.3}
\]

满足

\[
\max_m |\{e\in E\mid A(e)=m\}| < \lambda\frac{|E|}{p}, \tag{5.4}
\]

其中失衡因子 \(\lambda\ge 1\) 是一个较小常数。

我们把顶点 \(v\) 的 \(|A(v)|\) 个副本称为该顶点的复制副本：\(A(v)\) 中的每台机器都有一个 \(v\) 的副本。由于顶点数据变化要发送给所有副本，通信开销也由 \(|A(v)|\) 决定。因此，式（5.3）最小化图中的平均复制副本数，进而最小化 PowerGraph 引擎的总体存储与通信需求。

对于拥有多个副本的顶点 \(v\)，随机指定其中一个为主副本（master），维护顶点数据的主版本；其余副本称为镜像（mirror），维护本地只读缓存（图 4b）。图 4b 对一个图作三路顶点切割，只产生两个镜像。任何顶点数据修改（如 `apply`）都必须在主副本上执行，随后立即复制到所有镜像。

顶点切割解决了幂律图中边切割的主要问题。渗流理论 [3] 表明，幂律图通常具有良好的顶点切割。直观地说，只要切割少量度数极高的顶点，就能迅速使图破碎。此外，均衡约束式（5.4）保证边均匀分布于各机器，即使存在度数极高的顶点，也能自然改善工作负载均衡。

构造顶点切割最简单的方法是把边随机分配给机器。随机（哈希）边放置完全数据并行，在大图上几乎可达到完美均衡，也适用于流式场景。下面的定理将期望归一化复制因子（式 5.3）与机器数及幂律常数 \(\alpha\) 联系起来。

**定理 5.2（随机顶点切割）。** 在 \(p\) 台机器上进行随机顶点切割，其期望复制因子为

\[
\mathbb{E}\!\left[\frac1{|V|}\sum_{v\in V}|A(v)|\right]
=\frac{p}{|V|}\sum_{v\in V}
\left[1-\left(1-\frac1p\right)^{D[v]}\right], \tag{5.5}
\]

其中 \(D[v]\) 表示顶点 \(v\) 的度数。对于幂律图，期望复制因子（图 6a）完全由幂律常数 \(\alpha\) 决定：

\[
\mathbb{E}\!\left[\frac1{|V|}\sum_{v\in V}|A(v)|\right]
=p-\frac{p}{h_{|V|}(\alpha)}
\sum_{d=1}^{|V|-1}
\left(\frac{p-1}{p}\right)^d d^{-\alpha}, \tag{5.6}
\]

其中 \(h_{|V|}(\alpha)=\sum_{d=1}^{|V|-1}d^{-\alpha}\)。

**证明。** 由期望的线性性，

\[
\mathbb{E}\!\left[\frac1{|V|}\sum_{v\in V}|A(v)|\right]
=\frac1{|V|}\sum_{v\in V}\mathbb{E}[|A(v)|]. \tag{5.7}
\]

考虑将与单个顶点 \(v\) 相邻的 \(D[v]\) 条边随机分配。令指示变量 \(X_i\) 表示 \(v\) 至少有一条边位于机器 \(i\) 上，则

\[
\begin{aligned}
\mathbb{E}[X_i]
&=1-P(v\text{ 在机器 }i\text{ 上没有边}) \tag{5.8}\\
&=1-\left(1-\frac1p\right)^{D[v]}. \tag{5.9}
\end{aligned}
\]

因此

\[
\mathbb{E}[|A(v)|]
=\sum_{i=1}^{p}\mathbb{E}[X_i]
=p\left[1-\left(1-\frac1p\right)^{D[v]}\right]. \tag{5.10}
\]

代入式（5.7）即得式（5.5）。再把顶点度视为服从
\(P(d)=d^{-\alpha}/h_{|V|}(\alpha)\) 的 Zipf 随机变量并取期望，即得式（5.6）。证毕。

| UK [7] | 1.328 亿 | 55 亿 | 1.9 |
| Amazon [5, 6] | 70 万 | 520 万 | 2.0 |

图 6a 针对不同幂律常数绘制了随机顶点切割的期望复制因子。较低的 \(\alpha\) 意味着高度顶点更多，因而复制因子更高。图 6b 比较随机边切割与随机顶点切割的通信和存储成本，表明顶点切割可带来数量级改进。

**定理 5.3（顶点切割上界）。** 任意一个产生 \(g\) 个幽灵顶点的边切割，都可转换为一个大小相同、镜像数严格少于 \(g\) 的顶点切割。

**证明。** 考虑被切边集合 \(E'\)，令 \(V'\) 为它们所诱导的顶点集。幽灵顶点总数至少为 \(|V'|\)。从 \(V'\) 中任取一个顶点及其相邻边删除，直到 \(E'\) 中不再剩边；这等价于沿一个顶点分隔集进行顶点切割。最多需要删除 \(|V'|-1\) 个顶点，因此最多产生 \(|V'|-1\) 个镜像。证毕。

### 5.2 贪心顶点切割

我们可以通过对边放置过程去随机化来改进随机顶点切割。所得算法是一种顺序贪心启发式：把下一条边放到使条件期望复制因子最小的机器。设前 \(i\) 条边已经放置，其分配为 \(A_i\)。对第 \(i+1\) 条边，目标为

\[
\arg\min_k\ 
\mathbb{E}\!\left[
\sum_{v\in V}|A(v)|
\;\middle|\;
A_i,\ A(e_{i+1})=k
\right]. \tag{5.13}
\]

利用定理 5.2 计算式（5.13），对边 \((u,v)\) 可得到以下放置规则：

1. 若 \(A(u)\) 与 \(A(v)\) 相交，则把边分配到交集中的一台机器。
2. 若二者均非空但不相交，则选择尚未分配边数更多的那个顶点，并把边分配到该顶点所在的某台机器。
3. 若只有一个顶点已被分配，则从该顶点所在的机器中选择一台。
4. 若两个顶点都未被分配，则把边分配给负载最低的机器。

由于该贪心启发式是对随机算法的去随机化，其期望复制因子保证不劣于随机放置，实践中往往好得多。随机算法易于并行和分布式执行，而贪心算法需要机器间协调。我们考察两种分布式实现：

- **协调式（Coordinated）：** 在分布式表中维护 \(A_i(v)\)。每台机器运行贪心启发式，并定期更新分布式表。通过本地缓存降低通信，但会牺牲 \(A_i(v)\) 估计的准确性。
- **无感知式（Oblivious）：** 每台机器独立运行贪心启发式。各机器只维护自己的 \(A_i\) 估计，不产生额外通信。

图 7a 比较五个真实图上随机、无感知式和协调式启发法的实际复制因子。两种贪心启发法在所有场景中都显著优于随机放置；固定 \(p=32\) 时，协调式方法把复制因子降低了近一个数量级。无感知式方法略逊于协调式方法，却不需要协调，因而在加载时间与复制因子之间取得良好折中。图 7b 表明，更低的复制因子可直接降低算法运行时间。

## 6 抽象比较

本节通过实验刻画在幂律扇入与扇出图上运行 PageRank 时，Pregel、GraphLab 与 PowerGraph 对 \(\alpha\) 的依赖。我们构造五个千万顶点的幂律图，\(\alpha\) 从 1.8 到 2.2。每个图先从 Zipf 分布随机抽取各顶点入度，再添加相应数量的出边，获得幂律入度图；随后反转全部边，得到与之对应且度数分布完全相同的幂律出度图。每个图的密度以及每个顶点的扇入/扇出由 \(\alpha\) 决定。

实验使用 GraphLab v1 的 C++ 实现 [29]，并增加网络用量检测。当时公开的 Pregel 实现（如 Giraph）受内存限制，甚至无法处理较小的合成问题，因此我们使用 Piccolo [32] 作为 Pregel 的代理实现：Piccolo 能自然表达 Pregel 抽象，并提供带动态负载均衡的高效 C++ 实现。PowerGraph 使用第 7 节所述实现。

本节实验在一个八节点 Linux 集群上完成。每个节点有两颗四核 Intel Xeon E5620 处理器、32 GB 内存，通过 1 GigE 以太网互连；所有系统均用 GCC 4.4 编译。GraphLab 与 Piccolo 使用随机边切割，PowerGraph 使用随机顶点切割。结果为 20 次迭代的平均值。

### 6.1 计算失衡

PageRank 顶点程序的顺序计算部分，在 Pregel 抽象中与出度成正比，在 GraphLab 抽象中与入度成正比。PowerGraph 则通过把单个顶点程序分布到多台机器，消除了这种顺序依赖。因此，对高度偏斜（低 \(\alpha\)）的幂律图，我们预期 Pregel（扇入图）与 GraphLab（扇出图）会出现更严重的工作失衡，而 PowerGraph 不会，因为它能均匀分布高度顶点程序。

为检验该假设，我们让每个系统运行八个工作进程（共 64 个工作进程），记录各工作进程的顶点程序时间。图 9a、9b 分别绘制幂律扇入图与扇出图上各工作进程每轮运行时间的标准差，以此衡量工作失衡；标准差越大，失衡越严重。较低的 \(\alpha\) 会增加 GraphLab 在扇入图和 Pregel 在扇出图上的工作失衡，而 PowerGraph 在两个边方向上都不受影响。

### 6.2 通信失衡

GraphLab 和 Pregel 使用边切割，通信量与幽灵副本数量成正比，即与划分边界上复制的顶点和边数据量成正比。如果每条边发送一条消息，Pregel 的合并器可确保每个幽灵副本恰好传输一条网络消息。类似地，每轮迭代结束时 GraphLab 会同步各幽灵副本，所以通信量同样与幽灵数成正比。

PowerGraph 使用顶点切割，每轮迭代后只同步镜像。因此，完整迭代的通信量与顶点切割产生的镜像数成正比，我们由此预期 PowerGraph 能减少通信量。

图 9c、9d 给出三个系统在幂律扇入与扇出图上的每轮通信字节数。Pregel 只沿出边发送消息，因而在幂律扇出图上的通信量高于扇入图。GraphLab 与 PowerGraph 在数据同步时都不考虑边方向，其通信量不受扇入或扇出影响。不过，由于顶点切割卓有成效，PowerGraph 的通信量显著低于 GraphLab。即使图变得更稠密，PowerGraph 的总通信量也只略有上升，且整体最低。

**图 9：合成实验——工作失衡与通信。** （a）、（b）三种抽象在幂律扇入图和扇出图上、跨 8 个分布式工作进程的计算时间标准差；（c）、（d）三种抽象在两类图上的每轮通信字节数。

### 6.3 运行时间比较

在低 \(\alpha\) 图上，PowerGraph 的性能显著优于 GraphLab 和 Pregel。图 10a、10b 给出各抽象的每轮运行时间。两种情况下，总体运行性能都与通信开销（图 9c、9d）高度一致，而计算失衡（图 9a、9b）的影响似乎不大。这是因为 PageRank 计算相对轻量；我们预计统计推断等更复杂算法更容易受到失衡影响。

采用贪心的协调式划分后，运行时间还可进一步改善 25%—50%。

## 7 实现与评估

本节描述并评估 PowerGraph 系统的实现。所有实验均在由 64 个 Amazon EC2 `cc1.4xlarge` Linux 实例组成的集群上完成。每个实例有两颗四核 Intel Xeon X5570 处理器、23 GB 内存，并通过 10 GigE 以太网连接。PowerGraph 使用 C++ 编写，以 GCC 4.5 编译。

我们实现了 PowerGraph 抽象的三种变体。为展示其相对实现复杂度，下面给出排除公共支持代码后的代码行数：

- **批同步（Sync）：** 第 4.3.1 节所述的完全同步实现，约 600 行。
- **异步（Async）：** 第 4.3.2 节所述的异步实现，允许顶点程序任意交错，约 900 行。
- **可串行化异步（Async+S）：** 保证所有顶点程序可串行化的异步实现，等价于 GraphLab 的“边一致性”，约 1600 行。

三种实现都完全对称，不存在单一协调实例或调度器。每个实例只需获得其他机器的列表，启动时从 HDFS 读取图数据文件的一个独立子集。系统按需与其他机器建立 TCP 连接，以构造分布式图并运行引擎。

### 7.1 图加载与放置

所有实例并行地从分布式文件系统 HDFS 中的一组文本文件加载图结构与数据。每台机器通过哈希确定自己加载的文件子集，并在加载过程中应用三种分布式图划分算法之一来放置数据。因此，划分过程并行完成，数据会立即到达最终位置。除非另有说明，所有实验均采用无感知式算法。计算结束后，最终顶点与边数据并行写回分布式文件系统。

图 7b 比较不同划分方法下多种算法的性能。简单的划分启发法就能显著改善所有算法的性能，降低运行时间与内存占用。此外，运行时间与复制因子呈线性关系：复制因子减半，运行时间也大致减半。

### 7.2 同步引擎（Sync）

同步实现严格遵循第 4.3.1 节。每台机器运行一个多线程实例，以充分利用多核架构；系统通过后台通信交叠计算与通信。同步引擎的执行完全确定，便于从程序层面理解，也减少了调优和性能优化所需的工作。

图 11a、11b 分别给出各种划分方法下，在 Twitter 关注者网络上执行一轮 PageRank 的运行时间和总通信量。作为对照（表 2），Spark [37] 在同一张图上使用 50 个节点、100 个核心的集群执行一轮 PageRank 需 97.4 秒 [35]。在核心数可比时，PowerGraph 比 Spark 快 3—8 倍；使用完整的 512 核集群时，每轮只需 3.6 秒。

贪心划分启发法以更长加载时间为代价，改善了引擎性能与可扩展性。随机、无感知式和协调式放置的加载时间分别为 59、105 和 239 秒。贪心启发法虽使加载时间最多增加至四倍，但只要 PageRank 迭代超过 20 轮，就能缩短总运行时间。

图 11c 给出 Twitter 图上 PageRank 各轮运行时间。增量缓存避免了不必要的收集计算，使总运行时间减少 45%。图 11d 评估弱扩展性，即保持每个处理器的问题规模不变时的扩展能力。我们在 \(\alpha=2\)、每台机器一千万顶点的合成幂律图上运行 SSSP（图 3）。实现表现出接近最优的弱扩展性，只需 65 秒即可求解一张含 64 亿条边的图。

**图 11：同步实验。** （a）、（b）同步 PageRank 在 Twitter 图上的扩展性与通信量；（c）启用和禁用增量缓存时，每轮 PageRank 的运行时间；（d）SSSP 在合成图上的弱扩展性。

### 7.3 异步引擎（Async）

我们用每个顶点上的简单状态机实现第 4.3.2 节的异步模型。顶点可处于 `INACTIVE`、`GATHER`、`APPLY` 或 `SCATTER` 状态。顶点被激活后进入收集状态，并被放入本地调度器。调度器把核心分配给活动顶点，使许多顶点程序可以同时运行，从而隐藏通信延迟。

虽然允许顶点程序任意交错，我们仍保证每次 `gather`、`apply` 和 `scatter` 调用都独占访问其参数，以避免数据竞争。

我们在 Twitter 关注者网络上运行 PageRank，评估 Async 引擎。图 12a 给出吞吐量（每秒顶点程序操作数）随机器数的变化。随着机器数增加和划分改善，吞吐量均有所提高。为评估增量缓存的收益，图 12b 比较启用与禁用缓存时吞吐量随时间的变化。缓存使算法以更少操作更快收敛。

令人意外的是，禁用缓存时，吞吐量会随时间上升。进一步分析表明，计算逐渐集中到高度顶点上，使计算/通信比提高。

我们还评估图 3 的图着色顶点程序。该程序无法同步运行，因为每轮中所有顶点都会变成同一种颜色；图着色可作为许多 MLDM 算法的代理 [17]。图 12c 在 \(\alpha=2\)、每台机器五百万顶点的合成幂律图上评估弱扩展性，结果表明 Async 引擎接近最优。运行时间略有增加，可能是图规模扩大导致所需颜色数量增多所致。

### 7.4 可串行化异步引擎（Async+S）

Async 引擎适用于广泛任务，具有较高吞吐量和性能。然而，与同步引擎不同，异步引擎较难从程序层面推理，因此我们扩展 Async 引擎以强制可串行化。

Async+S 通过禁止相邻顶点程序同时运行来保证可串行化。对图并行计算保证可串行化，等价于求解“哲学家就餐”问题：每个顶点是一位哲学家，每条边是一把叉子。GraphLab [29] 实现了 Dijkstra 的方案 [14]，按全序依次获取叉子。我们则实现 Chandy–Misra 方案 [10]，同时获取所有叉子，从而允许更高并行度。

我们把 Chandy–Misra 方案扩展到顶点切割场景：每个顶点副本只请求本地边对应的叉子，再通过简单的共识协议判断所有副本是否均已成功。

我们在图着色任务上评估 Async+S 的可扩展性与计算效率。图 12c 显示，可实现的并行度不会随顶点数线性增长。由于幂律图的密度（即竞争程度）随顶点数超线性增长，我们本来也不期望可串行化并行度线性增加。

图 12d 给出 Async 与 Async+S 中满足着色条件（两个端点颜色不同）的边所占比例。Async 很快使大多数边满足条件，但剩余 1% 的边却消耗 34% 的运行时间。我们认为，这是紧密连接的顶点上频繁发生竞争所致。Async+S 的表现则更均匀。从用户操作总数看，Async 完成的工作量超过 Async+S 的两倍。

**图 12：异步实验。** （a）随着机器数增加，动态 PageRank 每秒发出的用户操作（`gather`/`apply`/`scatter`）数量；（b）启用和禁用缓存时，用户操作总数随时间的变化；（c）Async 与 Async+S 执行图着色时的弱扩展性；（d）在 8 台机器、4000 万顶点的问题实例上，无冲突边比例随时间的变化。绿色曲线表示 Async 因缺乏一致性而引入冲突边的速率，峰值为每秒 23.6 万条；Async+S 从不引入冲突边。

最后，我们在一种常用机器学习算法——交替最小二乘（ALS）上评估 Async 与 Async+S。ALS 有多种变体，可用于用户个性化 [38]、文档语义分析 [21] 等广泛应用。我们把 ALS 应用于 Wikipedia 词项—文档图，该图含 1100 万个顶点、3.15 亿条边，用于为每个文档和词项提取主题混合表示。主题数 \(d\) 是自由参数，决定每个顶点程序 \(O(d^3)\) 的计算复杂度。

图 13a 比较两个引擎的 ALS 吞吐量。Async 吞吐量更高，但随着 \(d\) 增大、计算逐渐超过一致性开销，二者差距缩小。为说明可串行化的重要性，图 13b 给出训练误差这一解质量指标。Async 虽具有更高吞吐量，Async+S 却收敛得更快。

Async+S 引擎的复杂性是合理的，因为许多应用（如 ALS）必须具备可串行化。此外，可串行化还为非确定性异步执行增添了可预测性。例如，在稠密图上，即使图着色也可能无法终止，除非保证可串行化。

**图 13：** （a）ALS 吞吐量，以每秒百万次用户操作计；（b）ALS 应用的训练误差（越低越好）随运行时间的变化。

### 7.5 容错

与 GraphLab、Pregel 一样，PowerGraph 通过保存数据图快照实现容错。同步 PowerGraph 引擎在超步之间构建快照；异步引擎则暂停执行来构建快照。也可实现使用 GraphLab 快照算法 [29] 的异步快照。即使对本文考察的最大图，检查点开销通常也只有数秒，相对于每个应用的运行时间很小。

## 8 相关工作

分布式图放置中的顶点切割方法与超图划分研究 [9, 13] 有关。具体而言，把每条边转换为一个顶点、把每个顶点转换为一条超边，即可将顶点切割问题转化为超图切割问题。然而，现有超图划分可能非常耗时。我们的切割目标与“通信量”目标相似，但本文描述的流式顶点切割场景是新的。Stanton 等人 [35] 提出了若干流式边切割启发法，却未考虑顶点切割问题。

一些工作 [8, 22] 提议以广义稀疏矩阵—向量乘法作为图并行计算的基础。这些抽象在满足交换律与结合律的半环上运行，因此也具备广义 `gather` 与 `sum` 操作。然而，它们不支持更通用的 `apply`、`scatter` 和可变边数据，而且基于严格同步模型，每轮都要运行全部计算。

除本文详细讨论的 Pregel 与 GraphLab 外，还有其他相似的图并行抽象。BPGL [20] 与 Pregel 密切相关，实现了同步遍历者模型。Kineograph [11] 面向随时间演化的图，融合了 GraphLab 与 Piccolo 的特性。Pujol 等人 [33] 提出一种分布式图数据库，但未显式考虑幂律结构。

GraphChi [25] 是 GraphLab 抽象的高效单机磁盘实现。令人印象深刻的是，它仅用一台机器便能在许多图问题上显著超越大型 Hadoop 部署：在 Twitter 图上执行一轮 PageRank 只需 158 秒，而 PowerGraph 为 3.6 秒。GraphChi 的技术可用于为 PowerGraph 增加外存支持。

## 9 结论与未来工作

对大规模图结构数据进行推理的需求，推动了 GraphLab、Pregel 等新型图并行抽象的发展。然而，由现实世界现象形成的图往往具有幂律度分布，难以划分，容易造成工作失衡，并显著增加通信与存储开销。

为应对这些挑战，我们提出 PowerGraph 抽象。它利用“收集—应用—散发”（GAS）计算模型，沿边分解顶点程序，从而拆分高度顶点，并在自然图中暴露更多并行性。随后，我们提出顶点切割及一组快速贪心启发法，大幅降低大型分布式幂律图的存储和通信成本。

我们从理论上建立幂律常数与 PowerGraph 系统通信、存储需求之间的联系，并通过与 GraphLab 和 Pregel 的比较对分析进行了实证检验。最后，我们在一个 64 节点 EC2 集群上，以多个大规模问题评估 PowerGraph，证明其具有良好的可扩展性与效率，并且在许多情况下，相较已发表结果可获得数量级提升。

我们正使用 PowerGraph 探索新的大规模机器学习算法，并开始研究如何利用顶点复制与数据依赖关系，在不设置检查点的情况下支持容错。此外，我们也在探索支持时变图结构的方法。最后，我们相信，PowerGraph 抽象中的许多核心思想会对 PowerGraph 之外的图并行系统设计与实现产生重要影响。
