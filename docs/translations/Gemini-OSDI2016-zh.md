## 摘要

传统的分布式图处理系统主要通过优化节点间通信与负载均衡来追求可扩展性。然而，与共享内存图计算框架相比，这些系统的总体处理效率往往并不理想。我们分析了若干图并行系统的行为，发现为获得可扩展性而引入的额外开销已经成为限制效率的主要因素；在采用现代多核处理器和高速互连网络时，这一问题尤为突出。

基于上述观察，我们提出 Gemini——一种采用多项面向计算性能的优化、在高效率基础上构建可扩展性的分布式图处理系统。Gemini 采用：（1）稀疏—稠密信号—槽抽象，将共享内存环境中的混合推—拉计算模型扩展至分布式场景；（2）基于块的划分方案，在实现低开销横向扩展的同时保留顶点访问局部性；（3）双重表示方案，以压缩对顶点索引的访问；（4）NUMA 感知的子划分，以提高节点内存访问效率；以及（5）局部性感知的分块与细粒度工作窃取，分别改善节点间和节点内负载均衡。

我们在一个 8 节点高性能集群上，使用五种广泛采用的图应用和五个真实世界图进行评估。结果表明，Gemini 显著优于所有知名的现有分布式图处理系统；相较其中最快的系统，其性能提升为 8.91 倍至 39.8 倍。

## 1 引言

图处理正日益受到学术界和工业界的重视。随着图数据规模快速增长，人们提出了许多专门的分布式系统 [3, 12, 16, 17, 30, 32, 41, 45] 来处理大规模图。尽管这些系统能够利用多台机器获得可扩展性，其性能与先进的共享内存系统 [36, 47, 49, 57] 相比却往往不尽如人意。近期的一项研究 [33] 甚至表明，经过优化的单线程实现可以胜过使用多得多处理器核心的多种分布式系统。我们的实际实验与性能分析揭示了导致性能损失的多类设计和实现缺陷，详见第 2 节。

通过性能测量和代码检查，我们认识到，传统分布式图并行系统已经不适应当今计算能力强大的多核集群节点和高速网络。为了获得更好的整体性能，系统必须同时关注计算与通信两部分的性能：在积极压缩计算时间的同时隐藏通信开销，而不能像多种现有系统那样，主要着眼于减少通信量。

为了弥合高效共享内存系统与可扩展分布式系统之间的差距，我们提出 Gemini，在效率之上构建可扩展性。本文的主要贡献如下：

- 我们详细分析了若干现有共享内存和分布式图并行系统，并识别出多项设计缺陷。
- 我们认识到，高效且可扩展的分布式图处理涉及应用特征、底层系统与输入图属性之间的复杂相互作用。为此，我们探索了多种自适应运行时选择，包括密度感知的双模式处理方案，以及多种局部性感知的数据分布和负载均衡机制。由此得到的系统在从多核到多节点的不同规模平台上都能提供有竞争力的性能。
- 我们提出了一种简单却出人意料地有效的块式图划分方案。它既能利用输入图中的天然局部性，又可无缝地进行分层细化。本文还给出了由这种新划分方式促成的多项优化。
- 我们通过大量实验评估 Gemini 原型，并与五种先进系统比较。在五个真实图上运行五种应用的结果显示，Gemini 显著优于现有分布式实现；相较其中最快的系统，性能提高 8.91—39.8 倍。我们还收集了详细测量数据，用于性能分析并验证内部设计选择。

## 2 研究动机

先进的共享内存图处理系统能够相当高效地处理图，但缺乏可扩展性，因此无法处理超出单机内存容量的图。另一方面，现有分布式方案虽然可以扩展到比共享内存系统更大的数据规模，其性能与成本效率却往往不能令人满意 [33, 59, 60]。

为了研究性能损失，我们对若干具有代表性的图并行系统进行了剖析，包括 Ligra [47]、Galois [36]、PowerGraph [16] 和 PowerLyra [12]，并以 COST 论文 [33] 提出的优化单线程实现作为参照。实验平台是一个采用 InfiniBand EDR 网络互连的 8 节点高性能集群，网络带宽最高为 100 Gbps。每个节点配有两颗 Intel Xeon E5-2670 v3 CPU（每颗 12 核、30 MB 三级缓存）和 128 GB DRAM。我们在常用于图并行系统评估的 twitter-2010 图 [28] 上运行 20 轮 PageRank [38]。

**表 1：现有系统性能分析样例（在 twitter-2010 上运行 20 轮 PageRank）。OST 指优化单线程实现。**

| 指标 | OST（1 核） | Ligra（24 核） | Galois（24 核） | PowerGraph（8 节点） | PowerLyra（8 节点） |
|---|---:|---:|---:|---:|---:|
| 运行时间（秒） | 99.9 | 21.9 | 19.3 | 40.3 | 26.9 |
| 指令数 | 525G | 496G | 482G | 7.15T | 6.06T |
| 内存引用数 | 15.8G | 32.3G | 23.4G | 95.8G | 87.2G |
| 通信量（GB） | — | — | — | 115 | 38.1 |
| IPC | 1.71 | 0.408 | 0.414 | 0.500 | 0.655 |
| LLC 未命中率 | 8.77% | 43.9% | 49.7% | 71.0% | 54.9% |
| CPU 利用率 | 100% | 91.7% | 96.8% | 65.5% | 68.4% |

总体而言，从单线程实现到共享内存实现、再到分布式实现，系统效率逐级下降。考虑到通信与同步开销、负载均衡问题以及更高的软件复杂性，这一趋势并不意外；但各系统在几乎所有测量维度上的巨大差距，说明仍有很大的改进空间。

剖析结果显示，网络远未饱和，例如 PowerGraph 的平均聚合带宽使用量低于 3 Gbps。计算而非通信，似乎才是这些分布式系统的实际瓶颈；这与近期针对分布式数据分析框架的发现 [37] 相呼应。与共享内存系统相比，分布式系统执行的指令和内存引用显著更多，访问局部性更差，多核利用率也更低。

进一步检查代码后，我们发现低效率来自多个方面：（1）使用哈希表转换全局与局部顶点 ID；（2）维护顶点副本；（3）GAS 抽象 [16] 中受通信约束的 apply 阶段；以及（4）缺乏动态调度。这些因素或者扩大工作集、产生更多指令与内存引用，或者妨碍多核 CPU 得到充分利用。

我们认为，在设计分布式图并行系统时，如果把可扩展性建立在效率之上，而不是首先以可扩展性为中心，那么上述许多副作用都可以避免。后续的分布式系统设计应密切关注当今高速互连环境中跨节点操作的计算开销，以及划分后图上的本地计算效率。

为此，我们把 Ligra 的混合推—拉计算模型改造为分布式形式，以支持高效的顶点中心数据更新与消息传递；采用块式划分方案，实现低开销图分布，并允许在多个系统层级递归应用；进一步部署多项优化，积极压缩计算时间；最后设计协同调度机制，使计算任务与节点间通信任务相互重叠。

## 3 Gemini 图处理抽象

现代集群通常由少量或中等数量的节点通过高速网络互连而成，其形态类似共享内存多核机器。Gemini 因而采用一种图处理抽象，使先进的单节点图计算模型能够平滑扩展到集群环境。下面先说明目标图处理场景。

与许多单节点 [47, 59, 60] 或分布式 [11, 18, 23, 50] 图并行系统一样，Gemini 假设图处理问题更新存储在顶点中的信息，而把边视为不可变对象。Gemini 同时处理有向图和无向图；无向图可以通过把每条无向边替换为一对有向边而转换为有向图，因此下文统一假定边为有向边。

常见图处理应用沿边传播顶点更新，直至图状态收敛或完成给定轮数。仍有更新发生的顶点称为**活跃顶点**，它们的出边共同构成待处理的**活跃边集**。

### 3.1 双重更新传播模型

在图处理的某一时刻，活跃边集可能稠密，也可能稀疏，通常由其规模——活跃顶点的出边总数——相对于总边数 \(|E|\) 的比例决定。例如，连通分量（CC）应用在最初几轮中的活跃边集很稠密；随着越来越多顶点得到最终标签，活跃边集逐渐变稀疏。单源最短路径（SSSP）则从极稀疏的边集开始；随着更多顶点被入邻居激活，边集逐渐变密；算法接近最终收敛时又再次变稀疏。

先进的共享内存图处理系统 [4, 36, 47, 57] 已经认识到，不同的活跃边集密度适合不同的更新传播模型。具体而言，稀疏活跃边集偏好**推（push）模型**：系统沿出边把更新传给邻居，只需遍历确实产生新更新的活跃顶点的出边。稠密活跃边集则更适合**拉（pull）模型**：每个顶点沿入边收集邻居状态来完成自身更新，从而显著减少使用锁或原子操作更新顶点状态时的竞争。

Ligra [47] 在共享内存机器上根据活跃边集密度自适应切换这两种模式，默认阈值为 \(|E|/20\)，Gemini 沿用该阈值。本文探索如何把这种设计扩展到分布式系统。主要差异在于，图会被划分并分布到不同节点，信息和更新必须通过显式消息传递共享。

为此，Gemini 使用与 PowerGraph [16] 类似的主本—镜像概念：每个顶点被分配给一个划分并由其拥有，在该划分中称为**主本顶点（master）**，作为维护顶点状态数据的主副本；同一顶点还可能在拥有其至少一个邻居的每个节点或划分上保有副本，称为**镜像（mirror）**。每个主本—镜像对之间会建立一对有向边，但每种传播模式只使用其中一条。与 PowerGraph 不同，Gemini 中的镜像只是更新传播的占位符，并不保存实际数据。

![图 1：稀疏—稠密信号—槽模型](https://www.usenix.org/system/files/conference/osdi16/osdi16-zhu.pdf)

借助顶点副本，Gemini 采用稀疏—稠密双引擎设计，并通过**信号—槽（signal-slot）抽象**将顶点状态传播（通信）与边处理（计算）解耦。该概念借鉴 Qt 软件框架 [1]，但含义略有不同：信号和槽分别表示用户定义的、以顶点为中心的消息发送与接收函数。

两种模式以不同方式处理计算和通信。在稀疏（推）模式中，每个主本先通过 `sparseSignal` 向自己的镜像发送包含最新顶点状态的消息，镜像再通过 `sparseSlot` 沿出边更新邻居。在稠密（拉）模式中，每个镜像先通过 `denseSignal` 根据入边邻居的状态执行本地计算，再向主本发送包含结果的更新消息；主本随后通过 `denseSlot` 适当地更新自身状态。

该抽象的一项重要特性是自动启用消息合并 [32]。每个顶点的每对活跃主本—镜像只需一条消息，消息数因而从 \(O(|E|)\) 降至 \(O(|V|)\)。它还允许系统在本地聚合向外传播的更新，无须像许多类 Pregel 系统 [3, 32, 44] 那样再执行一次单独的“合并遍历”。

### 3.2 Gemini API

Gemini 的 API 设计与共享内存系统 [47, 57] 类似，对用户隐藏数据和计算的分布细节。图以边数据类型 `E` 和若干用户定义的顶点数组完整描述。系统提供紧凑的 `VertexSet` 数据结构（内部用位图实现），以高效表示顶点子集，例如活跃顶点集。

**图 2：Gemini 核心 API。**

```text
class Graph {
    VertexID vertices;
    EdgeID edges;
    VertexID[] outDegree;
    VertexID[] inDegree;

    def allocVertexArray() -> V[];
    def allocVertexSet() -> VertexSet;

    def processVertices(
        work: (VertexID) -> A,
        active: VertexSet,
        reduce: (A, A) -> A
    ) -> A;

    def processEdges<A, M>(
        sparseSignal: (VertexID) -> void,
        sparseSlot: (VertexID, M, OutEdgeIterator) -> A,
        denseSignal: (VertexID, InEdgeIterator) -> void,
        denseSlot: (VertexID, M) -> A,
        reduce: (A, A) -> A,
        active: VertexSet
    ) -> A;

    def emit(recipient: VertexID, message: M) -> void;
};
```

用户需要提供的主要 Gemini API 代码只涉及计算任务，即 `processVertices` 和 `processEdges` 所接受的函数。下面用 CC 说明这些用户定义函数的语义。

**图 3：CC 的定义与初始化。**

```text
Graph g(...);                         // 从文件系统加载图
VertexSet activeCurr = g.allocVertexSet();
VertexSet activeNext = g.allocVertexSet();
activeCurr.fill();                    // 将所有顶点加入集合
VertexID[] label = g.allocVertexArray();

def add(VertexID a, VertexID b): VertexID {
    return a + b;
}

def initialize(VertexID v): VertexID {
    label[v] = v;
    return 1;
}

VertexID activated =
    g.processVertices(initialize, activeCurr, add);
```

我们先为当前轮和下一轮创建活跃顶点集，定义标签顶点数组，并通过一次 `processVertices` 调用，以每个顶点自身的 ID 初始化标签。随后使用经典的迭代式标签传播方法计算连通分量。

**图 4：CC 的迭代式标签传播。`OEI` 和 `IEI` 分别为出边和入边迭代器。若 \(b<a\)，`atomicWriteMin(a,b)` 以原子方式把 \(b\) 赋给 \(a\)。`swap(a,b)` 交换二者。**

```text
def CCSparseSignal(VertexID v) {
    g.emit(v, label[v]);
}

def CCSparseSlot(VertexID v, VertexID msg, OEI iter): VertexID {
    VertexID activated = 0;
    while (iter.hasNext()) {
        VertexID dst = iter.next().neighbour;
        if (msg < label[dst] && atomicWriteMin(label[dst], msg)) {
            activeNext.add(dst);       // 将 dst 加入下一轮前沿
            activated += 1;
        }
    }
    return activated;
}

def CCDenseSignal(VertexID v, IEI iter): void {
    VertexID msg = v;
    while (iter.hasNext()) {
        VertexID src = iter.next().neighbour;
        msg = msg < label[src] ? msg : label[src];
    }
    if (msg < v) g.emit(v, msg);
}

def CCDenseSlot(VertexID v, VertexID msg): VertexID {
    if (msg < label[v] && atomicWriteMin(label[v], msg)) {
        activeNext.add(v);             // 将 v 加入下一轮前沿
        return 1;
    } else {
        return 0;
    }
}

while (activated > 0) {
    activeNext.clear();
    activated = g.processEdges<VertexID, VertexID>(
        CCSparseSignal, CCSparseSlot,
        CCDenseSignal, CCDenseSlot,
        activeCurr, add
    );
    swap(activeCurr, activeNext);
}
```

图 4 给出了两对信号—槽函数所定义的每轮更新逻辑。在稀疏模式下，每个活跃顶点先从主本向所有镜像（包括主本自身）广播当前标签（`CCSparseSignal`）。镜像收到标签后遍历本地出边，并更新邻居的顶点状态（`CCSparseSlot`）。在稠密模式下，每个顶点——无论主本或镜像、活跃或非活跃——先遍历本地入边，把邻域中的最小标签发送给主本（`CCDenseSignal`）；主本收到小于当前标签的值时更新自身状态（`CCDenseSlot`）。系统使用 `add` 聚合槽函数返回值，得到本轮顶点激活总数，以判断是否收敛。

Gemini 的图划分止于处理器插槽层级。同一插槽中的核心不通过消息传递通信，而是直接更新共享图数据。因此，如示例所示，槽函数需要使用原子操作，确保顶点状态得到正确更新。

并非所有用户定义函数都是必需的；例如不存在聚合时就不需要 `reduce`。Gemini 的双模式处理也是可选的。用户可以只提供稀疏模式或稠密模式实现，尤其是在已知固定使用某种模式即可获得足够性能时（如 PageRank 使用稠密模式），或者内存只能容纳一个方向的边时。

## 4 分布式图表示

Gemini 的计算模型向用户提供完整图的统一逻辑视图，但部署在高性能集群上时，实际图必须在内部划分并分布，以利用并行性。现有划分方法包括以顶点为中心的方案 [30, 32, 48] 和以边为中心的方案（亦称顶点切分）[8, 12, 16, 24, 39]。

以顶点为中心的方案采用集中式计算模型，把顶点及其状态、邻接边等关联数据均匀分配到各划分。以边为中心的方案则把边均匀分配给各划分，并相应复制顶点。然而，第 2 节的剖析结果表明，既有研究主要围绕负载均衡和通信优化设计划分方式，没有充分关注由此产生的系统复杂性，以及划分选择对计算效率的影响。

为了在保持效率的同时获得可扩展性，我们提出一种轻量级、基于块的多层划分方案，并围绕图划分和内部表示做出多项旨在改善分布式图计算性能的设计选择。

### 4.1 块式划分

Gemini 块式划分的灵感来自许多大型真实世界图中天然存在的局部性。这些图通常通过爬取收集，相邻顶点很可能彼此邻近地存储。例如，在典型 Web 图中，URL 的字典序保证大部分边连接顶点 ID 相近的两个顶点 [7]；在 Facebook 好友网络中，大部分链接的地理位置彼此接近 [52]。即使输入数据中的局部性已经丢失，也存在有效且成本可控的方法从拓扑结构中“恢复”局部性 [2, 5]。只需付出一次预处理成本，便可让可能反复执行的图处理受益于块式划分。

在含 \(p\) 个节点的集群上，全局图 \(G=(V,E)\) 被划分为 \(p\) 个子图 \(G_i=(V'_i,E_i)\)，其中 \(i=0,\ldots,p-1\)，\(V'_i\) 和 \(E_i\) 分别是第 \(i\) 个划分上的顶点子集与边子集。为区分主本顶点与其他顶点，我们用 \(V_i\) 表示第 \(i\) 个划分拥有的顶点子集。

Gemini 使用简单的块式方案划分 \(G\)：把 \(V\) 分成 \(p\) 个连续顶点块 \((V_0,V_1,\ldots,V_{p-1})\)，块大小由本节稍后介绍的优化决定。进一步地，用 \(E_i^S\) 和 \(E_i^D\) 分别表示划分 \(i\) 在稀疏和稠密模式下使用的出边集与入边集。每个块 \(V_i\) 分配给一个集群节点，该节点拥有块内所有顶点。边按以下规则分配：

\[
E_i^S=\{(src,dst,value)\in E\mid dst\in V_i\}
\]

\[
E_i^D=\{(src,dst,value)\in E\mid src\in V_i\}
\]

其中，\(src\)、\(dst\) 和 \(value\) 分别表示边的源顶点、目标顶点和边值。换言之，第 \(i\) 个划分的出边集 \(E_i^S\) 包含目标位于其自有顶点集 \(V_i\) 中的边，而入边集 \(E_i^D\) 包含源位于 \(V_i\) 中的边。

**图 5：块式划分示例（稠密模式）。按 ID 排序的顶点数组被切分成三个块 \(\{0,1\}\)、\(\{2,3\}\)、\(\{4,5\}\)；黑色与白色顶点仍分别表示镜像和主本。**

图 5 展示了三个节点上的顶点集及相应的稠密模式边集。对于本地主本存在出边指向的每个远程顶点，系统都会创建镜像。这些镜像“拉取”本地邻居状态，以更新远程主本。稀疏模式的边集与之类似，因篇幅限制省略。

块式划分使 Gemini 能以很低的开销获得可扩展性。连续划分让顶点归属查询只需检查划分边界。每个块内部连续，也简化了顶点数据表示：每个节点仅实际访问和分配顶点数组中归自己所有的部分，并把它们置于连续内存页中。因此，内存占用易于控制，也无须通过顶点 ID 转换来压缩顶点状态空间。

推、拉两种模式访问邻居状态时都会产生随机访问，因而顶点访问局部性通常对性能至关重要。块式划分自然保留这种局部性，而随机分布容易使其丢失。此外，对顶点状态的随机访问全部落在自有块 \(V_i\)，而不是 \(V\) 或 \(V'_i\) 中。随着系统横向扩展、块大小缩小，随机访问将更容易高效处理，Gemini 也因此获益。

这种轻量级方案确实牺牲了边的均匀分布或最小割边集，但 Gemini 以三方面弥补：（1）低开销横向扩展设计；（2）保留内存访问局部性；（3）后文介绍的额外负载均衡与任务调度优化。

### 4.2 双模式边表示

Gemini 以压缩稀疏行（CSR）格式组织出边，以压缩稀疏列（CSC）格式组织入边。二者都是图系统常用的紧凑稀疏矩阵结构，便于以顶点为中心顺序访问边。图 6 使用图 5 中节点 0 上的图划分，说明与自有顶点 0、1 相邻的边如何以 CSR/CSC 表示。

索引数组 `idx` 记录各顶点的边分布：对顶点 \(i\)，`idx[i]` 与 `idx[i+1]` 表示其指向这一特定划分的出边或入边的起止偏移。数组 `nbr` 记录边的邻居，即入边的源或出边的目标。

实验与性能分析表明，基本 CSR/CSC 格式仍不够充分。随着节点数 \(p\) 增加，边存储规模按 \(O(|E|/p)\) 成比例缩小，而索引数组 `idx` 的规模仍为 \(O(|V|)\)，可能成为扩展瓶颈。例如，图 6 中的划分只有 4 条稠密模式边，却必须遍历含 7 个元素（\(|V|+1\)）的 `idx` 数组，导致对相邻顶点而非边的处理成为稠密模式计算的瓶颈。

常规解决办法是压缩顶点 ID 空间，但这需要在全局和局部状态之间转换 ID，又会给系统增加不可忽视的开销。Gemini 分别使用以下方案轻量地增强两种模式的索引数组，如图 6 所示：

- **位图辅助压缩稀疏行。** 对稀疏模式边增加存在位图 `ext`，标记每个顶点在本划分中是否有出边。例如，只有顶点 0、2、4 存在，对应位图 `101010`。
- **双重压缩稀疏列。** 对稠密模式边采用双重压缩方案 [9]，只保存有入边的顶点 `vtx` 及其边偏移 `off`；`off[i+1]-off[i]` 表示顶点 `vtx[i]` 拥有的本地入边数。例如，只有顶点 1、2、3、5 有本地入边。

两种方案都减少了边处理所需的内存访问。在必须处理本地划分全部顶点的稠密模式中，压缩索引使 Gemini 只需访问 \(O(|V'_i|)\) 个顶点索引，而非 \(O(|V|)\)。在稀疏模式中，若某顶点在本地划分没有出边，位图会避免查询其 `idx`；图被划分后，这种情况十分常见。

**图 6：使用 CSR/CSC 表示稀疏/稠密模式边的示例，高亮部分为 Gemini 的增强结构。**

### 4.3 局部性感知分块

下面说明 Gemini 如何依据局部性感知准则，在生成 \(p\) 个连续顶点块时确定 \(p-1\) 个切分位置。传统图划分通常追求顶点（顶点中心场景）或边（边中心场景）的均匀分布，以改善负载均衡。

虽然 Gemini 的块式划分以顶点为中心，但我们发现，均匀分配顶点会导致较差的负载均衡，因为大多数真实世界图的顶点度呈幂律分布 [15]；这通常被视为顶点中心方案相对于边中心方案的劣势 [16]。

然而，在块式划分中，即使让每个划分均匀包含 \(|E|/p\) 条边，仍会产生显著负载不均。深入检查发现，尽管边数相等，不同划分的顶点访问局部性差异很大，导致顶点块大小 \(|V_i|\) 差异显著。工作负载再分配等动态负载均衡技术 [26, 41] 或许有帮助，但其高成本和额外复杂性违背 Gemini 的轻量级设计。

因此，Gemini 采用局部性感知增强：以同时考虑自有顶点和稠密模式边的混合指标作为均衡标准。具体而言，顶点数组 \(V\) 的切分方式使各划分的

\[
\alpha\cdot|V_i|+|E_i^D|
\]

尽量均衡。其中 \(\alpha\) 是可配置参数；实验中的 Gemini 默认设为 \(8(p-1)\)，也可依据硬件配置、应用或输入属性调整。

这一混合指标的直觉是：计算复杂度既来自顶点，也来自边。以 \(|V_i|\) 和 \(|E_i^D|\) 描述的划分规模，不仅影响工作量 \(|E_i^D|\)，也影响内存访问局部性 \(|V_i|\)。如何分析具体系统、算法与输入特征对负载均衡的共同影响，并据此自适应划分（例如自动配置 \(\alpha\)），仍是我们正在研究的问题。

### 4.4 NUMA 感知子划分

当今高性能集群中，节点内并行规模很容易达到甚至超过节点间并行规模。例如，我们的测试平台有 8 个节点，每节点 24 核。有效利用节点内与节点间的硬件并行性，对分布式图处理的整体性能至关重要。

现代服务器大多采用非一致内存访问（NUMA）体系结构：内存在物理上分布于多个处理器插槽，每个插槽通常包含一颗多核处理器及其本地内存；各插槽通过高速互连组成全局缓存一致的共享内存系统。访问本地内存比访问挂接在其他插槽上的远程内存具有更低延迟和更高带宽 [14]，因此应尽量减少跨插槽访问。

Gemini 的块式图划分在此呈现出另一项优势：系统可以一致地递归执行子划分，并在每一层应用适合该层级的不同优化。在节点内部，Gemini 跨多个插槽执行 NUMA 感知子划分。对含 \(s\) 个插槽的节点，顶点块 \(V_i\) 被进一步切成 \(s\) 个子块，每个插槽一个；边则按照与节点间划分相同的规则分配到相应插槽。

NUMA 感知子划分显著提高了 NUMA 机器上的性能。它既保留输入顶点数组中的天然局部性，也保留轻量级划分与簿记方式。子块更小且处理更集中，因此对边的顺序访问和对顶点的随机访问都更可能落在本地内存中，同时改善内存访问速度和末级缓存（LLC）利用率。

## 5 任务调度

与大多数近期分布式图处理系统 [3, 11, 12, 16, 17, 23, 26, 32, 41, 43] 一样，Gemini 遵循批同步并行（BSP）模型 [53]。在每轮边处理中，Gemini 按环形循环顺序协同调度计算与通信任务，使节点间通信与计算有效重叠。节点内部则使用带共享预计算块计数器的细粒度工作窃取调度器，实现细粒度动态负载均衡。

### 5.1 计算与通信任务的协同调度

受 HPC 通信库中高度优化的集合操作（如 MPI 的 `AllGather`）启发，Gemini 把集群节点组织成环，以均衡的循环方式协调消息发送和接收，从而降低网络拥塞并最大化聚合消息传输吞吐量。这些经过编排的通信任务又与计算任务谨慎重叠，以隐藏网络通信开销。

在拥有 \(c\) 个核心的集群节点上，Gemini 维护含 \(c\) 个线程的 OpenMP 线程池，用于并行执行以顶点为中心的边处理，即信号和槽任务。每个线程绑定到特定插槽，配合 NUMA 感知子划分。除此之外，每个节点再创建两个辅助线程，通过 MPI 执行节点间消息发送和接收。

得益于块式划分和 CSR/CSC 边组织，Gemini 在稀疏和稠密模式下都能自然地批量组织发往同一划分的消息，实现高性能通信。批量消息也使系统能够采用简单的、以划分为单位的任务调度方式。图 7 以此前示例中第一个划分（节点 0）的稠密模式为例，展示四类任务的协同调度顺序。

一轮迭代被分为 \(p\) 个微步。每个微步中，节点 \(i\) 与一个对等节点通信，从节点 \(i+1\) 开始，最终回到自身。图 7 的示例共有三个阶段，节点 0 依次与节点 1、节点 2 和自身通信。每个微步依次执行本地 `denseSignal`、消息发送/接收和最终的本地 `denseSlot`。

例如，第一个微步中，属于节点 1 的顶点 2、3 的本地镜像，从节点 0 自有的顶点 0、1 拉取更新，形成发往节点 1 的批量消息；发送后，节点 0 等待来自节点 2 的类似批量消息，并在 `denseSlot` 中处理。下一微步中，属于节点 2 的全部本地镜像——图中只有顶点 5——以类似方式拉取更新，随后执行通信和本地处理。该过程持续到节点 0 最后与自身“通信”，此时只需从本地自有邻居拉取，例如顶点 1 从顶点 0 拉取。消息传输任务计算负担很轻，并由独立线程执行，因此通信能够有效地与计算重叠。

### 5.2 细粒度工作窃取

Gemini 的局部性感知块式划分基本保证了节点间负载均衡，但当划分从节点缩小到插槽、再缩小到核心时，顶点—边混合均衡越来越困难。划分越小，可用于调节 \(\alpha\) 以实现核间负载均衡的余地越少；顶点度方差很大的图尤其如此。

利用节点内共享内存这一节点间均衡不具备的条件，Gemini 为节点内边处理采用细粒度工作窃取调度器。系统首先以局部性感知的均衡方式，把每个插槽的边处理工作初步分给所有核心；进入 OpenMP 并行区后，每个线程一次只取得一小块顶点来执行信号/槽处理。块式划分在这一细化过程中仍保持连续处理，有利于缓存利用和消息批处理。簿记也很简单：每个核心只需一个计数器，用于标记当前微块的起始偏移；计数器由各线程共享，并通过原子操作访问。实验所用默认微块大小为 64 个顶点。

每个线程先尝试完成自己的核级划分，再从其他线程的划分窃取微块。相较从一开始就交错分配微块，这一方式利用缓存预取改善了内存访问，还把共享核级计数器上的原子加竞争推迟到整个计算的收尾阶段。此时，核间负载均衡的改进足以抵消这部分成本。

**图 8：Gemini 分块机制的层次视图。**

图 8 总结了 Gemini 的多层块式划分：从节点级、插槽级、核心级，一直到用于核间工作窃取的微块粒度。图中对应实际测试集群：8 个节点，每节点 2 个插槽，每插槽 12 核，每个微块 64 个顶点。简单的块式划分可以按层次不断细化，并在整个边处理过程中持续保持访问局部性。

## 6 实现

Gemini 以约 2,800 行 C++ 代码实现，使用 MPI 进行进程间通信，并使用 `libnuma` 完成 NUMA 感知内存分配。以下介绍若干实现细节。

**图加载。** Gemini 从输入文件加载图时，每个节点并行读取分配给自己的连续部分。边被分批顺序读入边缓冲区，并在其中完成初次遍历。与现有系统的常见做法相比，这显著降低了加载阶段的内存消耗，使系统能够加载规模接近整个集群聚合内存容量的图。对于对称图，Gemini 只保存一种模式的图拓扑数据，因为此时稀疏模式边与稠密模式边等价。

**图划分。** 加载边时，每个节点计算每个顶点的本地度数；随后通过 `AllReduce` 收集这些度数信息，按第 4 节的方法切分顶点集。各节点无须通信即可在本地确定切分位置。接着重新从文件加载边，并把边分发到目标节点以构造本地子图。

**内存分配。** 所有节点共享节点级划分边界，以支持节点间消息传递；插槽级子划分信息则仅在节点内部保存。每个节点在共享内存中分配完整顶点数组，但 Gemini 只访问自身顶点块内的数据，并把节点级顶点划分切成子块后放到相应插槽上。子划分后的图拓扑数据集——边和顶点索引——同样采用 NUMA 感知分配，以提高本地内存访问比例。

**模式选择。** Gemini 沿用 Ligra 的模式切换机制。每次执行 `ProcessEdges` 前，Gemini 先调用通过 `ProcessVertices` 接口定义的内部操作，计算活跃边数，再据此决定下一轮使用的模式。

**并行处理。** 程序初始化时，Gemini 把每个 OpenMP 线程固定到特定插槽，防止线程迁移。为支持工作窃取，每个线程维护自身状态（`WORKING` 或 `STEALING`）、当前微块的起始偏移和预计算终止偏移；其他线程可访问这些信息。它们以 NUMA 感知且对齐的方式分配，避免伪共享和不必要的远程内存访问——后者应只发生在窃取阶段。每个线程从自己的划分开始工作，完成后改变状态，并按循环顺序尝试从编号更高的线程窃取工作。并发控制由 OpenMP 的隐式同步机制完成。

**消息传递。** Gemini 在每个节点运行一个进程，使用 MPI 完成节点间消息传递。在插槽间层级，每个插槽通过共享内存中的插槽专用发送和接收缓冲区生产或消费消息，从而避免额外内存复制，并进行 NUMA 感知的消息批处理。

| SSSP | **2.81** | 3.33 | 3.29 |
| BFS | **0.347** | 0.528 | 0.468 |
| BC | 2.45 | 3.94* | **1.88** |

尽管带有为分布式执行设计的通信复杂性，Gemini 在 PR 和 BC 上仍优于 Ligra 与 Galois，在 CC、SSSP 和 BFS 上居第二。NUMA 感知子划分使边处理受益于更快的内存访问和更高的 LLC 利用率，因为远程内存访问显著减少。Ligra 和 Galois 的访问模式不感知 NUMA；Gemini 的线程则只会在工作窃取和消息传递时访问远程内存。

与此同时，分布式设计不可避免地引入额外开销。消息抽象——即信号产生、槽消费的批量消息——会增加内存访问。对 BFS 这类计算不密集的应用，这成为主要性能约束：算法计算量很小，而访问边和生成消息的数量都是 \(O(\sum |V_i|)\) 量级。[^3] 相比之下，多数其他应用访问每个活跃顶点的全部邻接边，边处理成本与活跃边数成正比，足以掩盖消息生成开销。

共享内存系统通过直接访问获得邻居最新状态，而 Gemini 基于 BSP 的通信机制只能以超步粒度通过消息传递取得邻居状态。因此，在 CC 和 SSSP 这类基于标签传播的应用中，Gemini 的顶点状态传播落后于共享内存系统，所需迭代次数也多于 Ligra 和 Galois。

[^3]: 在 BFS 的稠密模式中，只要某顶点成功从任一邻居“拉取”，该顶点的边处理即告结束 [4]。

总体而言，Gemini 只付出相对较低的分布式执行支持成本，却能够通过增加节点来处理大得多的图，并在单节点多核机器上高效运行，从而适应多种应用—平台组合。

### 7.2 可扩展性

我们先考察节点内可扩展性：使用 1—24 个核心在 twitter-2010 上运行 PR（图 9）。总体可扩展性良好，使用 2、4、8 核时加速比分别为 1.9、3.7 和 6.8。随着核心数增加，核间负载均衡更困难，同步开销更明显，内存带宽和 LLC 竞争也更激烈；即便如此，Gemini 在 12 核和 24 核时仍分别达到 9.4 和 15.5 倍加速。

### 7.3 设计选择

下面评估 Gemini 若干主要设计选择对性能的影响。虽然比较各项优化的相对重要性很有吸引力，但我们发现难以分离单项技术的贡献，因为它们往往相互促进，例如块式划分与节点内工作窃取。此外，若在基线系统上逐步叠加优化，测得的表观收益高度依赖叠加顺序。因此，以下分别展示和讨论各项设计决策的优势，结果并不代表其相对强弱。

#### 7.3.1 自适应稀疏—稠密双模式

根据活跃边密度在稀疏与稠密模式间自适应切换，显著提高了 Gemini 的性能。为了说明双模式抽象的必要性，我们强制 Gemini 在每一轮分别以两种模式运行。

图 11 显示，三种应用在稀疏与稠密模式下的性能差距都很明显。PR 始终是稠密模式更快。CC 在最初几轮大部分顶点仍活跃时，稠密模式更好；随着更多顶点收敛，稀疏模式更有效。SSSP 在大多数轮次中稀疏模式优于稠密模式，只有一段大量顶点发生更新的轮次例外。

Gemini 能在绝大多数轮次中选择更好的模式；CC 的 76 轮中仅误选 2 轮，SSSP 的 172 轮中仅误选 5 轮。这些“误预测”只带来轻微次优结果，并且如预期那样发生在两种模式性能曲线的交点附近。

**图 11：Gemini 在稀疏与稠密模式下的逐轮运行时间（uk-2007-05）。红色区域表示自适应引擎选择了次优模式的轮次。**

#### 7.3.2 块式划分

我们通过与基于哈希的划分比较，考察 Gemini 块式划分的有效性。[^4] 图 12 给出两种方法在 twitter-2010 和 uk-2007-05 上运行 PR 的表现，这两个图分别代表社交图和 Web 图。

[^4]: 我们把哈希方案集成到 Gemini 中：先按哈希结果重新排列顶点，再进行分块；顶点 \(x\) 被分配给划分 \(x\bmod p\)。

Gemini 的块式划分在两个图上都胜过哈希划分，在 Web 图 uk-2007-05 上尤其显著，速度提高超过 5.44 倍。原因在于块式划分能够保留局部性，而哈希划分会丢失原图的天然局部性。因此，后者不仅产生更高的 LLC 未命中率，还会在每个划分中产生大量镜像，从而增加主本—镜像消息传递和顶点索引访问的通信成本与内存引用。

## 8 相关工作

前文已经讨论并评估了若干关系最密切的图并行系统，本节简要概括相关研究类别。

人们已经提出大量图并行系统 [3, 10, 11, 12, 16, 17, 21, 22, 23, 26, 29, 30, 32, 36, 41, 42, 43, 44, 47, 49, 55, 56, 57, 59, 60]，以高效处理规模不断增长的图。Gemini 在多个方面受到先前系统启发，但它以整体视角进行系统设计，同时追求单节点效率和多节点可扩展性，因而与这些系统不同。

**推与拉。** 现有分布式图处理系统或者采用推式模型 [3, 26, 32, 43, 44]，或者采用拉式模型 [11, 12, 16, 17, 23, 30]，也有系统同时提供两者但分别使用 [13, 19, 22]。共享内存方案 [4, 36, 47, 57] 已表明，自适应组合推、拉操作非常重要。Gemini 通过信号—槽抽象把通信与计算解耦，将混合推—拉模型从共享内存扩展到分布式内存环境；在分布式图处理领域，这是一项新设计。

**数据分布。** 传统图划分研究 [8, 12, 16, 24, 25, 30, 32, 39, 48] 主要关注降低通信成本和负载不均，没有充分重视划分给分布式图处理带来的额外开销。受若干单节点图处理系统 [29, 42, 49, 57, 60] 的实现启发，Gemini 采用块式划分，实现低开销横向扩展。将分块方法用于分布式环境时，我们通过进一步优化解决顶点索引稀疏、节点间负载不均和节点内 NUMA 等新问题，以加速计算。

**通信与协调。** GraM [55] 设计了高效的 RDMA 通信栈，使通信与计算重叠并获得可扩展性。Gemini 借鉴 MPI 集合操作的实现 [51]，以面向划分的环形顺序协同调度计算与通信任务，不依赖 RDMA 也能达到相似目标。PGX.D [22] 强调节点内负载均衡对性能的重要性，并提出边分块方法。Gemini 将块式核级工作划分集成到细粒度工作窃取调度器中，扩展了这一思路，从而获得更好的多核利用率。

此外，还有许多系统专注于大图上的查询处理 [40, 46, 54]、时序分析 [13, 19, 27, 31]、机器学习与数据挖掘 [50, 58]，或更一般的任务 [34, 35, 45]。探索如何把 Gemini 以计算为中心的设计应用于这些系统，将是一项有意义的工作。

## 9 结论

本文研究了以计算为中心的分布式图处理。围绕提高现代多核集群节点上的计算效率这一主题，我们重新设计了图划分、图表示、更新传播、任务与消息调度、多层负载均衡等关键系统组件。

系统开发与评估揭示出两点：（1）要有效利用系统资源，必须把低开销分布式设计建立在优化后的单节点计算效率之上；（2）跨多个并行层级保留数据局部性的低成本块式划分表现出乎意料地好，并为系统各处的后续优化创造了大量机会。

与此同时，通过评估 Gemini 和其他开源图处理系统，我们注意到，性能、可扩展性和瓶颈位置高度依赖算法、输入图和底层系统之间的复杂交互。论文——包括本文——报告的多个备选系统之间的相对性能结果，换用不同平台配置或输入图后有时无法复现。这也凸显了自适应系统的必要性：系统应依据应用、数据和平台的动态行为定制决策。
