## 1. 目标与设计结论

LLM 提交自然的数学推导；代码负责解析、识别依赖、验证每个关系，并生成可回放证书。合法推导不应仅因为证明器先尝试了昂贵路径而频繁失败，也不应要求 LLM 在每个 Method 中重复已经证明的条件。

本设计作出六个决定：

1. **已验证事实属于有效 Scope，不属于某个 Method 的私有知识。** 来源 Method 保留在证据中，但不能成为复用障碍。
2. **事实库与搜索上下文分离。** 事实库保存已验证知识；一次证明只检索相关事实，不能把全部历史关系塞入多项式归约。
3. **事实复用与输入绑定分离。** 辅助前提允许代码检索；target、StateVersion、previous_bound 等计算输入仍准确绑定，不能由搜索替换。
4. **搜索与检查分离。** 策略负责提出候选证明；小范围、确定性的规则检查器决定证明是否成立。回放不调用搜索。
5. **搜索采用显式阶段、确定性排序和分支预算。** 不继续以大型函数中新增分支的位置表达优先级。
6. **事实发布与 Runtime 事务、依赖图和 Retry 一致。** 未提交、不可见、来自未来或过期版本的结果都不能成为前提。

非目标：自动规划完整解题路线、通用定理证明、无限代数搜索、自动求解所有取等方程、靠数值抽样接受结论、把自然推导改成由 LLM 输出内部证明指令。有限能力仍可能返回未证明；必须区分数学错误、能力不足和资源耗尽。

## 2. 现状与问题

### 2.1 已有机制

- `math_kernel/expression_parser.py` 与 `derivation_math.py` 保存表达式、关系角色、原文及位置。
- `proof_kernel.py` 提供 `ProofContext`、有限规则、搜索、精确算术预算和 `replay_proof`。
- `_Search.need()` 处理定义域、递归、循环和成功证明缓存；规则节点在构造时检查。
- `_replay()` 使用 `_Environment` 检查证书，不重新运行 `_Search`。
- Runtime 已有 Scope 可见性、准确输入绑定、事务提交、StateVersion 和 checkpoint/Retry。
- M11/M12/M13 通过准确前序结果传递界、证书和累计取等条件。

### 2.2 当前不足

| 问题 | 现状 | 目标 |
|---|---|---|
| 搜索顺序 | `_Search.core()` 集中了约 640 行条件和循环 | 策略注册、分阶段调度、明确适用条件 |
| 成本控制 | 分支共享预算；`proof_limit` 直接向上传播 | 分支配额与总预算分开，有限回退 |
| 知识复用 | 主要是当前输入、原条件、显式前序界及当前推导前缀 | Scope 内经授权的已验证事实视图 |
| 前提选择 | 验证链不断累积关系，部分路径超限时再裁剪 | 按目标检索、按实际依赖组装证书 |
| 诊断 | 经常只剩最终的预算或证明失败 | 记录策略、子目标、依据和各项消耗 |

另有两处必须与共享证书一起迁移的实际耦合：`inequality_bound_v2.py` 的 `check_local_contract` 和最终 `pairs` 收集都扫描 `math.two_term_amgm` 节点；后者按不同参与项对去重并要求恰好一对，并非已有独立的“本次应用”模型。`runtime/inequality_teaching_evidence.py` 同样扫描 `derivation.proofs[].nodes` 生成 `local_relations`。第 10.1 节定义替代协议，第 13、15 节列出强制接入点；不能仅改证书存储而保留这两个消费者。

## 3. 总体架构与职责

```text
Authenticated ProblemIR                  已提交的 Method 执行证据
          │                                        │
          └────────── Fact Admission ───────────────┘
                                │
                   Scoped Proof Fact Store
                                │
             Scope + 依赖 + 版本过滤的只读快照
                                │
当前 Method 准确输入 ──→ Proof Session ←── 自然推导解析结果
                                │
                       Relevant Fact Retriever
                                │
                       Proof Search Scheduler
                                │
                 Candidate DAG → Certificate Checker
                                │
                  Method Contract / Runtime checks
                                │
                      原子提交输出与事实增量
```

### 3.1 Runtime 层

Runtime 负责身份、授权和生命周期：从 authenticated 题设接入原条件；从成功执行的证书接入派生事实；在调用前创建只读视图；在提交时发布事实增量；在 Retry 时恢复或作废依赖。

共享数学事实是现有 Runtime 已验证状态的证据索引，不建立第二份自行决定身份与权限的 Context。索引可从题设和已提交证据重建；不能通过写入索引绕过现有提交和 promotion 权限。

### 3.2 Method 层

Method 保持 `run(resolved_typed_inputs, kernel)`，不直接读取 RuntimeContext、搜索 handle 或选择最新状态。Executor 通过内部执行服务传入冻结的 `ProofEnvironmentView`；具体可经现有 kernel 服务接口承载，但不能成为 LLM 参数。

Method 声明可消费的辅助事实种类、要证明的关系、核心操作契约、允许发布的证据类型；数学检查结果不直接提交。

### 3.3 数学内核层

只消费身份已解析的符号、关系、前提与证明引用；不理解题号、Planner prompt、页面或 Runtime 路径。内核证明结果返回实际读取依赖、证书和诊断，交 Runtime 校验后提交。

## 4. 事实模型

以下为目标内部模型，不是现在已有的序列化 schema。

```text
VerifiedMathFact
  fact_id                    # 该声明及其证明身份
  statement_key              # 结构规范键，用于检索；不表示任意代数等价
  relation_ast
  symbol_bindings[]          # MathObject/换元符号的确切身份
  validity
    scope_id
    assumption_refs[]       # 成立所需的分支假设
    definition_refs[]       # 依赖的换元/定义身份
    state_version_refs[]    # 若依赖版本化表达式
    witness_ref?            # 若仅在某个见证下成立
  semantic_kind             # domain / identity / definition / bound / relation / witness
  source                    # ProblemIR fact，或 producer call + 源位置
  proof_ref?                # 原题条件由可信输入来源授权；派生事实必须有证明
  dependency_fact_refs[]
  publication_scope
  commit_id
```

### 4.1 事实身份与去重

- 相同显示名称不代表相同符号；不同小问的 `a` 或两次换元的 `u` 不合并。
- `statement_key` 可使用已有安全结构规范化，例如有声明依据的交换律键；不得通过约分丢失原始分母义务。
- 数学内容相同而来源、假设或定义域不同的声明可以共存。索引归组，证书保留具体来源。
- 代数等价关系的合并必须有证明，不能仅凭 SymPy 简化结果授予事实身份。
- 同一关系的多个证书按已获授权、依赖规模、已测成本、稳定 ID 确定性选择。不能把较弱假设的证书与较强假设的证书混同。
- 本设计首批不进行任意假设集合的逻辑包含搜索；优先使用相同假设身份或当前分支显式包含的假设。

### 4.2 取等条件单独建模

“应用基本不等式时等号成立当且仅当两项相等”是一个带作用对象的条件，不是已经成立的全局等式。

```text
AttainmentRequirement
  bound_ref
  application_ref
  required_relation
  characterization_proof_ref
```

例如 `b=a-b` 以 AttainmentRequirement 保存，不能作为通用关系加入事实检索。M13 创建见证上下文后可以验证它；见证成功也不将它提升为原题所有取值下成立的关系。

### 4.3 现有局部前提的迁移分类

下表是首批证据适配器的审计清单。名称用于定位现有代码，不是依靠字符串前缀决定发布权限；实际分类必须由构造位置、生产证书和传递依赖确认。`semantic_kind` 由关系用途确定；“已验证”不等于“无假设”。

| 现有命名空间 | 性质与 semantic_kind | validity / 发布规则 |
|---|---|---|
| 原题条件、M01 绑定条件 | authenticated relation / domain | 保留原 Condition、Scope；条件列表本身不授予新权限 |
| `bound:previous` | 已验证的 `bound` | 准确 target、前序 StepResultRef、原条件、定义和版本依赖；可发布，但消费界仍需准确绑定 |
| `substitution:definition:{name}` | 保守定义，新增 `definition` kind | 新鲜符号、定义表达式的域及 `definition_refs`；只在获准的定义环境内共享，不作为普通无依赖恒等式 |
| `substitution:verified:{i}` | 已验证 relation / identity / domain | 继承原题与换元定义依赖，绑定准确 substitution 证据；逐条分类后发布 |
| `substitution:domain:{i}` | 非等式已验证关系，可能是 domain 或一般 relation | 当前代码按 `op != '='` 选取，不能因名字带 domain 就把所有记录当域事实；保留实际证明与定义依赖 |
| `elimination:row:{i}` | 当前 M08 验证序列的局部关系 | 提交前仅会话内；需从完整证据找到生产证明，提交后依关系类型与假设决定可否发布 |
| `elimination:{i}` | 已证明的还原等式、关系及输出域事实 | 绑定准确 elimination/substitution 结果与原条件；域结论也须指向证明节点，不能仅凭重算 `domains()` 认定已证 |
| `quadratic:verified:{i}` | 系数正性、域、配方恒等式及下界 | 按实际关系分成 domain / identity / bound / relation；保留 source、目标版本和前序界依赖 |
| `attainment:reference` | 为验证取等刻画而引入的临时假设 | 仅本次取等刻画子上下文可用；不发布为全局事实，结果进入 AttainmentRequirement 证据 |
| `solution_case` | M13 分支假设 | 保留 branch assumption identity；首批只在分支会话中保留，不发布到共享库 |
| `shared_solution:{i}` 与取等联立推导中的中间关系 | 在取等假设下验证的关系 | “shared”只表示若干取等分支共用，不代表题目 Scope 的无条件事实；首批留在 M13 局部证据 |
| `derivation:{i}`、`bound:row:{i}` 等通用序列键 | 已验证前序行，具体性质不由键决定 | 继承全部假设、定义和版本；不得把所有前序行统一提升 |

阶段 A 须产出可机读的构造点清单（构造函数、上下文、生产证书位置、角色和现有预算 profile），阶段 C 的适配器逐项消费。未知构造点默认不可发布，不能兜底成 `relation` 后放行。M07 的“仅通过定义改写目标”等子任务还须使用受限事实视图，防止共享原条件等式越过 M07/M08 的职责边界。

## 5. Scope 可见性与执行可读性

**数学上在哪成立、Runtime 是否允许读取、在当前执行位置是否已经可用，是三个独立条件，必须同时满足。**

### 5.1 可见性规则

| 来源 | 当前调用能否使用 |
|---|---|
| 当前题目/小问及其可见祖先的原条件 | 可以，由原题身份授权 |
| 同一有效 Scope 内此前成功发布的无额外假设关系 | 可以，仍检查执行依赖与版本 |
| 祖先 Scope 发布的关系 | 按现有父链可见性继承 |
| 子 Scope 的关系 | 默认不可以；需要明确 promotion 及假设处理证明 |
| 兄弟小问或互斥分支的关系 | 不可以 |
| 当前 Method 中已验证的前序推导行 | 当前 Proof Session 可用，调用提交前不对外发布 |
| 未验证的 ∵/∴、未来推导行、失败调用产物 | 不可以 |
| 仅在某组赋值下成立的见证关系 | 仅匹配的见证上下文可用 |

不能仅把 step Scope 改成 question Scope 就提升事实权限。Runtime 中现有事实可见性见 `runtime/context.py:is_visible`；新索引必须复用同一身份与授权体系。

### 5.2 同 Scope 的独立调用如何共享

首批采用**确定性的执行前缀快照**：在当前 Scope 的 canonical 步骤顺序中，仅允许读取排在当前调用之前、成功提交且获准发布的事实。跨 Scope 仍遵守父链可见性。候选步骤的顺序来自已有 canonical 结构，不按实际完成时间排序，也不改变显式参数绑定。

这为同 Scope 内未显式写辅助事实引用的调用提供复用机会，同时不允许后续调用反向供给前提。实际读取后记录 `proof_reads` 边，必须指向合法的前驱，加入 Runtime 依赖闭包。

现有调用执行路径按 canonical 顺序串行执行；首批保持这一约束，不需要实施“从并行改回串行”。其他不消费此视图的执行路径保持现有行为。若将来新增调用级并行，应按预定快照屏障或确定性依赖执行；不能“哪个先完成就读哪个”。

显式 DAG 与前缀顺序若存在冲突，在准备阶段拒绝并诊断，不临时改变输入或读取未来结果。独立失败调用没有事实可发布；不依赖它的调用仍可执行。

### 5.3 动态证明依赖不能成为隐藏依赖

新增的 `proof_reads` 是辅助数学前提读取，不替代 `StepResultRef`。它必须进入：

- call commit manifest 与依赖图；
- goal-reachable 执行证据闭包；
- checkpoint/restore 兼容性检查；
- ExplanationSnapshot 的证据来源；
- 离线 replay bundle。

下游因读取某事实而依赖其 producer 时，该 producer 必须纳入可回放的实际执行闭包，不能在最终聚合时被当成“无用步骤”删除。

## 6. 事实接入、事务和 Retry

### 6.1 原题条件接入

只从 authenticated ProblemIR 的真实条件接入，保留 Condition identity、Scope 与来源。题目目标、待证结论、gold answer、静态页内容不能作为条件接入。

当前 `_check_context()` 进行有限矛盾检测，包括可归约为假的常数关系、差式成比例且符号相反的关系、空区间；它不只是字符匹配，但也不是一般可满足性判定。检测到矛盾即报告 `inconsistent_premises`，不设置“矛盾即可推出任意目标”的规则；**这不保证未检测到的不一致前提下不会经合法代数规则推出荒谬结论**。内核证书只证明“当前提都真时结论成立”，不能证明这些前提存在共同解。

共享派生事实仍是依赖原前提的条件性结论，必须保留依赖，不能把它们重新根定为独立公理。题设或分支的相容性状态可以保持 unknown；检索扩大事实范围不能将其改为 satisfiable。

最值闭合的保障来自 M13 对完整见证的检查：具体取值必须同时满足全部原始条件、分母及根式域、累计取等关系和原目标值。这既验证可达性，也提供原题条件相容的存在性证据。见证必须在原始条件上验证，不能只检查裁剪后的搜索上下文。若没有见证，最多得到条件性的界，不能宣称最值；其他需存在性的闭合能力应有各自的见证/存在性契约，不能依赖有限矛盾检测代替。

### 6.2 派生事实发布

每个 Method 的证据适配器返回 `VerifiedFactDelta` 候选，逐条指向已检查的 proof root 和源推导行。Runtime 完成 Method 契约、输出、闭合和版本检查后，才原子提交输出与事实增量。

可发布的内容：经过验证的学生推导行、Method 的正式结论、实际成功证明 DAG 中必要的定义域关系。是否可共享由有效假设和 publication policy 判断。

publication policy 由 Method 的内部能力声明和 Runtime authority 共同确定，不由 LLM 填写，也不由 Method 自行选择父 Scope。接入检查按以下顺序执行：

1. 确定当前 canonical call 获准发布结果的逻辑 Scope；只在临时 step 内有权限的内容保持局部。
2. 沿证明依赖收集全部未解除假设、换元定义、符号和 StateVersion，不能只看最终等式中出现的变量。
3. 确认这些依赖在拟发布 Scope 有效；临时假设未解除时，保留分支限定，不提升为父级无条件关系。
4. 对获准共享的关系生成事实增量，对其他关系仅保留局部证据；身份不完整或授权冲突直接拒绝发布。

首批无需新增一般假设消解定理。没有已有规则证明可以解除的假设，继续作为事实有效性的限制。Method 的新事实发布声明必须随能力注册接受检查，不能默认为所有输出开放父级写权限。

不发布：搜索尝试中的候选、未被接受分支的临时事实、纯猜测的符号、只在见证下成立却没有 witness 标签的关系。初期不把全部内部搜索节点持久化成可检索事实，防止知识规模随试探次数增长。

### 6.3 事务生命周期

1. 从已提交状态创建不可变 `FactSnapshot`。
2. 当前调用持有私有 `SessionFactOverlay`；每行验证成功后才能加入。
3. 搜索分支使用自己的候选节点区；失败可回滚节点，但已消耗的预算不返还。
4. Method 全部验证后提交输出、事实增量及实际读取依赖；任何一步失败，全体回滚。
5. 其他调用只能读取新的已提交快照，不能读取 overlay。

### 6.4 Retry 与缓存失效

重试不复用上一轮内存中的“已证明”标记。保留的 producer 需满足既有恢复签名、准确输入版本、Scope 和依赖兼容性；其证书验证通过后才能重建索引。

producer、条件、换元定义或版本变化时，沿 `proof_reads` 和原有依赖边使下游证据失效。取消提交或替换 Scope 时，同时撤销对应事实的可见性。

检索与成功证明的直接缓存键都显式包含可用事实快照的 `committed_manifest_hash`，再包含目标结构、符号身份、有效假设、定义/状态版本、实际依赖指纹、条件解析协议版本和规则集版本；搜索产物另记录 SearchPolicy 版本。实际依赖指纹不能代替可用快照指纹：相同目标在不同快照中可能得到不同证明。

跨快照只能作为显式的证明导入：逐项校验依赖在新快照中的授权与版本，再重建本次局部上下文及外层导入记录，经 checker 验证后生成新快照缓存项。写入证据的局部 context hash、前提表及外层 manifest 必须与本次回放环境相符；不得把旧快照证书仅改 hash 后当作新证书。原始证书可作为带原环境的依赖片段保留。失败缓存仅允许记录固定环境下可确定的“不适用”；循环阻断、局部超限和不完整搜索的失败不能永久缓存成“不可证明”。

## 7. 相关事实检索

### 7.1 索引

至少建立：关系结构键、关系类型、表达式子树、符号身份集合、正性/非零关系、孤立变量等式、目标与版本身份、producer/依赖反向索引。

符号重合只用于排序，不构成可见性或正确性依据。定义域事实优先按完整子表达式匹配，例如 `a-b>0`，不能只索引单个变量正性。

### 7.2 查询流程

1. 固定授权快照，过滤不可见、假设不满足、版本不匹配或未来事实。
2. 查询与当前关系完全匹配的证书。
3. 查询当前 AST 子表达式的正性、非零和已知等式。
4. 按策略声明补取特定关系，例如单调性所需的分母正性。
5. 仍不足时，按稳定顺序有限扩大候选集；返回检索截断原因。

不一次性枚举所有前提组合，也不把全部相关等式交给归约器。每个候选证明明确列出拟使用的前提。

### 7.3 大事实库与小证明上下文

`ProofLimits.premises=16` 只是默认值，并非所有路径的现行上限。`elimination_context()` 已使用 48，`substitution_context()` 已使用 64，且连同归约、节点和尝试上限一起扩展。这反映了当前将累积关系装入局部上下文的做法；阶段 A 必须记录各入口的有效 profile 及覆盖/嵌套规则，不能只用默认 16 做性能基线。

这些局部限制不应成为整题事实库容量。迁移初期兼容各入口现有 profile，不强行把 48/64 降为 16，也不为新失败自动上调。目标是每个证书片段只带必要前提，通过依赖 DAG 连接已验证片段；是否收紧 profile 在基线比较后单独决定。

事实总数、检索候选数、证明 DAG 总大小分别设有限额。不会通过拆成多个片段绕过全局工作量与回放预算；超限时报告具体维度。

## 8. 分层搜索调度

### 8.1 策略接口

```text
ProofStrategy
  strategy_id
  phase
  supported_goal_kinds
  match(goal, view) -> NotApplicable | CandidateDescriptors
  propose(candidate, view, budget_slice) -> CandidateProof

CandidateProof
  rule_id
  conclusion
  premise_refs[]
  subgoals[]
  certificate_data
  estimated_cost_class
```

`match` 只做有界结构检查，不得隐藏高成本代数运算；所有实际计算计入预算。策略不可直接返回“可信成功”，必须经 checker 验证。注册表决定阶段和适用类型，不允许方法实现靠新增一个更靠前的分支改变全局优先级。

### 8.2 阶段与顺序

| 阶段 | 内容 | 约束 |
|---|---|---|
| S0 已有证明 | 原条件、当前已验证行、Scope 证书引用 | 精确身份和完整依赖检查 |
| S1 结构规则 | 正负乘除、幂、平方非负、已知非零、简单关系弱化 | 优先直接操作数事实，不进行无关等式改写 |
| S2 简单等价传递 | 公共项抵消、显式局部替换、已知恒等式、同差关系复用 | 定义域保留；需要代数检查的操作全部计费 |
| S3 专门数学规则 | 二项 AM-GM、倒数单调性、平方相等与符号约束、已知区间上的二次式界 | 模板匹配后提出有限子目标 |
| S4 有限代数兜底 | 多项式证书、有限代入、受限前提组合 | 限制候选数量、深度、次数与归约成本 |

不是每个目标都走完五阶段。策略必须按关系形状筛选；等式无需尝试 AM-GM，符号目标首先找操作数符号。

初始排序固定为 `(阶段, 成本等级, 子目标数量, 依赖数量, strategy_id, candidate_key)`；记录在版本化 SearchPolicy 中，不能依赖哈希遍历、线程完成时间或题号。调优依据冻结样本，不在线学习或随机改序。

### 8.3 递归调度与定义域

目标及其定义域义务组成任务图。先识别候选证明与其必要定义域，再按已有事实和低成本子目标推进；任何结论在全部原始定义域义务满足前都不能被接受或供其他步骤使用。

不得因“等式约分后没有分母”跳过原式定义域，也不得用尚待证明的结论证明自身分母非零。活动目标键包括目标、假设环境与授权快照；遇到循环仅阻断当前候选。

候选搜索采用确定性工作队列与有限回溯。一个候选递归产生的子目标继续受候选配额及全局预算约束，不能无限展开后才尝试同层其他候选。

### 8.4 缓存与证明检查

已验证子目标在会话内共享，且带真实依赖。策略构造的 proof node 必须先检查才能作为成功结果缓存。导入共享证明需验证其依赖已在本快照授权；本进程已按相同指纹校验的内容可使用校验缓存，独立回放仍能从证据完整验证。

搜索发现证明不代表 Method 契约已通过；两者按第 10 节分别检查。

## 9. 预算与诊断

### 9.1 三种资源边界

- **输入/结构上限**：AST 深度、系数大小、次数、变量数量等。非法输入或超出声明能力应明确拒绝。
- **搜索工作量上限**：检索候选、策略尝试、代数归约、任务展开。由一个 Proof Session 统一计费。
- **最终证明与回放上限**：证书节点、依赖深度、证据体积与精确校验工作量。独立计量，不能靠缓存或切片无限扩大。

长推导中出现很多简单关系，不等同于单个代数问题复杂；两者分别计数。关系条数与单证书前提数不应混为一个限制。

### 9.2 分支配额

候选开始前分配有限配额。进入昂贵阶段时为其他候选保留额度；未使用额度可归还，已经发生的运算始终记入总账。切换候选或回溯不重置总计数。

局部配额耗尽返回 `strategy_budget_exhausted`，可以尝试其他候选。真正全局耗尽返回 `proof_search_exhausted`。某候选的结构过大可标记不可用并尝试其他候选；原输入本身超限不能伪装成策略不适用。

初始全局算术上限沿用相应入口实际生效的 profile（包括消元和换元的覆盖值），不是统一套用默认 ProofLimits。阶段 A 同时记录前提、变量、等式、归约、节点和尝试等配置及实际开销。分支配额及候选数在离线基线阶段固定、版本化并写入报告，不凭 q30 临时增大。若保留原总限无法覆盖既定范围，必须通过基准明确区分算法低效与能力范围不足后再评审调整。

### 9.3 搜索轨迹

每次证明至少记录：目标源位置、环境快照、候选策略、实际前提、产生的子目标、命中缓存、拒绝原因、各预算增量、最终依赖及证书。失败路径保留摘要；完整轨迹为受限调试产物，不能使日志本身无界增长。

诊断区分：

| 内部结果 | 给 Planner 的含义 |
|---|---|
| 缺少可证明的域/正性 | 指出具体分母或正项及可见条件，不要求内部 fact ID |
| 能验证为错误的关系 | 指出该行关系为何不成立 |
| Method 核心操作不匹配 | 指出本次允许的操作和发生的额外转换 |
| 有限策略未找到证明 | 说明尚未证明，不断言数学错误 |
| 搜索资源耗尽 | 标记验证器资源限制，不归咎于 LLM 数学错误 |
| 版本/作用域/证书无效 | 标记执行或证据错误，不能通过改写措辞绕过 |

内部资源失败优先进入工程诊断；如果仍允许 Planner 补充中间关系，应说明这是帮助验证而非纠正数学错误。Runtime 不偷偷更换 Method 或模型。

## 10. 与 Method 契约的关系

不能泛化成“每个 Method 只允许一行或一次变换”。不同 Method 的核心职责不同：

| Method | 可做的工作 | 不能因共享事实而绕过的边界 |
|---|---|---|
| M01 | 多行恒等整理、局部恒等式和整体总结 | 必须连接准确的原目标/当前版本；不把不等式写成等价 StateVersion |
| M11 | 一次双项 AM-GM，必要的恒等变形、缩放与单调传递 | 其余项保持；不能顺便删独立平方项 |
| M12 | 对指定变量验证一次参数二次式配方下界 | 系数正性、恒等式、余项独立性和取等关系都要验证 |
| M13 | 联立累计取等条件并验证完整见证 | 不能将见证值作为全局前提，不能遗漏原始条件和定义域 |

必须区分两类输入：

- **计算对象输入**：target、expression 的准确 StateVersion、previous_bound 的 StepResultRef、substitution 等，仍由 typed binding 决定。
- **辅助证明输入**：已证明的正性、非零、恒等式、关系等，由授权事实视图提供。

即使事实库中已经有 `F≥4`，当前 M11 也不能只引用它就宣称完成了一个新的 AM-GM 应用。应用契约由 submitted relation 与准确输入确定的应用证据验证；不能按搜索内部 AM-GM 节点总数计算本次应用次数，也不能把旧应用当新应用。

跨 Method 使用界必须保留原目标、准确前序界、方向及累计取等条件。辅助事实检索不能取代已有 `AmgmBound / QuadraticBound` 消费协议。

### 10.1 本次 AM-GM 应用证据与教学投影

现行 `inequality_bound_v2.verify()` 在两处依赖搜索实现细节：`check_local_contract` 扫描新生成证书中的 AM-GM 节点做早期契约检查；验证序列之后又从所有节点收集参与项对，要求 `len(pairs)==1`。共享证书内联会把旧应用混进来，引用而不内联又可能失去可识别节点。因此这两处都要迁移，不能仅过滤一部分节点作为长期方案。

新增独立的本次应用记录，作为第 12.4 节 Method 应用契约接口的 M11 实现，概念模型如下：

```text
VerifiedAmgmApplication
  application_id              # 当前 call 内的操作事件，不是数学定理的新颖性标志
  producer_call_id
  target_ref
  source_state_or_bound_ref   # 当前调用的准确计算输入
  submitted_relation_origins[]
  participating_terms[2]
  local_rule_relation        # 当前二项基本不等式的规范关系
  local_rule_root_ref         # 本次局部规则检查根
  positivity_proof_refs[]
  domain_proof_refs[]
  effect_proof_refs[]         # 恒等改写/倒数/缩放/余项保持至完整结论
  conclusion_ref
  attainment_requirement_ref
```

识别和验证流程：

1. 从提交关系及准确 source→conclusion 的局部变化提出参与项候选，不从整棵依赖 DAG 寻找任意 AM-GM 节点。允许直接公式、局部倒数传递和此前支持的等价写法，不要求 LLM 增加内部字段。
2. 对候选构造调用局部的二项规则根，显式验证两项、正性、域和公式；前提可引用历史证书，核心规则由 checker 确认。即使底层节点按内容去重，本次 application anchor 仍指向当前 call 的提交关系和准确输入。
3. 检查局部根经允许的恒等/单调转换形成完整结论，且其余项保持；独立平方项的丢弃仍属于越界。
4. 在本次提交和变化范围内归并同一应用的重复叙述；只接受唯一成立的应用识别。确有两个不同的核心应用时拒绝，无法唯一定位时返回具体歧义。
5. 为当前 call 生成一个 VerifiedAmgmApplication。历史 application 保留自己的 producer，只作前序依据；不计入当前应用数量。回放也验证上述锚点和效果证据，不能仅相信应用记录字段。

本次应用不等于“新证明了一条历史上没出现过的定理”。同一二项模板或已缓存正性可以复用；但只读入旧界、没有形成与当前准确输入相连的局部操作证据，不能冒充本次应用。重复无变化的旧界陈述也不能借缓存产生应用事件。

教学消费者迁移为读取该记录的参与项、`local_rule_relation`、源位置、完整效果及取等要求。`runtime/inequality_teaching_evidence.py` 不再从 `derivation.proofs[].nodes` 扫描 `math.two_term_amgm` 生成 `local_relations`；引用或内联历史片段不得改变教学图。缺少新应用证据是结构化证据错误，不允许教学层自行反推或编造公式。

旧记录继续走带版本的旧教学适配器；若要转换成新应用记录，必须完整验证转换，不能给旧记录直接添加 `verified=true`。新执行路径不以旧节点扫描作为静默兜底。

### 10.2 M01 条件协议迁移

**当前代码并非一律要求显式 conditions。** `_bind_original_expression_conditions()` 已在 `args.conditions` 省略且 expression 唯一对应可见原题目标时自动绑定原条件，显式传入（包括空列表）则保持不变。Method 接收解析后的 conditions 验证定义域；不足时仍返回 `bind_domain_conditions`。PROMPT 和 summary 对绑定条件的描述也需要一起统一。

采用两个内部条件解析协议，执行产物显式记录版本，不新增要求 LLM 填写的参数：

| 协议 | 条件语义 | 用途 |
|---|---|---|
| `bound-conditions/v1`（旧行为标识） | 以原次调用解析后的绑定条件为可用前提；保留该版省略参数的解析规则 | 历史计划恢复、历史证据回放 |
| `scoped-facts/v2`（目标协议） | 原题可见条件及获准共享事实自动进入检索视图；显式 conditions 是经过身份校验的引用与检索提示，不是可用事实的排他白名单 | 新架构执行 |

v2 的具体规则：

- `args.conditions` 省略、空列表或只列部分条件，都不关闭已获授权的原条件视图。不得将“未列出”解释为数学上不可使用。
- 显式引用依旧必须真实、可见、版本有效，并按既有 binding 记录；无效引用不能因其它事实足够证明而被忽略。
- `using` 和数学 ∵ 表达作者所引用的依据，代码验证其来源或推导。它们不会把候选关系直接升格为事实，也不自动排除其它授权辅助条件；实际使用关系记录在证书和 `proof_reads`。
- 自动可用范围由准确 expression/owner、Scope 和执行快照决定，不靠同名变量猜题目。一般表达式没有可确认的目标关联时仍可使用其授权 Scope 的条件，但不能从不可见目标导入条件；身份歧义仍返回 binding 诊断。
- 每种子任务可再施加 Method 的前提种类约束，例如禁止借条件等式完成仅允许定义替换的操作；共享检索不能扩大 Method 操作范围。

这保留 JSON 形状，但改变显式条件列表的可用性语义，必须更新 `organize_expressions.py` 的 PROMPT、summary、preconditions 和错误修复动作，以及 Python Method spec 派生 JSON、Function/Family 目录和 Planner 上下文。v2 下已检索原条件仍无法证明分母非零时，应报告 `domain_unproved` 及具体义务；只有确实缺少身份绑定时才提示绑定条件，不能要求 LLM 重复写出系统已经持有的事实。

**旧证据回放不得使用扩大后的事实集。** 保存并重建原次调用的 resolved conditions、来源、局部前提表、context hash、有效预算和解析协议，再按旧证书协议回放；不能用新版绑定器重新选择条件。旧记录没有显式版本时，经原 schema 的兼容适配器归为 legacy，使用记录的原始上下文；无法恢复准确上下文则明确报不兼容，不猜测或静默补条件。

同一份录制 Plan 可以在 v2 下重新执行以比较能力，但这是新的执行和证书，必须另存产物，不能叫作“原证据回放通过”。Retry 恢复同样要检查条件协议版本，不能跨版本复用旧的成功执行标记。上述版本是数学执行/解析契约，不以 prompt hash 作为回放硬锁。

## 11. 证书格式与离线回放

### 11.1 兼容方式

现有 `bounded-real-proof/v1` 的局部规则及节点语义保持不变。新引入版本化的外层共享证明 bundle，概念名为 `scoped-proof-bundle/v1`；这不是给旧 schema 增加隐含字段。

外层包含：题设来源 manifest、符号与 Scope 身份、派生事实、局部证书片段、实际前提引用、producer 与版本依赖、Method 契约证据以及证明根。

每个局部证书的上下文从其明确引用的关系重建，并继续由现有 checker 校验。关键是：派生关系进入该局部上下文之前，外层验证器必须先验证其生产证书和授权，不能把引用关系直接当 trusted given。

外层同时记录条件解析协议、committed manifest 和本次 Method 应用证据。旧证据使用原前提集、旧局部上下文及旧应用识别/教学适配协议；新执行使用 scoped-facts 视图与 VerifiedAmgmApplication。不要将“旧证据能够回放”与“同一 Plan 在新环境重执行得到相同节点”混为一谈。

### 11.2 回放顺序

1. 核对外部 authenticated 题设与 manifest；bundle 自称的条件不构成信任根。
2. 验证符号身份、Scope 可见性、假设、版本、producer authority 和调用依赖。
3. 检查依赖无环，按拓扑顺序验证事实的生产证书。
4. 重建各局部上下文并检查其证书，不调用任何搜索策略。
5. 检查 Method 操作契约、准确输出和最终目标闭合。

所有嵌套片段共享外层回放资源上限；重复 DAG 节点按内容与环境去重。仅验证 hash 或 `verified=true` 不算回放。

改变搜索顺序只更新 SearchPolicy 版本，不修改数学规则 hash。确实改变规则语义时才升级规则版本并保留历史检查器；旧证据继续按旧 schema 回放。prompt hash 不作为数学证书硬锁。

## 12. q30 示例与泛化边界

### 12.1 事实复用

以 q30 的一个确定性变体说明复用：题设 `a>b>c>0` 进入题目 Scope；M01 只提交分式恒等整理，后续 M11 提交合法 AM-GM 关系和完整界，但**不显式重写** `b>0`、`a-b>0`。这不是声称现有 q30 Planner 样本没有写这两行；已有样本的 M11 确实可能显式提交它们。

若 M01 为证明原分母非零的成功证书中含 `b>0`、`a-b>0` 子结论，适配器从对应已检查节点导出这些必要域依据，经提交后复用。它们的来源是定义域子证明，不是把 M01 的分式整理行当成正性关系。当前 M01 也已有辅助条件说明路径，但本测试刻意不依赖它。不能要求某种证明路径一定生成这两个节点：若实际成功证书只证明了非零，就只发布已证明的非零，不凭展示需要补造正性；后续正性仍从原条件验证。

第一个 M11 需要证明 `b(a-b)>0` 时：

```text
目标：b(a-b)>0
→ 检索直接操作数 b 与 a-b
→ 命中两个已提交的正性事实
→ sign 规则构造并检查证书
```

不应先把乘积改成另一组分式的倒数，再递归证明新分母。若 Scope 尚无这两条正性关系，则从原题条件经有限关系规则证明，并在当前成功证明中保留依据。

### 12.2 连续求界

验收调用链保持 `M01 → M11 → M12 → M11 → M13`。

- M01 准确版本被第一个 M11 消费。
- M11 得到 `F≥2a²−10ac+25c²+4/a²`，发布界及必要域事实；`b=a-b` 记录为取等要求。
- M12 消费该界，得到 `F≥a²+4/a²`，增加取等要求 `c=a/5`。
- 第二个 M11 消费 M12 输出，得到 `F≥4`，增加 `a²=4/a²`。
- M13 在见证上下文验证 `a=√2, b=√2/2, c=√2/5`、全部原条件、域与累计取等要求，最后确认最小值。

以上数值与路线用于测试验收，不进入检索排序、求解输入或题号分支。改名、改系数、调换合法项顺序仍通过同一机制。

### 12.3 页面与自然推导

共享证明不新增学生步骤。目标架构中教学层读取 Method 的实际认知操作和源推导；必须先完成第 10.1 节的现行节点扫描迁移，才能成立。重复正性证明可被引用，不把内部 fact lookup、cache hit 或搜索路径展示给学生。

保留已有自然推导解析与来源映射。新架构不要求 LLM 输出 fact ID、策略 ID、预算或内部 proof node。中文连接词兼容与数学搜索是两个模块，不在此次调度重构中混成一套特殊字符串规则。

### 12.4 跨题型泛化与扩展点

第 12.1–12.3 节只覆盖同一题型内的泛化（改名、改系数、调换项序）。本节规定哪些部分可跨题型复用、哪些依赖证明内核能力、哪些属于题型专属，以及首批实现必须预留的扩展点。

| 层次 | 内容 | 跨题型状态 |
|---|---|---|
| 与题型无关 | Scope 事实库、可见性与前缀快照、`proof_reads`、事务发布与 Retry、搜索/检查分离、分阶段调度与预算、外层 bundle 与回放 | 直接复用；不得包含题型分支 |
| 依赖内核能力 | `bounded-real-proof/v1` 的通用实数规则：多项式恒等、符号、缩放、单调、传递、区间、开方与平方、代入、见证/存在 | 适用于有限变量的实数代数：化简与分式整理、定义域/非零/正性、方程变形等价与增根检验、换元消元、配方求界 |
| 题型专属 | AM-GM 类规则、VerifiedAmgmApplication、`local_rule_relation`、`AmgmBound/QuadraticBound` 消费协议、不等式教学投影 | 仅服务对应 Method；不上移到共享层 |

当前规则集不覆盖：几何对象关系（共线、全等、相似、角）、三角/指数/对数与导数、参数恒成立类问题的量词消去、数列归纳和计数。这些问题接入前必须先有对应规则包和拒绝测试，不能靠 S4 代数兜底、数值抽样或放大预算“碰巧”通过。现有几何和二次函数 Family 不经过 `proof_kernel`，本文不改变它们的验证路径；将其接入共享事实需单独设计 MathObject 身份映射及现有验证与证书的共存方式。

首批只有实数代数一个实现，但以下扩展点必须按接口组织，不能写成只认 AM-GM 的专用路径：

1. **规则包**：规则 ID、checker 与版本 hash 成组注册。现有规则集是第一个规则包，保持 `bounded-real-proof/v1` 身份和既有 hash；bundle 记录每个局部证书所用规则包及版本。新增规则包不改变已有规则包 hash，旧证书回放不受影响。
2. **策略包**：策略声明 `supported_goal_kinds` 和所需规则包，只能提出所属规则包内规则的候选。调度器、预算和轨迹不感知题型；规则包未启用时相应策略不参与匹配。
3. **事实类型注册**：`semantic_kind` 可扩展，每种类型声明身份键、检索索引键、发布条件，以及能否作为无条件前提。未注册类型不能发布；新类型不能借用已有类型的发布授权。
4. **Method 应用契约**：定义通用接口 `identify(submitted_relations, exact_inputs) -> candidates` 与 `verify(candidate, view) -> application_evidence`，教学投影只读应用证据。VerifiedAmgmApplication 是 M11 的实现；M12 配方、M07 换元等按需各自实现。共享层不按 rule_id 统计应用次数，也不假设每个 Method 恰有一个核心规则节点。
5. **条件性要求**：以带 `requirement_kind` 的公共要求接口建模，AttainmentRequirement 是取等专用实现；其 `bound_ref/application_ref` 不强加给增根检验或其他待检条件。公共接口按“带作用对象、需由见证或检验契约兑现的要求”建模；取等条件、增根检验、分支假设下的待检条件共用这一模型，由持有相应契约的 Method 兑现，均不进入全局事实检索。分支假设本身仍属于假设环境/validity；不能因采用公共要求接口而丢失分支身份。

规则包兼容边界：

- 当前 `bounded-real-proof/v1` 同时包含通用实数规则和 AM-GM 规则，首批将其完整注册为一个兼容包，不拆包、不删规则、不重算既有 hash。
- “禁用 AM-GM”指新搜索的允许规则能力集合收窄，属于已记录的 SearchPolicy 配置；不修改旧包内容。对应隔离测试同时审计最终证书及其依赖不含被禁用规则。旧证书回放仍使用其声明的完整旧包，不能受当前搜索开关影响。
- 策略可声明多个所需规则包，候选中的每个规则都须归属于声明且启用的包；跨包依赖在 bundle 中逐项绑定，不能将其他包的规则冒充本包规则。

约束：

- 共享层（事实库、检索、调度器、外层 bundle、Runtime 发布）不得出现 AM-GM、题号、Family 或题型名称分支；题型知识只能进入规则包、策略包、事实类型和 Method 契约。
- 不为“以后泛化”预建几何或三角规则；扩展点以接口和隔离测试证明，而不是以空实现证明。
- 首批验收包含一条不经过 AM-GM 的冻结 authored 子链：q12/q25 的 M07 换元 → M08 消元，其中 M08 所需的定义域依据（如新变量的非负/正性）从 M07 已发布事实复用，不依赖任何 AM-GM 规则、应用记录或教学适配。

下列新路径为实施建议；不能只搬动旧函数而保留原来的隐式全局分支顺序。

| 模块 | 职责 |

| `math_kernel/proof_facts.py`（新增） | 数学事实、假设环境、证明引用的不可变模型 |
| `math_kernel/proof_retrieval.py`（新增） | 面向只读数学视图的相关事实索引与检索 |

| `math_kernel/amgm_application.py`（新增或并入局部契约模块） | 应用契约的 M11 实现：从本次提交关系与准确 source 识别、验证 VerifiedAmgmApplication，不统计整个证明 DAG |

必须接入的现有位置：

- `runtime/executor.py`：只读证明服务注入，不扩大 Method 直接访问 RuntimeContext 的权限。
- `runtime/method_proof_backends.py`：显式登记证明内核与原生验证后端；v2 只对证明内核 Method 强制要求已授权的单 invocation 适配器。原生几何、二次函数验证继续自身路径，不生成共享事实；未知后端拒绝，新增 Method 必须登记并通过穷举测试。
- `runtime/functional_transaction_execution.py`：事实与输出原子提交，记录 `proof_reads`，恢复与撤销。
- `runtime/planner_state_context.py`、checkpoint 相关 schema：记录稳定依赖与恢复指纹；生成 schema 必须同步。
- `math_kernel/inequality_bound_v2.py`、`quadratic_bound.py`、`expression_rewrite.py`、`bound_chain.py`：使用共享会话、保持准确输入与 Method 契约。
- `math_kernel/inequality_bound_v2.py`：替换 `check_local_contract` 的节点扫描及最终 `pairs` 统计为本次局部应用根和效果证据；不能只调整最终计数。
- `runtime/inequality_teaching_evidence.py`：由 VerifiedAmgmApplication 生成本次 `local_relations` 与来源；消除新路径对 `derivation.proofs[].nodes` 的结构依赖。相关 `verified_local_amgm_relation_missing` 诊断和本地 AM-GM 视觉绑定测试同步迁移。
- `runtime/methods/organize_expressions.py`、`runtime/functional_plan_reconciliation.py`、M01 的 Function/Family 输入与提示词派生产物：同步第 10.2 节条件协议、旧行为兼容、修复动作和生成 spec；不能只修改底层 prove 函数。
- Explanation 聚合：增加辅助证据依赖闭包，不制造额外教学动作。

核心依赖方向是 Runtime → 数学视图/内核；数学内核不能反向导入 Runtime。fact store 不成为全局单例，按执行会话隔离。

内部服务接口的预期边界如下，名称在实现时可调整，但职责不能混合：

```text
prepare_proof_view(call_authority, committed_manifest) -> ProofEnvironmentView
open_proof_session(view, policy, limits) -> ProofSession
session.prove(relation, source_origin) -> VerifiedProof | ProofDiagnostic
session.finish() -> CertificateBundle + ActualFactReads + CandidateFactDelta
validate_publication(call_authority, method_result, candidate_delta) -> AuthorizedFactDelta
commit_call(outputs, authorized_delta, actual_reads) -> NewCommittedManifest
replay_bundle(bundle, authenticated_problem, restored_authority) -> ReplayResult
```

`session.prove` 成功只允许当前会话使用该关系；`session.finish` 也不构成发布。唯一共享发布点是 Runtime 的原子提交。若证据适配器暂不支持某 Method，该 Method 仍按原路径验证，但不能通过非结构化 trace 文本猜测并导入事实。

## 14. 测试设计

### 14.1 事实与权限

- v2 下原条件自动可用；M01 成功定义域子证明中的正性与非零、已验证恒等式在后续 M11 可复用，专门覆盖后续推导未显式重写这些关系的样本。
- 同 Scope 前序调用可读；未来调用、兄弟小问、分支假设、失败事务不可读。
- 同名不同身份符号、不同换元定义、不同 StateVersion 不混用。
- 原题数学关系相同而依赖不同的证书正确去重、选择和追踪。
- 取等条件和 witness 关系不能用于证明全局下界。
- 回滚不残留事实；producer 被 Retry 替换后，下游 `proof_reads` 正确失效。
- 现有串行执行的前缀快照与实际读取依赖一致；将来引入并行时才加入乱序完成的屏障等价测试，不把当前串行 Runtime 写成已有并行。
- 第 4.3 节每个前提构造点都有发布/不发布测试；`attainment:reference`、`solution_case`、`shared_solution:*` 不泄漏为全局事实。
- 检测到的矛盾明确拒绝；未检测到矛盾不产生“题设可满足”标记。最值闭合缺见证或见证不满足全部原条件时拒绝，即使局部界证书成立。
- M01 条件协议矩阵：省略、空列表、部分显式条件、完整条件、无效/越权引用；v1 与 v2 分别验证其前提可用范围和诊断，不混用预期。

### 14.2 搜索与预算

- `b>0,a-b>0 ⇒ b(a-b)>0` 命中结构符号策略，不进入多项式兜底。
- 添加不相关分式恒等式、调换事实插入顺序，不改变上述策略选择。
- 局部额度耗尽后其他候选仍可成功；总额度不因切片、回溯或缓存失效而重置。
- 循环候选失败不污染其他路径；不缓存条件不完整的失败。
- 大事实库下局部证书前提保持有限；检索截断有明确诊断。
- 同一事实经不同合法表达形式书写时，有受限等价路径，而非默认语法相等。
- 定义域、错误方向、错误配方、虚假正性、丢失余项持续被拒绝。
- 默认、消元、换元三类有效预算 profile 独立记录并回归；嵌套链不会无声重置总预算。
- 同一目标在不同 committed manifest 下不直接命中旧成功缓存；合法导入重建正确证据环境，过期/被撤销依赖拒绝。

### 14.3 证书与跨 Method

- 新 bundle 在禁用搜索模块时仍能回放；依赖、来源、Scope、版本、假设和关系篡改均拒绝。
- 缺生产证书的派生 given 被拒绝；循环事实引用被拒绝。
- M11 不能借共享结果冒充新应用；M12 与 M13 的准确链路及累计取等保留。
- 依赖中包含旧 AM-GM 应用且当前合法新增一次应用时，引用式与内联式共享证书均通过，不误判为“应用不唯一”。
- 仅引用旧界且缺少本次局部效果时拒绝；真正一次提交两个不同核心 AM-GM 应用时拒绝；重复叙述同一应用仍只产生一个事件。
- 教学读取本次应用证据：共享片段含或不含本地展开节点时，当前参与项、局部公式、取等条件、源位置和线框图投影一致；不把旧应用画成当前应用。
- 旧 M01 仅绑定部分条件的证书按原前提集回放通过；向当前 Scope 加入额外事实不改变其回放上下文。同一录制计划在 v2 重执行可生成不同证书，必须作为独立产物记录。
- 界分别成立但取等条件不能同时满足时，M13 不关闭最值目标。
- 原有 AM-GM 及换元证书继续按旧协议回放。

### 14.4 系统回归与指标

冻结已保存 q30 首轮失败响应，不重新生成后再宣称修复。阶段 A 先区分数学合法且属于本架构范围的失败、真实 Method 越界、数学错误和句法能力缺口；只有前一类要求新架构验证与回放通过，不能为“所有失败变绿”放宽契约。每个样本统计：证明结果、失败分类、有效预算 profile、策略次数、归约次数、检索数、事实/缓存命中、实际依赖、证书节点、回放成本、耗时。

覆盖 q30 改名/系数/项顺序、旧 M11 连续链、q29 整体倒数、q25/q12 换元、M01 整理，以及几何、二次函数、Scope Retry 和教学回归。

正确性门禁必须使用真实证明和回放，不能 mock 通过。性能门禁以确定性操作数为主，墙钟耗时为辅；固定机器与配置比较，不把缓存预热或并行差异误当算法改善。

### 14.5 扩展点隔离

- 共享层模块（事实库、检索、调度器、外层 bundle、Runtime 发布）静态检查不引用 AM-GM 规则 ID、应用记录类型、题号或 Family 名称。
- 注册一个测试用规则包与策略包：不改变现有规则包 hash 和旧证书回放；禁用后其策略不参与匹配；其规则不能出现在其他规则包的证书中。
- 未注册的 `semantic_kind` 不能发布；新注册类型不能继承已有类型的发布授权。
- q12/q25 的 M07 → M08 子链在禁用全部 AM-GM 规则时，M08 复用 M07 已发布的定义域事实，验证并独立回放通过。
- 增根检验或分支假设下的待检条件按条件性要求建模，不能作为全局前提参与检索。

### 14.6 性能基线与优化验证

阶段 E 审查修订后，使用冻结 q30、显式 `scoped-facts/v2`，真实执行 `M01 → M11 → M12 → M11 → M13`，未调用真实 LLM。独立进程顺序执行的单次对照如下：

| 配置 | 完整离线运行耗时 |
|---|---:|
| 当前实现，完整调试输出 | 38.46 秒 |
| 同实现，关闭调试输出 | 25.77 秒 |
| 关闭调试输出，并实验性缓存派生元数据 | 15.98 秒 |

三次答案、5 个事实提交、3 条取等要求及完整证明快照 hash 一致；实验未跳过数学检查。每配置只有一个样本，约 58% 的降幅仅说明优化潜力，不是中位数、p95、正式性能承诺或毫秒级目标。关闭调试输出用于隔离成本，不作为删除审计产物的实施方案。

剖析发现：无 Retry 的首轮成功执行仍重放提交 25 次，其中当前提交检查 5 次、前缀重新校验 20 次。整份调用列表与 Scope 输出变化会使验证缓存失效；manifest、事实标识和完整调试产物也被反复计算、序列化。剖析累计耗时有重叠且受 profiler 影响，不能相加或直接与上表比较。详细数据、输入与实现指纹见 [性能验证记录](validation/scoped-proof-performance/README.md)。

正式优化应先建立重复基准，再验证以下场景：

- 正常整题求解、独立进程冷回放、同进程缓存命中、Retry 恢复、产物生成分别计时；固定输入、机器、协议和输出模式，每场景多次运行，报告中位数与范围。
- 记录生产证书重放次数、重复转换/序列化次数、搜索候选与算术操作、证据体积；为重复工作建立确定性计数断言。若报告峰值内存，应单独测量，不能用证据体积代替。
- 深度不可变对象的派生标识与 canonical bytes 缓存须保持 payload/hash 不变；替换对象、修改返回副本不能污染缓存。禁止复用含可变嵌套字段的未冻结对象。
- 新增无关后续调用或无关输出不应使生产证明缓存失效；改变原条件、生产授权、相关 Scope 可见性、符号身份、定义、版本、规则或证书内容时，必须拒绝复用或重新验证。
- 冷缓存、缓存失效、撤销及篡改用例仍通过独立 checker 检验；验证缓存不允许跳过当前消费者的权限检查，也不能把外部“已验证”标记当作授权。
- 保留失败请求、响应、检查点和最终完整回放证据；输出去重后独立重建与回放结果一致。

## 16. 维护规则

- 本文只维护目标语义与实施状态，不累积每次失败的时间线；运行记录保存在 review/solver artifacts。
- 新增数学规则先定义 checker 与拒绝测试，再接入搜索；新增搜索策略不能自行创造公理。

- Method、事实权限、搜索、证书和自然语言解析分别归属各自模块，错误诊断必须指出所属层。
