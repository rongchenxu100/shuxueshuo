# 基本不等式章节题库：首版设计与实施计划

> 现状补记（2026-10-02）：基本不等式 Q01–Q30 交互题库已完成，用户已确认发布，入口为 <https://shuxueshuo.com/1/>。下文保留首版规划，其中“仅 Q01”“待发布”等属于历史阶段；登录与个人进度保存不能据此视为已实现。当前交互架构与公共组件见[共享运行时设计](interactive-lesson-shared-runtime-design.md)。下一专题见[一元二次不等式恒成立问题题库设计](quadratic-inequality-always-true-practice-design.md)。

状态：**首版范围已确认，章节静态入口已实现、待发布；个人状态与登录待实施**。更新日期：2026-09-29。

## 1. 目标与范围

建立一个基本不等式章节题库，让孩子可以选题练习，并保存个人做题状态。

首版只完成三个能力：

1. 题库里能看到题目，点击后进入练习。
2. 题目沿用 Q01 demo 的交互方式，支持点选和对话。
3. 登录后记录自己的做题状态，下次打开题库仍能看到。

章节内按六种题型分组展示，不增加单元解锁或复杂训练流程。暂不做掌握度评估、智能推荐、知识图谱、题库后台编辑器，以及“再次做错变红”等更细的状态。做完题不等于掌握某种方法，首版不作这类推断。

## 2. 文件与数据库的分工

| 内容 | 首版存储方式 | 用途 |
| --- | --- | --- |
| 题目静态网页及资源 | 文件 | 展示题目、组件和推导 |
| 每题教师 JSON | 后台每题一份文件 | 提供题目、节点要求、判定依据和对话上下文；网页独立承担学生课程和本地组件答案 |
| 章节题库清单 | JSON 文件 | 记录稳定题目 ID、题号、标题、顺序和页面地址 |
| 用户与登录信息 | 数据库 | 确定当前孩子的身份 |
| 用户做题状态 | 数据库 | 记录孩子在每道题上的进度 |

**首版不要求把题库清单导入数据库。** 增题、改题仍通过文件发布；数据库保存随用户操作变化的数据。以后需要在线管理题库时，再考虑迁移清单。

每题 HTML 承担课程内容、展示模板和本地组件配置，公共 CSS/JS 完成点选、填写、校验和步骤推进，不依赖后台。Q01 已实现此模式；学生发起对话时才批量同步页面操作，由后台加载教师 JSON + Context 调用 LLM。个人状态远端保存仍待实施。详见[交互题目公共运行时设计](interactive-lesson-shared-runtime-design.md)。

复用当前主站静态服务、现有 API 服务和数据库，不为这个题库另起独立服务。

## 3. 页面与状态

入口是一页“基本不等式”章节题库，按以下六种题型依次分组，各组内展示题号圆圈：

1. 直接法求最值。
2. 常规配凑法求最值。
3. 分式分离法求最值。
4. 配齐次式求最值。
5. 条件消元求最值。
6. 换元求最值。

分享入口固定为 `https://shuxueshuo.com/1`，方便在小红书以文本形式分享。对应静态文件 `site/1/index.html`；当前静态服务器会将 `/1` 自动转到 `/1/`。对外可始终使用无尾斜杠的短链接，页面资源使用明确的站内路径，无需新增 API 或 Nginx 路由。

所有题目入口只链接与 Q01 相同形式的交互网页，不链接旧解析页，也不预先展示尚未生成的题号。当前仅在“直接法求最值”中提供 Q01，其余五组标记待更新；Q01 内已有的条件消元路径仍可使用，但不因此在章节页重复增加一道题。后续逐步新增交互题目并归入对应题型。现阶段圆圈只代表题号入口，不显示虚构的完成进度，也不根据链接访问记录推断做题结果；以下学习状态在后续阶段接入。

- 圆圈包含题号，用颜色和小图标共同表达状态，并提供文字说明。
- 点击圆圈进入对应题目的静态网页。
- 题目页提供“返回题库”；返回后显示最新状态。
- 首版不设解锁条件，孩子可以自由选题。

| 状态 | 视觉表示 | 含义 |
| --- | --- | --- |
| 未做 | 灰色空心圆 | 尚未开始练习 |
| 进行中 | 蓝色进度标记 | 已开始，尚未完成 |
| 完成正确 | 绿色＋勾号 | 已按本题交互判定完成 |
| 待再练 | 橙色＋重练标记 | 有明确作答错误，需要再练 |

无操作、主动提问、请求提示、网络失败或模型无法理解输入，都不自动算作答错。静态练习依据 HTML 组件配置中的答案本地校验；写入个人状态时由后台按相同教学规则校验，不直接信任客户端上报的结果，也不依据老师回复是否出现“正确”等文字。

**待确认：有过错误、后来在引导下完成，显示绿色还是橙色。** 先分别记录“是否完成”和“是否出现明确错误”，颜色作为展示规则，不存成唯一事实，便于后续调整。绿色只表示完成情况，不表示独立掌握。

首版保证题库中的状态可恢复；恢复到上次具体对话、槽位和节点不作为本版必需验收项。若需要断点续练，再扩展 Context 持久化。

## 4. 最小数据设计

### 4.1 题库清单

建议位置：`site/practice/basic-inequality/index.json`。只放公开目录信息，页面地址指向实际生成的文件。格式示意：

```json
{
  "chapter_id": "basic-inequality",
  "title": "基本不等式",
  "items": [
    {
      "problem_id": "basic-inequality-q01",
      "category_id": "direct",
      "number": "01",
      "title": "第 1 题",
      "order": 1,
      "page_url": "/1/q01/"
    }
  ]
}
```

这是建议格式，尚未建立该文件。清单中还需声明上述六种题型的稳定 ID、名称和顺序，题目以 `category_id` 关联题型。`problem_id` 不随题型、页面路径或排序变化；与现有 demo 内部 lesson ID 建立明确映射，不从 URL 猜测题目身份。实质不同的新题使用新 ID，避免旧状态落到另一道题上。

### 4.2 用户与状态

复用已有 `users` 用户主体，登录阶段补充必要的身份和会话能力，不把做题状态加到用户表里。现有工作台固定用户身份不能直接作为所有孩子的身份。

新增一张用户题目状态表，例如 `user_problem_progress`，以 `(user_id, problem_id)` 唯一确定一条记录。最小业务字段：

| 字段 | 含义 |
| --- | --- |
| `user_id` | 当前孩子 |
| `problem_id` | 稳定题目 ID |
| `started_at` | 开始本次练习的时间 |
| `is_completed` | 本次练习是否完成 |
| `has_error` | 本次练习是否出现明确作答错误 |
| `updated_at` | 最近更新时间 |

没有记录表示未做。首版保存当前／最近一次练习的摘要，不建立完整历史统计系统。建议仅在明确点击“重新练习”时重置本次摘要；普通刷新或再次打开页面不清掉已存题库状态。

状态更新接在现有开始练习、判定作答和完成题目的流程上。读取题库时按登录用户获取状态，再与 JSON 清单合并。实现时补充必要的练习标识或版本控制，处理重复请求和旧练习响应，防止旧结果覆盖重新练习的状态。

## 5. 四个实施阶段

| 阶段 | 实施内容 | 验收结果 |
| --- | --- | --- |
| 1. 实现章节静态入口 | 建立 `/1` 章节页，按六种题型组织圆圈题号，仅链接现有 Q01 交互题，提供返回入口 | 手机与电脑均可访问；分组名称、顺序正确；没有旧解析页链接和无效题号 |
| 2. 补齐题目与文件清单 | 确定固定题目 ID 和题型，建立 JSON 清单，逐步生成与 Q01 同形式的交互页与教学数据 | 清单与章节页一致；新题完整可用后才加入对应分组 |
| 3. 保存做题状态 | 建立状态表，接通开始、错误、完成和重新练习；先使用开发测试用户 | 刷新或重启后状态仍在；网络失败不变成做错；重复和旧请求不破坏状态 |
| 4. 接入登录 | 选定登录方式，将开发测试身份替换为实际孩子身份 | 两个账户状态隔离；退出再登录、换设备均能读取本人状态 |

### 阶段约束

- 第一阶段只接入现有 Q01 demo，保留其余题型的待更新位置，不链接旧解析页。
- 第二阶段先补两三道代表题走通闭环，不等待所有交互页生成完。样本状态预览不能宣称已支持长期或跨设备保存。
- 第三阶段确认“有过错误但最终完成”的颜色规则。开发测试用户只用于验证，不作为多人公开使用方案。
- 第四阶段由后端从登录会话确定用户，不信任前端任意指定的 `user_id`；学生登录不授予内容制作工作台权限。
- 首版题库内容可公开浏览，保存个人状态要求登录；游客状态自动合并暂不纳入范围。

## 6. 推进顺序

先用少量题目走通完整闭环：

```text
打开章节题库 → 进入题目 → 练习 → 保存状态 → 返回题库
                                         ↓
                             再次登录后看到自己的状态
```

闭环验证后，再批量补齐基本不等式章节题目。后续增题原则上更新题目文件和题库清单即可，不应要求每加一题都修改状态表或登录逻辑。

登录方式、错误后的颜色优先级在对应阶段落地前确认，不阻塞题目准备和题库入口。当前实现仅覆盖章节静态入口，其余阶段仍为计划。
