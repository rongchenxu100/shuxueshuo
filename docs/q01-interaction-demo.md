# Q01 交互 Demo：三个节点、页面交互与组件职责

状态：**交互讨论稿；静态 happy path 演示已实现，正式对话与运行时接线待实现**。更新日期：2026-09-26。

静态演示入口：[site/demo/q01.html](../site/demo/q01.html)，本地启动方式见[演示说明](../site/demo/README.md)。三个节点可以点选走通；底部对话框默认展示但不发送消息。页面使用本题预设推导，不调用 LLM 或 Solver，不代表下文的文本理解已经实现。

本文作为 Q01 交互 Demo 的讨论入口，记录已确定的三个顺序节点、通过条件、页面交互和组件职责。总体规划见[学生交互与个性化教学系统设计](student-tutor-chat-system-design.md)；Q01 的具体交互以本文为准。

## 1. 题目与范围

题目：设正实数 \(m,n\) 满足 \(m+n=2\)，求 \(mn\) 的最大值。

- 首版同时接收页面点选与文本。底部对话框默认展示，学生也可使用设备自带的语音输入法，不自行实现录音或语音识别。
- 学生表达思路、方法关系和取等条件；系统承担代入、化简、求值与核验。
- 状态机只有三个顺序节点，不增加独立的“选择方法”或“系统计算”节点。
- 第三个节点通过并完成系统核验后，整题结束；“结束”是完成标记，不是第四个教学节点。

```text
观察结构 → 应用基本不等式 → 验证取等
```

## 2. 节点一：观察结构

**学生需要表达完整的结构与方法联系：**

> m+n 是定和，要求 mn 的最大值，所以可以直接用基本不等式。

通过条件包含三个关键点：

1. 条件中 \(m+n\) 是定和。
2. 目标是求同一组数的乘积 \(mn\) 的最大值。
3. 根据这个结构，判断可以直接应用基本不等式。

可通过的口语示例：

> 两个数加起来固定，要让它们的积最大，所以直接用基本不等式。

尚不足以通过的表达：

- “它们的和是二”：缺少目标与方法判断。
- “定和求积”：缺少直接应用基本不等式的方法判断。
- “用基本不等式”：缺少条件、目标与方法之间的联系。

关键意思齐全后进入第二个节点；不要求标准句式或固定术语。此节点不要求学生提前写出基本不等式公式。

以上意思也可以通过页面操作表达：选择方案，再用圈框组件表示条件和目标。两个问题都属于本节点，具体流程见第 7 节；不要求完成点选后再用文字复述。

## 3. 节点二：应用基本不等式

**本节点要求学生把本题的数学对象代入给定的基本不等式模板。** 页面点选和等效文本都可以作答，最终形成：

\[
m+n\ge 2\sqrt{mn}
\]

### 3.1 交互输入：圈框代入或等效文本

页面提供模板：

\[
\Box+\bigcirc\ge2\sqrt{\Box\cdot\bigcirc}
\]

- 点击方框或圆圈，只能从本题的 m、n 中选择，同形状在公式中同步填入。
- 方框为 m、圆圈为 n，或方框为 n、圆圈为 m，均可接受；两个形状都填同一个变量不能通过。
- 系统核验对象映射和正性条件。公式的系数、不等号及根号由模板提供，不要求学生再次选择或默写。
- 正确填写并提交后即可进行系统推导，不把本次操作记录为“学生独立回忆出了公式”。

学生也可在默认展示的对话框中表达。例如：

- “方框放 m，圆圈放 n。”
- “m 加 n 大于等于两倍根号下 m 乘 n。”
- “两个数的和，大于等于两倍根号下它们的积。”
- \((m+n)/2\ge\sqrt{mn}\)。

文本含义明确且与本题模板代入等效时，系统自动把 m、n 填入交互组件，同步显示对应关系，使用与点选相同的核验与流转规则。学生提交文本即为提交回答，不要求再点一次确认或重复填写；对称的两种映射均接受。

仅说“用基本不等式”仍不足以通过，它没有明确本次对象映射或具体关系。文本有实质歧义、遗漏必要映射，或不等式方向、系数错误时，不擅自补成正确答案，不覆盖已经确认的内容；只针对缺口澄清或纠错。只明确一个槽位时可更新该槽位，但不直接宣布完成。

### 3.2 展示解释：自动代入定和

对象映射确认后，展示“代入定和”区域，帮助学生看清题目条件如何进入公式：

1. 呈现已确认的 \(m+n\ge2\sqrt{mn}\)，高亮左侧 m+n。
2. 关联题目中的 m+n=2，将左侧替换为 2。
3. 展示代入与化简结果：

\[
2\ge2\sqrt{mn}\quad\Rightarrow\quad mn\le1
\]

这部分使用展示组件，由系统自动完成，不增加一道必答填空或单独的状态节点；学生可通过对话框追问。

### 3.3 下方数学步骤与完成条件

下方自动生成经过核验的推导记录，包含正性、应用基本不等式、代入定和与化简得到上界。学生不必输入中间计算，也不必重复说明题面已给出的正性。

节点完成条件是：**学生通过点选或等效文本正确完成对象映射，系统核验并推导出上界。** 成功后进入第三个节点。此时只确认上界为 1，不提前宣布最大值为 1，也不自动补齐取等判断。

## 4. 节点三：验证取等

**学生需要明确表达取等条件：**

\[
m=n
\]

可通过的表达示例：

- “m 等于 n 时取等。”
- “两个数相等时取等。”

只说“能取到”或“最大值是一”不能代替明确的取等条件。

学生表达 \(m=n\) 后，系统承担剩余工作：

1. 联立 \(m=n\) 与 \(m+n=2\)，求得 \(m=n=1\)。
2. 验证该取值满足正性与定和条件。
3. 验证 \(mn=1\)，确认上界可以达到，得到最大值为 1。

**不额外要求学生说“还要检查原条件”，也不要求学生算出 m=n=1。** 学生给出取等条件、系统核验成功后，本节点结束，整题完成。

交互组件采用“空方框 = 空圆圈”：等号固定提供，学生从 m、n 中选择两侧对象，组成 m=n 或 n=m。同一对象填入两侧不能代替本题两个正项的取等对应。节点 3 重新填写，不自动沿用节点 2 的填值。正式文本交互中，等效表达可自动填入；当前静态演示只实现点选。

## 5. 共同流转规则

- 通过依据是学生表达的数学含义，不是关键词命中；允许自然口语和等价表达。
- 条件未满足时保留当前节点，围绕缺失或错误的意思继续交互。
- 后台已知解法或答案，不等于学生已经完成相应节点；系统不替学生补齐要求表达的关键点。
- 每个节点按顺序检查。一次输入已经完整覆盖多个节点时，可以连续通过，不要求学生重复作答。
- “学生表达满足要求”与“系统计算核验成功”都应成立，才能完成涉及计算的流转。

点选和文本共同推进同一份步骤状态：明确的组件提交直接形成结构化回答；文本由 LLM 理解后提交相应回答，再由状态机判断。组件和 LLM 均不能自行宣布节点通过。具体 Context 字段、文本解释协议和追问策略后续逐项讨论，不预先增加复杂接口或状态。

## 7. 单栏页面与第一步的点选流程

### 7.1 页面分工

采用单栏页面：上方是题目与逐步形成的解题过程，底部对话框默认展示。

- **可视化区域是主要讨论区域。** 能通过选择数学对象、关系和结构完成的判断，优先在页面中操作；提示与局部反馈也可出现在对应区域。
- **下面的数学步骤是系统整理和计算的记录。** 学生判断通过后，系统整理数学表述，执行基础计算并呈现经过验证的结果。
- **底部对话框始终可用。** 学生可以直接提问、说明其他想法或纠正系统理解，无需先点击“我有疑问”。点选与文本可以交替使用，都针对当前步骤。
- 学生已经通过点选明确表达的内容，不要求再打字说明一次。已确认结果保留为解题记录，讨论历史可关联相应步骤回看。

刚进入题目时显示题目、第一步“观察结构”及其第一个问题，暂不展开第二、第三步。删除“定和求积的最大值”这类提前透露结构的标题，保留题号即可；不提前展示答案、完整解题要点或后续推导。

### 7.2 第一个问题：选择解题方案

页面提问：

> 这道题，你准备采用哪种解题方案？

提供可点击选项，例如：

- 直接应用基本不等式。
- 换元法。
- 条件消元法。

学生选择“直接应用基本不等式”后，保存方法提议，展开第二个问题。此时观察节点尚未结束，也不自动执行基本不等式计算。其他方案不因未命中预设路径就被判为数学错误，具体引导后续讨论。

### 7.3 第二个问题：操作圈框表示结构

复用现有结构展示的视觉形式，制作独立的交互组件。页面提问：

> 用下面的结构，表示题目的条件和目标。

交互规则：

1. 上排固定表示“条件”，下排固定表示“目标”。
2. 点击方框或圆圈，只提供本题的 `m`、`n` 作为数学候选项，不允许在槽位中调用输入法任意填写；底部对话框仍可自由表达。
3. 同一形状在上下两排同步更新，不重复填写。方框为 m、圆圈为 n，或二者交换，都可以成立；两种形状都填成 m 或都填成 n，不能视为正确表示本题结构。
4. 中间交换箭头可点击，用于交换加法与乘法在上下两排的位置，清楚标注“交换和与积”。它改变学生的结构表示，不改写原题条件。
5. 学生组成并确认“条件中两数相加且固定，目标是同一组数相乘并求最大值”。结合已选择的方法，满足观察节点的完整通过条件。

正确结构示意：

```text
条件： [m] ＋ (n)    固定
           ⇅
目标： [m] · (n)    求最大值
```

作答中的槽位尚未完整、尚未确认或表示错误，都不能自动完成节点。不得把已填好的完整正确结构直接当成学生答案。“定和求积 → 直接应用基本不等式”等总结应在确认后展示。

### 7.4 确认后的页面结果

状态机确认通过后，将已确认的结构交给展示组件，下方整理数学过程，例如：

> ∵ m、n 为正数，m+n=2，目标为 mn 的最大值。\
> ∴ 本题为定和求积，可以直接应用基本不等式。

然后进入第二节点。第二节点仍需学生完成基本不等式模板的对象映射，或提交等效文本；第三节点仍需表达 m=n，不因第一步点选成功而自动补齐。

第二节点使用第 3 节的圈框代入交互组件；定和替换和化简使用展示组件。提供模板后完成代入是本节点认可的作答方式，与独立写出公式分别记录。第三节点使用固定等号、两侧圈框填写的交互组件，遵守第 4 节的通过条件。

## 8. 展示组件与交互组件分别声明

两者可以采用相似的视觉形式，但应是独立组件，拥有不同的职责与数据契约。

| 项目 | 展示组件 | 交互组件 |
| --- | --- | --- |
| 输入 | 已确认的数学对象、关系与结果 | 当前问题、受限候选项和学生当前选择 |
| 行为 | 呈现已确认结构或推导 | 接收选择、修改和提交，表达学生的判断 |
| 输出 | 可视化画面 | 结构化学生回答 |
| 通过判定 | 不负责 | 提交给状态机，不自行决定通过 |

例如圈框展示组件直接接收 m、n 与定和求积关系；圈框交互组件允许选择 m、n、交换和积并提交。两者可以共享形状、公式排版等底层绘制能力，但不将展示组件简单切成可编辑状态来代替独立的交互契约。

每个学生步骤需要有明确的交互组件声明。复用声明宜放在 Method 对应的教学单元上，再绑定到本题 Lesson Step，因为一个 Method 可以产生多个不同的学生步骤：

| Method | 教学单元 | 交互职责 | 展示职责 |
| --- | --- | --- | --- |
| `apply_two_term_amgm` | 观察结构 | 方案选择与圈框结构输入 | 已确认的结构与方法依据 |
| `apply_two_term_amgm` | 应用基本不等式 | 圈框限定点选；等效文本自动填入并提交同一映射 | 已验证不等式、定和替换的视觉解释、自动化简与推导记录 |
| `close_equality_and_restore` | 验证取等 | 固定等号、圈框限定点选 m/n；正式文本交互支持等效自动填入 | 取等求值、条件检查与最终结论 |

结构化回答通过状态机确认后，交由展示组件形成解题记录。文本输入经理解后也进入同一条确认流程；不增加一套聊天专用状态机。

工程假设是：有限、可组合的 Method 及其教学单元可以复用于大量中学数学题；组件绑定不同题目的对象、候选项和已验证结果，无需逐题重做。覆盖程度需通过真实题集验证，不能将其视为已经证明的普遍覆盖能力。具体 schema、组件 API 和注册方式留待实现设计，本文只确认职责与复用方向。

## 9. DeepSeek 接入版（2026-09-26）

在前述交互设计基础上，对话框已接入真实后端。实现位于 `server/shuxueshuo_server/tutor_demo/`，运行方式见该目录 README。

- 文件输入 `lessons/q01.json`：原题、题意整理、直接应用基本不等式与条件消元两条路径、节点问题与通过标准、其他方法的适用性解释。
- 前端发送点选/填写/确认的结构化学生事件和自由文本，后端持有权威 context；展示组件保持原有视觉。
- 规则处理点选；DeepSeek 处理文本/提示，使用 system 与 turn 两个 Jinja 模板。完整等效回答自动填入并提交当前节点，提问与提示保持节点。
- 学生和老师的文本对话附在所属节点下，已完成节点保留对话和状态快照。10秒呼吸邀请不自动请求模型。
- 重新体验创建新会话，清空页面状态、对话和计时；旧请求结果不进入新会话。
- 第一版使用内存会话；刷新/重启不恢复进度。自然语言识别还需继续用实际错答与歧义表达测试。

第7节的操作性提问文案已在演示中替换为“定和求积还是定积求和？”，标签按结构显示定和/定积及求最大值/求最小值。每个完成节点保留一个主要可视化，其余推导用数学文字解释；条件消元的函数分支另附函数图像。

完成本步所需信息后，老师仅简短确认，不追加下一步问题；信息不足时继续引导补齐当前判断。当前步骤对话展开，已完成步骤对话默认折叠，支持随时回看，数学可视化和推导继续展示。

## 10. 多路径尝试

学生做完消元后说“再试试基本不等式”，系统在同一会话中归档消元记录，并新建基本不等式路径尝试。旧步骤与对话可展开回看，新路径从首节点重新收集证据。学习途中也可以明确要求切换路径，原进度保留为历史记录；默认不将旧路径通过证据迁移到新路径。

切换是独立流程意图，必须由执行器成功执行后再确认。通用 prompt 不硬编码 Q01 数学规则，而是读取当前节点的证据标准、组件候选项和允许动作。详细数据契约见 tutor_demo/README.md 的 v2 说明。
