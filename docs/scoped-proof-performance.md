# Scope 证明链路：性能剖析与优化顺序

日期：2026-09-28。基于阶段 E 审查修订后的实现，使用冻结 q30，实际执行 M01 → M11 → M12 → M11 → M13。本轮仅剖析与隔离实验，未改正式实现、未调用真实 LLM、未进行浏览器检查。

## 非剖析对照

| 配置 | 本次完整离线运行 | 相对基线 |
| --- | ---: | ---: |
| 当前实现，完整调试输出 | 38.46 秒 | 基线 |
| 同实现，debug_dir=None | 25.77 秒 | 减少约 33% |
| 关闭调试输出，并在进程内缓存派生元数据 | 15.98 秒 | 减少约 58%，约 2.4 倍速度 |

最后一项只缓存 VerifiedMathFact 的 statement_key/fact_id、FactCommit 的 commit_id、FactSnapshot 的 manifest 和 ProofCallAuthority 的 fingerprint，不改变数学规则或跳过 checker。三次答案、提交数、取等要求及完整证明快照 SHA-256 一致。它证明存在明显的非数学计算开销，尚不能替代正式缓存的安全性回归。

每种配置只测一次，独立进程顺序执行；计时包括 Runtime 和输出开销，不包含真实模型等待。当前没有 p95 或稳定延迟结论，也不承诺优化后整题达到毫秒级。

## 实际热点

原实现带 cProfile 时总函数计时约 85.1 秒，记录约 4.77 亿次调用。剖析器有明显开销，下列累计耗时用于识别路径，不能相加或当作无剖析的真实延迟：

| 路径 | 次数 | 剖析累计耗时 |
| --- | ---: | ---: |
| 搜索调度 run_scheduled_request | 48 | 3.16 秒 |
| 快照校验 verify_snapshot | 10 | 22.67 秒 |
| 提交重放 _restore_one | 25 | 24.00 秒 |
| 调试写入入口 _write_debug_attempt | 5 | 28.26 秒 |
| 完整 manifest 计算 | 94 | 10.68 秒 |
| statement_key | 34,953 | 8.16 秒 |
| fact_id | 68,029 | 6.31 秒 |

首次成功执行没有 Retry，仍发生 25 次提交重放：5 次来自当前提交检查，20 次来自前缀快照重新校验。所以只优化 Retry 恢复，无法消除首次求解的主要重复成本。

代码中的缓存键包含整份 calls 和 repr(context.scopes)。新增下一调用、写入 Scope 输出都可能改变缓存键，虽然之前生产证书的数学内容未变；每次 miss 又从头重放整个前缀。manifest 则通过所有提交的 to_payload 生成，并触发事实解析、派生标识和 JSON 序列化。

调试入口在一次语义 attempt 内进入 5 次，总计调用 write_debug_json 172 次。safe_debug_json 和 JSON 编码本身也很昂贵，不能把这部分成本简单理解成硬盘写入速度。

## 建议实施顺序

### 1. 不可变元数据只计算一次

对深度冻结的事实、提交和快照缓存派生标识与 canonical bytes。对象替换产生新缓存，禁止共享可变 to_payload 字典。维持现有 hash 算法和序列化内容，确保旧证据兼容，不在此步迁移协议。

验收：新旧 payload/hash 完全一致；修改源对象、复制返回字典或替换字段不能污染其它对象；跨 Scope/定义/版本不共享事实身份；完整 checker 冷回放仍独立执行。

### 2. 修正已验证前缀的缓存失效边界

将“生产证书是否已经验证”与“当前调用能否读取这条事实”分开。前者绑定准确源条件、已提交内容、实际生产调用授权及规则/注册表；后者每次按当前 Scope、符号身份、有效性和准确输入检查。新增无关的后续调用、无关 Scope 输出不应使生产证明的验证缓存失效。

不要直接删除现有保护字段。先定义显式的源授权、Scope 可见性和生产授权指纹，分别覆盖旧字段的安全含义；真正改变授权、源条件、规则或前序证据时必须失效。缓存只存在于可信进程，不把“已验证”标记写进外部证据当作授权。

随后让恢复追加已认证的下一提交，避免 1+2+…+n 的前缀重放；失败依然丢弃私有事务。正常执行与 Retry 都应有精确重放次数断言，不能只检查答案。

### 3. 调试产物按版本落盘

按 semantic attempt、角色及内容版本避免重复转换、序列化和写出相同完整对象；保留请求、响应、失败记录和必要检查点。提供紧凑审计模式与完整诊断模式，正常模式保留最终可独立回放的完整证据，不能以删除验证和失败历史换取速度。

本次关闭全部调试输出只是测量成本上界，正式优化应保留审计能力。

### 4. 证据内容按 hash 共享

再将 previous_bound 的递归嵌入逐步迁移为证据 DAG 引用。冷回放包必须携带完整可达闭包；同一局部证书只存一份。该步骤涉及协议兼容、教学投影和恢复，风险与范围大于纯元数据缓存，不宜作为第一步。

### 5. 最后优化剩余数学热点

先完成以上测量驱动改造，再评估代数归约与策略匹配。当前证据不支持优先增加搜索额度，也不支持为了速度省略独立 checker。

## 性能门禁

分别测正常求解、独立冷回放、同进程缓存命中、Retry 恢复以及产物写出；每个场景至少多次运行，报告中位数与范围。保留真实操作数：生产证书重放次数、重复序列化次数、搜索候选及算术操作、峰值证据体积。验证冷缓存、失效缓存与拒绝用例，不以某次热缓存结果代替端到端性能。

建议首批实施第 1 项与第 2 项，随后做第 3 项；这比先重写搜索算法更符合当前证据。具体目标耗时应在重复基准后设定，本轮 15.98 秒是实验观测，不是正式实现的性能承诺。
