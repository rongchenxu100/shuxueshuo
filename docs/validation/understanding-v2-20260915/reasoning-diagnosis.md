# 单次 smoke 的推理输出诊断

检查范围：同一次语义调用的两次网络尝试，来源为 `live-audit.zip` 中的
`failed-attempts.json` 与 `request.json`。仅总结可观察的行为，不将推理中的草稿
视为正式响应、原图复核结果或已通过校验的题意。没有再次调用模型。

## 主要发现

两次返回开头都很早重述了定义、四个图景、角度倍数、长度倍数、面积比及正切目标。
因此，本次可观察到的主要消耗在于把题意组织成契约，而不是持续辨认字符。
由于同时提供了 OCR，这也不证明这些文字全部由视觉独立识别。

1. **定义形式化反复进行。** 多次讨论哪条对角线被平分、另一条线段比的方向、
   两种对角线角色乘两种比例方向应如何放入 all/any，以及交点 witness 和
   polygon_vertex 的写法。第二次过程中一度混淆被平分与取比例的对角线，随后
   在草拟的分支中改正。这里包含真实的语义建模难点，不只是字符识别。
2. **机器结构占据大量篇幅。** 反复选择 Part/Scope 层次、定义放在哪里、
   全局唯一 ID 的前缀、四个图景中同名点的隔离方式、点 M/D 的角色，以及
   source gaps、domain gaps、coverage 的关系。
3. **大量 JSON 写在推理通道。** 第一轮后半段草拟了接近整包的 JSON，直到
   match 尚未完成；第二轮多次草拟定义体，再开始书写整包，截断时仍在转录部分。
   这些内容没有进入最终 message.content，不能抽取其中片段当作成功返回。
4. **匹配不是主要难点。** 两次都能判断现有四个二次函数 family 不适用，选择
   unmatched 的方向明确。日志中未见尝试完成本题数值求解作为主要工作。
5. **原图确有缺口。** 图1～4缺失、□ABCD符号不明确，确实值得登记不确定性。
   第一轮草稿却补入 parallelogram，说明即使提高输出上限，也不能推断它将符合
   当前金标。第一轮 coverage 还引用了 scope ID，而校验要求具体图单元。

## 请求规模与契约说明问题

每次真实输入为25,844 tokens。实际模型提示词中的各组成部分，按紧凑 JSON 的
字符数计算如下（不是 tokens）：

| 部分 | 字符数 |
| --- | ---: |
| response_schema | 32,838 |
| 完整 observation_auxiliary | 29,629 |
| family_catalog | 2,455 |
| 合法示例 | 1,751 |
| 身份字段 | 193 |

系统提示另有约一千字。传入的观察还带有大量 provider、hash 和观察系统字段，
这些主要服务于程序审计。实际请求并非“读图后返回题面文字”，而是同轮完成
转录、通用图建模、定义形式化、来源关联和匹配五类工作。

Schema 明确了字段形状，但部分运行时语义没有同样明确地写入作者说明：

- bbox 为 `[x0,y0,x1,y1]`，模型却在考虑是否可能是 `[x,y,width,height]`。
- coverage 应指向实体/事实/目标/定义，而不是 Scope。
- source_gaps 与“可读内容是否完整编码”是不同判断，缺图不应自动等同领域 partial。
- 当前合法示例没有演示多作用域或参数化定义，模型需要自己设计完整编排。
- 系统提示写有“四个独立图景”，带入了本题数量，应泛化为“各独立图景”。

## 后续改进方向（本次未实施、未重新调用）

先压缩模型输入和减少表示选择：保留完整原图及有效 OCR/坐标/来源/不确定信息，
审计元数据由代码保存；从同一契约生成更紧凑的 Schema 与明确作者规则，补充
与本题无关的定义/作用域合法示例。可确定推导的 ID 命名、反向覆盖索引和哈希
交给程序，模型仍负责语义及来源关联，不由程序臆测条件。

增加输出上限只能缓解截断，无法保证消除重复组织或使错误结构通过校验。
若精简后仍不稳定，再讨论拆分题面提取与领域形式化；这属于修改已确认的调用边界，
不在本次检查中擅自执行。本次失败和一次语义调用记录保持不变。
