## 明确发现的问题

### 1. 南开：没有把持续的视觉疑问保留为不确定

原图中 DM 与 DN 之间的符号扫描不清。review 在 L13/L96/L124/L188/L220/L272/L302 反复怀疑它可能是一条横线、等号或其他符号。支持最终 confirmed 的理由包含：

> “不过题目显然需要 DM=DN，所以可接受。”（L220）

> “我不想报告错误。如果报告，会错误。应 confirmed。”（L272）

这是最有价值的发现：它识别了视觉风险，却用“常见题型应当如此”“否则题目不好确定”来消除疑问。日志没有给出后续看清等号的证据；已有 prompt 明确允许 uncertain/unreadable，因此也不是 Schema 没有出口。

这里**不判定 DM=DN 本身错误**。当前金标也是等长关系，数学语义比较通过；问题是来源可读性与确认依据。若最终仍无法从图片辨认，应使用 uncertain + unreadable/ambiguous，不能仅靠题型常识确认。这是金标等价检查容易遗漏、恰恰需要原图 review 负责的维度。

### 2. 多次重复已完成的检查

和平一模全文出现“连接BC”60 次，“常数”33 次；西青出现“常数”52 次；函数量词的短 review 也出现“实数”34 次。这些是可复现的字符串出现次数，**不是独立核对次数，更不是浪费 token 的精确占比**。

典型循环是：提出是否遗漏常数/连接声明 → 认为可接受 → 再提出同一疑问。和平二模也反复核对同一正方形顺序、交集写法和目标。缺少明确的覆盖完成与疑问关闭机制，使大量后续文字没有增加新来源证据。

### 3. review 不完全掌握候选契约

六次实际请求的业务载荷都是：`response_schema`、`math_expression_catalog`、`registered_families`、`candidate`、`few_shots`。

`response_schema` 是 **review 输出**的 Schema；没有发送 `problem-math-notation/v1` 的候选 Schema，也没有显式的代码校验通过摘要。当前 review 并未收到完整的目标类型枚举及各字段解释。南开 L292 于是猜测 `find_minimum` 是否合法、Schema 是否定义了 goal kind；多题也反复猜实数默认、常数声明和可选动点标签规则。其行为与这项输入缺口吻合，但不能由此量化缺口造成了多少额外 token。

补充：本地 `validate_match` 目前检查状态、注册 family ID、理由和字段一致性，并未证明 family 的数学适配。因此不能把所有 family 推敲都称为已由代码做完的重复工作；应先明确来源复核与题型适配检查的职责。日志把注册表里的 `path_minimum_target` 等内部概念误当成候选可能缺失的专用字段，则是可避免的契约干扰。

### 4. 会注意到 at，但理由有时过于依赖示例

河西 L30/L86/L167、西青 L80/L116/L218 明确讨论了 `at`，并非跳过没有检查。它主要用“当……时”和目录中的 `E=min(E)` 示例支持接受，没有系统说明目标参数是否独立于动点、优化范围是否一致或最小值是否可取到。

这两题最终接受的数学结果已由代码证书支持；不能再计为 review 漏检。不过，不能把同一段论证泛化到求动点位置或加入额外状态的情况。和平一模没有 `at` 也被接受，说明它至少没有要求所有“当最小值为……时”都补 at。

### 5. 推敲中也出现无依据的候选细节

西青 L120/L156 两次说 match_reason 出现“0次函数”笔误，而实际候选写的是“二次函数抛物线”。没有进入最终 findings，未造成修改，但说明长篇反复推敲本身也可能引入候选中不存在的内容，不能把 thinking 当成可靠审计凭证。

## 实际成本与评价边界

六次 review 累计 205.625 秒模型调用时间，输入 35,538、输出 41,798 token；输出中 41,732 是 reasoning，最终可见 JSON 合计仅 66 token。review 合计 77,336 token，占本批次总输入+输出约 40.02%；占累计模型调用时间约 51.13%。这些是 token 和累计耗时比例，不是账单金额或并发墙钟比例。配置已经是 thinking enabled、reasoning_effort=low。

六份被 review 的候选在当前金标语义比较中均通过，属于正例；K 题被代码缺图阻断，没有进入 review。因此本轮没有测到错误候选检出率、缺图漏报检出率或真实纠错效果。此前的 24 例是录制流程门禁，也不能替代真实模型负例评价。南开的来源不确定问题提示还应单独评价 unreadable/uncertain，不能只看金标数学关系是否相同。

## 建议的下一步（尚未实施）

1. **先守住来源证据边界。** 模糊符号只能由更清楚的图像证据确认，不能因“这种题通常如此”“否则不好解”而 confirmed。增加一个模糊关系应 uncertain、一个清晰关系可 confirmed 的独立图像例子。
2. **保留原始候选，补充简洁契约上下文。** 从现有 Schema 自动提取目标枚举与字段含义，附代码已通过 JSON/Schema/记法/类型检查的摘要；写明默认实数域、可选动点标签、可选最值下标及冗余连接声明的处理。无需把内部 IR 整包交给模型。
3. **围绕来源做一次覆盖核对。** 优先遗漏、符号范围、对象方向、分问归属、量词与区间、目标、污染和缺图；一项已经有依据确认后不再反复推敲。未关闭的视觉疑问应输出 uncertain。可记录简短来源摘录与候选路径作为覆盖证据，不要求输出长篇思考过程；更完整的审计协议需要另行讨论。
4. **用小规模真实负例决定是否保留全量 review。** 同一原图配正确候选及“只改一处、仍能通过代码”的错误候选：如反转射线、删正半轴、把 ≥ 改成 >、把局部条件提到父问、删除一个目标。记录具体检出、误报、不确定处理和成本，再判断收益。尚未发起付费评价。

当前建议是保留 review 的职责，但暂不将它视为已验证的质量保障，也不通过增加 thinking 预算解决重复问题。先修清晰可观察的输入契约与不确定性处理，再用真实负例测它是否能纠错。
