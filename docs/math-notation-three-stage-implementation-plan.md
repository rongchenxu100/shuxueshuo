# 数学题意与 Planner 简化：整体三阶段实施计划

日期：2026-09-17。阶段一已实现并完成独立 PostgreSQL/录制响应验收，见[实现说明](math-notation-stage-one-implementation.md)和[验收报告](validation/math-notation-product-stage-one-20260917/README.md)。日常/生产实例尚未迁移或部署；阶段二、三仍为后续计划。

## 当前基础与总目标

已完成 `problem-math-notation/v1` 抽取、代码校验、原图 review 和定向 repair 的独立闭环。目标 `at` 已删除；状态统一放在 facts，局部条件通过 children 限定作用域，不增加旧字段兼容层。

[最近一次 DeepSeek 七题真实闭环](validation/math-notation-state-facts-seven-20260917-094219/README.md)首轮及最终均为 6/7。六题严格通过且 review confirmed；K 题正确报告缺图并提前阻断，但仍有 k 作用域和四边形声明差异。该批次不能被写成 7/7。

[新旧对象树复审](validation/math-object-tree-state-facts-20260917/README.md)已覆盖五题人工样例与五题真实候选。对象与作用域能够对齐，但新题意到生产运行时的状态和参数绑定尚未完成。新抽取产物已支持独立候选/来源/运行记录入库，旧完整生成继续使用原正式题意路径。

最终形成：图片入库 → 简洁题意抽取、review/repair → 候选持久化 → 运行时绑定与求解准入 → 简洁 Planner 输入输出 → 现有执行器 → 讲解与页面。

数据保存与求解准入分别判断。缺图、题型未匹配、解析错误及复核不确定都必须留下数据和原因；只有满足运行时要求的当前题意版本才进入规划和求解。

## 已确认的设计原则：直接用数学表达式简化输入与输出

**通过直接的数学表达式大幅简化 LLM 的输入和输出，降低协议负担，提升数学规划表现，同时让人能够直接阅读和审阅。** 输入、输出和方法目录统一遵循这一原则。

- **JSON 组织结构，数学表达式承载语义。** 题设与方法参数直接使用 `a = 1`、`N ∈ ray(C,D)`、`min(sqrt(2)*MN + AN)` 等表达式；分问、方法调用、步骤依赖和答案来源保留必要的结构化字段。
- **LLM 表达数学决策，代码完成运行时绑定。** LLM 选择方法、必要数学参数和结果依赖；代码负责解析表达式、检查作用域、绑定对象与状态、生成内部引用、检查方法前提并执行。能由代码唯一确定的信息无需让模型重复填写，有歧义时给出诊断。
- **简化保持数学含义完整。** 参数范围、射线方向、联动关系、取等状态、分问隔离和合法分支必须保留；`min(S)=k` 与 `S=min(S)` 的区别继续显式表达。方法所需的 `free_parameters` 等数学选择与最值方法绑定的运动变量分别处理。
- **新增字段须有明确的数学用途。** 已删除的 `optimizations` 变量角色表不再加入简洁 Problem；已有路径、坐标和约束交由相应方法绑定。运行时句柄、状态版本和来源审计由代码维护。
- **同时验收可读性和模型表现。** 人工审阅确认表达直接、条件完整；真实规划批次比较首轮成功率、数学与绑定错误、重试次数、输入输出 token 和耗时。当前样例已支持可读性审阅，性能提升仍由后续实测验证。

## 阶段一：完成题意保存、查询与补充处理

目标：把已经实现的抽取闭环接入产品的数据与任务系统，让任何抽取结果都有可查询的记录。

### 实现内容

1. **建立候选与运行记录。** 新增抽取运行和不可覆盖的候选修订记录，关联 problem、图片集合、来源哈希、基准候选、契约版本及代码/模板版本。候选 JSON 和状态可在数据库查询；原图、完整请求响应和详细编译产物复用现有 artifacts 存储，并由数据库关联。
2. **保存所有结果。** 每次响应先可靠记录，再进行校验和采用判断。符合 Schema 的候选即使缺图、unmatched 或编译失败，也保存原候选及诊断；非法 JSON 仅保存原始响应和错误，不伪造有效候选。未被采用的 repair 返回保留在调用记录中，不覆盖当前候选。
3. **将状态分别记录。** 至少分别表达解析状态、来源复核状态、题型匹配状态、阻断原因、当前候选修订及求解就绪状态。缺图对应待补充；合法 unmatched 可以完成 review；review confirmed 不等于 solver_ready。
4. **接入现有 API、worker 和展示。** 提供候选详情、历史版本、诊断和调用记录查询；页面展示已提取内容及“待补图、待确认、题型暂未支持”等具体原因。本阶段的产品工作流在题意阶段结束。
5. **支持补图和人工修订。** 补图形成新的来源版本，人工修改形成新的候选版本，不覆盖原始证据；候选或图片变化使原来源复核失效，重新校验和复核。新增题型支持后，可对已保存候选重新编译、匹配，按版本和证据决定是否复用已有复核。
6. **迁移预算与恢复保障。** 将现有调用账本接到持久化运行记录，发送前原子预留预算，结合 worker 执行代次阻止旧响应覆盖新候选。已完成响应恢复处理；发送结果未知的调用明确停止，不能因数据库重试或消息重复投递再次付费。

当前 `product.services.save_revision()` 和 `problem_revisions` 要求旧领域校验通过。新候选采用独立存储，不把缺图或失败结果伪装为旧 VerifiedProblem，也不破坏正式题意修订的约束。

主要改动位置：`problem_understanding/workflow.py`、`workflow_ledger.py` 的存储边界；`product/models.py`、数据库迁移、`services.py`、`runner.py`、`api.py` 及对应产品页面。复用已有 artifacts、model_calls、diagnostics、任务事件和权限机制。

### 验收与交付

- 使用七题录制响应验证入库及查询：六题完整候选和复核可见，K 题缺图候选及失败原因可见；函数量词题保持 unmatched 且来源已复核。
- 增加非法 JSON、解析错误、review uncertain、被拒绝 repair 的保存用例；不能只验证成功路径。
- PostgreSQL/API 集成测试覆盖事务失败、重复请求、worker 中断恢复、并发修订、过期响应及跨用户/工作空间访问。
- 补图与人工修订生成新版本；旧复核不被错误沿用，原始记录可追溯。
- 存储接入优先通过录制测试验收，不因搬迁存储重复调用七题模型。

完成标准：题目无论是否能够继续求解，都能在数据库中找到题意候选或失败记录，并能通过 API/页面查看、补充和追踪版本。此时仍不把候选宣布为 Solver 就绪。

## 阶段二：完成运行时绑定并审阅简洁 Planner 输入

目标：让新题意能够提供完整、可验证的运行时输入，并给 Planner 一份人和模型都能理解的数学视图。

首批审阅材料：[五题简洁 Planner 题目输入示例与现有输入对照](planner-compact-input-five-case-review.md)。五份简洁输入统一使用 JSON，与现有题目 JSON、原 ProblemIR 逐题对照，并提供覆盖清单和紧凑 JSON 字符统计。已删除额外的 `optimizations` 字段，最值变量由相应方法根据题意绑定；另附河西Ⅲ的完整单目标步骤 JSON。运行时绑定和新输出协议尚未验收。

### 实现内容

1. **补完新题意到运行时的适配。** 从编译后的数学对象和关系生成现有 ProblemIR、PlannerStateContext 所需内容，建立对象、状态、目标、作用域及来源的绑定。内部 ID 和状态版本由代码生成，不要求抽取 LLM 输出。
2. **维护条件与状态的数学区别。** `min(S)=c` 与 `S=min(S)` 分别保留；局部条件不提升到父问，兄弟问不串用对象。最值变量省略不等于所有字母共同优化，也不等于没有变量；无法唯一绑定时返回明确诊断。
3. **补齐五题迁移差异的证据。** 使用已冻结的真实候选和原图审计结果，逐项确认坐标别名、几何等价、最优状态及方法前置条件的映射。不以最终答案一致代替原始条件树和运行时状态正确。
4. **显式判断求解准入。** 当前候选解析有效、来源证据有效、无缺图等阻断、题型受支持、运行时绑定及方法前置检查通过后，才允许进入已有求解入口。不能仅凭 family matched 或 review confirmed 设置 solver_ready。
5. **生成简洁 Planner 输入。** 提供数学题意、当前作用域与继承条件、所求、已知的可用结果和方法数学签名。省去模型不需要的内部句柄、哈希与状态槽，代码保存可追溯映射；任何压缩不得删掉影响题意或方法选择的关系。
6. **形成具体可审阅样例。** 五题逐题展示旧输入、新输入、覆盖清单、字符与 token 统计；增加同名对象跨图、兄弟问隔离、多目标、量词、缺图和 unmatched 示例。先审阅这些实际输入，再在阶段三定下简洁输出协议。

主要改动位置：`problem_understanding` 的编译与新运行时适配层、`solver/extraction` 的题意授权边界、`solver/runtime` 的规划上下文与 prompt 渲染。已有 `math_tree_audit` 用于差异审计，不直接变成生产运行时 IR。

### 验收与交付

- 五题人工样例和五题真实候选分别进行运行时绑定测试，逐目标覆盖实际 Method 所需的输入及条件来源。
- 用已有受信计划执行适配后的输入，隔离验证数据迁移，不把新 Planner 的不确定性混入绑定验收。
- 错误状态、射线/直线替换、比例颠倒、条件错问、引用不可见对象等反例必须被发现。
- K 题缺图、函数量词题未覆盖 family 时，候选继续可查询，并明确阻止进入当前求解链路。
- 对已知 K 题 k 作用域及构型遗漏分别保留诊断；只能通过来源纠正或有前提的通用证明处理，不通过放宽比较器提高通过率。

完成标准：五道支持题的新输入能正确绑定并驱动现有执行器；简洁 Planner 输入逐项覆盖必要语义且可供审阅。不能将“数学对象树对齐”单独当作本阶段完成。

## 阶段三：简化 Planner 输出并完成端到端接入

目标：让 Planner 返回简洁数学步骤，由代码编译、执行，并验证后续讲解与页面。

### 实现内容

1. **冻结简洁计划契约。** 基于阶段二的实际样例确定方法选择、数学参数、结果命名、步骤依赖、作用域、目标绑定，以及多结果和分支选择的表达。LLM 只给必要的数学计划；内部对象 ID、状态版本及执行结构继续由代码管理。
2. **实现计划编译与校验。** 用受限语法解析数学参数，绑定可见对象和已完成步骤结果，检查类型、作用域、依赖、方法前提及目标覆盖，编译到现有计划和 MethodInvocation。遇到未知表达或绑定歧义，给出具体错误。
3. **接入 Planner 的定向重试。** 复用现有受控重试预算，反馈错误步骤及允许修改范围；模型计划错误可以修复，编译器缺口和输入缺失明确停止。不能为通过执行而删题设、换目标或补未证假设。
4. **完成产品流水线贯通。** 将阶段一保存的当前候选、阶段二的运行时授权、简洁计划、执行结果及教学证据按版本关联，接通讲解、LessonIR、图形和页面生成。某题求解失败仍能查看其题意与完整调用记录。
5. **切换本地默认路径并清理旧入口。** 端到端门禁通过后，在未上线环境中切换默认流程，删除被替代的旧输出要求；冻结的历史批次继续作为证据，不新增旧 at 适配。生产部署单独进行。

主要改动位置：Planner prompt/Schema 和编译器、`solver/runtime/strategy_runtime_planner.py`、现有执行器对接、`product` 流水线与复核展示；讲解阶段优先复用现有已验证执行证据。

### 验收与交付

- 先完成录制计划、编译器及失败重试回归，再开展真实模型集成。
- 五道已有题型跑完整“图片 → 提取与复核 → 入库 → Planner → 求解 → 讲解/页面”；逐题检查答案、方法前置条件、对象/状态来源和教学证据。
- K 题及函数量词题分别验证缺图阻断与未支持题型分流，均保留数据库记录；不要求它们在当前 family 范围内被强行求解。
- 增加独立的等价改写和错误计划用例，验证通用规则，避免只对七题固定字符串有效。
- 报告按阶段统计输入/输出 token、reasoning、模型调用次数、耗时、首轮/重试结果和阻断状态；录制测试与真实运行成绩分别记录。

完成标准：支持的五题全链路可执行并产出经过验证的讲解页面；缺图、未支持及失败题完整留存且状态准确，恢复和追溯不依赖临时测试目录。

## 执行顺序与预算

按阶段一 → 阶段二 → 阶段三推进，每阶段都交付代码、测试、具体数据样例和可审阅报告。已有[对象树—Planner 三阶段技术路线](math-planner-simplification-stages.md)继续作为迁移子计划，其对象树审计成果作为本计划阶段二的输入。

真实调用前冻结代码、Schema、所有模板、图片及验收数据。抽取闭环继续沿用内容最多3次、review最多3次、总语义最多6次、网络尝试最多12次的单题上限；DeepSeek并发上限3，每次300秒、16,384输出token。Planner与后续讲解的预算在相应真实批次运行前单独明确，不把抽取预算误用为整条流水线预算。

同一冻结批次失败后先用原始响应离线复现与分类，不自动追加付费批次，不把离线修复后的回放成绩覆盖成原始真实成绩。阶段一已完成；下一步为阶段二的新题意到运行时适配、求解准入和简洁 Planner 输入审阅。
